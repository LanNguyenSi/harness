# harness CLI reference

Tracks the verbs available on the `harness` binary in the current release. Notes carry version-specific detail. For policy semantics see [`docs/policy-packs/`](policy-packs/); for the risk gate specifically see [`docs/risk-gate.md`](risk-gate.md).

The CLI is grouped by purpose below. Run any verb with `--help` for flags and examples.

## Manifest and config

| Verb | One-liner |
|------|-----------|
| `harness init [--template minimal\|solo\|team\|full] [--interactive] [--probe]` | Bootstrap a starter `harness.yaml` (default template: `minimal`). `--interactive` walks the wire-up Q&A and writes `harness.lock` + `harness.generated/`. `--probe` emits a JSON snapshot of detected runtimes and exits. |
| `harness apply [--runtime claude-code\|codex\|opencode] [--target <path>] [--merge\|--force]` | Render the manifest into the config files the agent runtime actually reads. Without `--runtime`, apply reuses the runtime the last apply recorded in `harness.generated/.last-apply` and says so (`runtime: codex (from last apply; pass --runtime to change)`); an explicit `--runtime` that differs is honoured and both `--dry-run` and the apply name the switch (`runtime: codex -> claude-code`). A `.last-apply` from an older release, which has no runtime field, is read through its files map (only `codex/config.toml` means codex, and so on; when both `settings.json` and `codex/config.toml` are present, the recorded policy-pack `instructions.md` entries decide if every one names the same runtime in its `## Runtime` section; only the packs the record's own manifest snapshot lists count, when it has a readable one) and the output says the runtime was inferred; when that is ambiguous, or with no `.last-apply` at all, the default is `claude-code` (for an older record the output says so and names the runtimes the record holds files for, e.g. `generated files for claude-code and codex; pass --runtime codex to keep codex`), which writes `~/.claude/settings.json` / `harness.generated/*`; `--runtime codex` emits `harness.generated/codex/config.toml` (`--install` merges it into `~/.codex/config.toml`); `--runtime opencode` emits `harness.generated/opencode/opencode.json` (MCP servers only, not auto-installed). `--target <path>` (claude-code only: without `--runtime` it implies `claude-code` and the output names it; rejected with an explicit `--runtime codex` or `--runtime opencode`) additionally writes settings.json to `<path>`, `--merge` 3-way-merges it, `--force` overwrites it. |
| `harness describe` | Print the effective merged manifest (inherited packs + local overrides). |
| `harness validate` | Lint the manifest and referenced assets without writing anything; do not execute manifest version commands. `tools.cli[].min_version` warns to run `harness doctor` (`--strict` promotes the warning to an error). |
| `harness diff` | Show what `apply` would change against the currently rendered config. |
| `harness adopt <file>` | Take an existing config file under management. |
| `harness add mcp\|cli\|skill\|hook <name> [opts]` | Insert a new managed entry into `harness.yaml`. Subcommands cover the four entry kinds. |
| `harness remove <type> <name>` | Inverse of `add`. |
| `harness export` | Dump the operator-declared manifest to stdout (e.g. for sharing or PRs), minus the `workflows[]`-derived merge-gate policies; `harness list policies` shows those, marked "(derived from workflows[])". |
| `harness pack add <name>` / `harness pack remove <name>` / `harness pack list` / `harness pack reseed <name> [--dry-run]` | Manage `policy_packs[]` entries (`list` takes no name). `remove --force` also deletes the pack's generated files and prunes their entries from `harness.generated/.last-apply`, keeping the record's other fields, including the runtime it records, so the next plain `harness apply` still reuses that runtime. `reseed` pulls the shipped builtin template's `config.ux` (and `config.producers`) for `<name>` into the manifest, preserving every other key (for example `protected_branches`); this is the supported way to pick up a deny-message wording fix on an already-installed manifest. A manifest that still names the removed `understanding-before-execution` pack loads with a warning and the entry is ignored (`remove --force` still deletes the entry and its generated files). The same `pack` namespace also carries the runtime hook entrypoints under `harness pack hook ...` (see below); there is no separate top-level `harness hook` runtime namespace. |
| `harness uninstall` | One-command teardown across the state root (`~/.harness/`, legacy `~/.claude/`) and `~/.claude/settings.json`. Dry-run by default; pass `--apply` to commit. |
| `harness migrate-home` | Move state from `~/.claude/` to `~/.harness/` (introduced in `v0.24.0`, legacy fallback still live). Dry-run by default; pass `--apply` to commit. |

## Health, audit, and observability

| Verb | One-liner |
|------|-----------|
| `harness doctor [--target codex\|opencode] [--rm-rogue-ledgers] [--yes]` | Health summary across hooks, packs, MCP registrations, runtime detection, and binary version. A bare run is read-only; `--rm-rogue-ledgers` opts into deleting each rogue evidence-ledger directory it finds (prompts per hit; add `--yes` to skip the prompts). Exits `1` when the report's `errorCount` is above zero (in both prose and `--json` mode) so CI/scripts can gate on doctor health; warnings alone (`warningCount`) still exit `0`. `--target codex` / `--target opencode` verifies that runtime's adapter wiring after `apply --runtime <same>` (config artefact presence/banner +, for opencode, every projected MCP server's command resolving on PATH). Policy packs are expanded for the pack checks (hook `min_version` floors, declared-but-not-live packs) against the runtime a plain `harness apply` would select (recorded in `.last-apply`, inferred from its files, else `claude-code`, through apply's own `selectRuntime`), never against `--target`, and the report names it (`Pack expansion runtime: codex (recorded by the last apply)`; `packExpansionRuntime` in `--json`; a malformed `.last-apply` falls back to the default and adds a warning naming the file). |
| `harness list <category>` | Print one category's entries as a flat table or JSON. Valid categories: `mcp`, `cli`, `skills`, `memories`, `hooks`, `policies`, `workflows`. `memories` rows carry a `project_rejected` field only when `--project` was supplied and rejected by `isValidProjectName` (see the SINK GUARD note below); `harness list` itself prints no warning for it, unlike `harness doctor`. |
| `harness audit [--since 1h] [--policy <name>] [--outcome <outcome>] [--session <id>] [--json]` | Replay recorded policy decisions from the evidence-ledger. `--json` also carries the resolved `sessionId`. |
| `harness session-export [sessionId]` | Export the full evidence-ledger for a Claude Code session as JSON, suitable for archival or attaching to a PR. |

## Policy runtime

`harness policy intercept` is the runtime evaluator that Claude Code calls on every tool event. The other policy-debug verbs are top-level (not nested under `policy`).

| Verb | One-liner |
|------|-----------|
| `harness policy intercept` | The runtime evaluator that hooks call on every PreToolUse / PostToolUse. Supports `--hook <name>` (v0.29.0) to scope evaluation to a single hook generator. |
| `harness explain [policy] [--trace] [--last]` | Print a policy's definition; `--trace` reads the last recorded evaluation; `--last` traces the most recent decision in the ledger. |
| `harness explain-action <event.json>` | Reason about a single hook event JSON file and print the Action Envelope the Risk Gate sees (Risk Gate debug verb, Phase 7). The envelope carries the same leading-Bash-prefix git context as `harness policy intercept` (leading `cd`, leading `git switch`/`checkout`); inline `VAR=value` is not part of the envelope, so it does not show here. `--config`/`--project` select the manifest, read only for a leading `git switch`/`checkout`; with no manifest at the default location (and no `--config`) the verb uses an empty manifest, so the switch upgrade is a no-op, while an explicit `--config` that is missing still fails. |
| `harness explain-policy <policy>` | Resolve and print a single policy by name (after merge + overrides) and whether it would apply to a tool event. The Action Envelope is enriched by the same Bash-prefix merges as `harness policy intercept` (inline `VAR=value`, leading `cd`, leading `git switch`/`checkout`), so the environment it reports matches the hook; it still reads no ledger, and its `parity` block names what it does not evaluate (`ledger_requires`, `kubectl_target`) and sets `kubectl_target_present: true` when this event's command is a `kubectl` invocation with an explicit `--context`/`--namespace`/`-n` (the merge the hook would apply but this verb skips). |
| `harness test-risk <event.json>` | Replay an event against the Risk Gate and print the assigned tier. The tier is unchanged by the shared enrichment (the classifier reads the raw command); the verb routes through the same helper as the other debug verbs for consistency. |
| `harness resolve-env <event.json>` | Resolve which `environment` block a given event maps to. The Bash-prefix enrichment is shared with `harness policy intercept`: inline `VAR=value` assignments, a leading `cd`, and a leading `git switch`/`checkout` are merged the way the hook merges them (so `DATABASE_URL=...prod... psql ...` resolves like the gate, not `unknown`). The `kubectl --context`/`--namespace` merge stays hook-only: `resolve-env` reports the ambient kube context, and `harness explain-policy` flags such an event with `parity.kubectl_target_present`. Ledger-free. |
| `harness dry-run <prompt>` | Statically predict which hooks fire, which policies match, and which memories route for a prompt. |

## Hook entrypoints

These are called by Claude Code via `settings.json`; you usually do not run them yourself. They are documented here for operators reading their settings files. All runtime hook entrypoints live under the `harness pack hook ...` namespace (the table previously showed a `harness hook ...` spelling that does not exist; `harness add hook <name>` is the unrelated manifest mutation).

| Verb | Called from |
|------|-------------|
| `harness pack hook branch-protection [--runtime claude-code\|codex]` | `PreToolUse` branch-guard for the protected branches (task `a4d8adc5`): asks git (`git -C <dir> symbolic-ref -q HEAD`) for the branch of every directory the call writes into and refuses when git names a protected branch (compared case-insensitively) or cannot answer; outside every repository and on a detached HEAD it allows. Claude Code gets a JSON deny envelope on stdout (exit 0); `--runtime codex` exits 2 with the reason on stderr. See [`docs/policy-packs/branch-protection.md`](policy-packs/branch-protection.md). |
| `harness pack hook runtime-reality` | `PreToolUse` drift gate (v0.31.0, opt-in): before destructive runtime commands, probes live process state and denies on critical drift against the expectations file. Fail-open on probe errors. See [`docs/runtime-reality-hook.md`](runtime-reality-hook.md). |

## Operator approvals

`harness approve <kind>` is the operator-driven approval surface; `risk` is the only kind left (the `understanding` kind is removed together with the understanding-before-execution pack). It records a best-effort evidence-ledger tag that the Risk Gate's `requires.ledger_tag` consults. Operator surface; agents cannot self-approve.

| Verb | One-liner |
|------|-----------|
| `harness approve risk [--scope deletion] [--force <reason>] [--i-am-the-operator]` | Write `risk-approved:` to clear the current Risk Gate `require_approval` tier. `--scope deletion` writes the dev-context deletion arm's own `risk-approved:deletion:` tag instead of the shared production tag (`gate-dev-unsafe-deletion`, see docs/risk-gate.md). `--force <reason>` only unblocks `deny`-tier (writes `risk-override:`) and requires a non-empty reason; from `!`-shell calls add `--i-am-the-operator`. |

Removed in task `a4d8adc5`: `harness approve branch-protection` and `harness session-start branch-check`. Removed in task `f3f15290`: the entire `harness session-start` command group (`preflight`, `toolchain-parity`, `stale-base-check`) and the top-level `harness preflight` alias. The branch-protection gate asks git for the branch on every call and keeps no ledger tag or override marker; to edit a protected branch deliberately, switch the gate off from an operator shell (`harness gate disable`, below).

## Smoke

| Verb | One-liner |
|------|-----------|
| `harness smoke` | End-to-end smoke run for the installed harness (hook plumbing, ledger write, policy evaluation). Useful after a fresh `init --interactive` or a version bump. smoke applies the `claude-code` variant into its own `<output-dir>/harness.generated/` (next to the rendered `settings.json`, kept with the other run artifacts and not cleaned up), never into the operator's `harness.generated/`: the apply output (the generated files and `.last-apply`) of the operator's tree stays byte-identical, so a codex machine's audit copies and recorded runtime are untouched and the next plain `harness apply` has nothing to restore. ## Evidence-ledger producers (`harness record`)

`harness record {review,review-subagent,dogfood}` are the interactive producers for the `review-before-merge`, `review-subagent-before-pr-create`, and `dogfood-before-release` process-gate families (both the MCP and gh-cli `-bash` variants of the first two; see `src/cli/init/templates.ts` for the exact policy definitions and `docs/writing-custom-policies.md` "the trust model" for what a process gate does and does not enforce). Unlike a hook entrypoint, these are never called by Claude Code itself — an agent or operator runs them deliberately after doing the underlying work (a review pass, a review-subagent pass, an end-to-end smoke run) — so a failure (unreachable ledger, no resolvable git context, an empty summary) exits non-zero with a clear stderr reason instead of degrading silently.

| Verb | One-liner |
|------|-----------|
| `harness record review <summary> --pr <number> [--base <branch>] [--branch <name>] [--task <id>] [--session <id>] [--ledger-timeout <ms>]` | Writes ONE ledger fact carrying `review:<pr>` + `review:<branch>` (+ `review:<base>` when a base resolves, + `review:<task-id>` with `--task`) so a single review satisfies the gate regardless of which merge surface fires. `--task` is what the `review-before-task-merge` / `review-before-task-finish-automerge` gates read; pass it and one call covers all four merge surfaces. See "Tag semantics" below. |
| `harness record review-subagent [summary] (--task <id> \| --adhoc) --verdict <text> [--branch <name>] [--session <id>] [--ledger-timeout <ms>]` | Writes ONE ledger fact carrying `review-subagent:<task>` + `review-subagent:<branch>` verdict:`<verdict>`, same multi-tag rationale as `record review`. Exactly one of `--task` or `--adhoc` is required (neither, or both, exits `64` naming both options). `--adhoc` records a review for work that has no agent-tasks task: the fact carries `review-subagent:<branch>` only, with no task tag, so it satisfies the `-bash` gate for that branch and carries nothing for the MCP-surface `review-subagent-before-pr-create` gate (which keys on the task id; matching is substring-based, see "Substring matching and the advisory trust model" below). With no resolvable branch (detached HEAD) `--adhoc` refuses until `--branch <name>` is passed. |
| `harness record dogfood <summary> [--session <id>] [--ledger-timeout <ms>]` | Writes `dogfood:<sessionId>` for the current session. |

All three also accept `--config <path>` and `--project <name>` for manifest resolution, same as every other verb.

### Tag semantics — single source of truth

This table is the canonical mapping from process gate to the ledger tag it consults and how that tag's value is resolved. If you are wiring a custom policy that reuses one of these tag families, resolve it the same way the corresponding gate does.

| Gate (`policies[].name`) | `requires.ledger_tag` | Value resolved from |
|---|---|---|
| `review-before-merge` (MCP surface) | `review:${PR_NUMBER}` | `toolArgs.prNumber` on the `mcp__agent-tasks__pull_requests_merge` call |
| `review-before-merge-bash` (gh-cli surface) | `review:${BRANCH}` | the local `.git` checkout's current branch at the moment `gh pr merge` fires (or an explicit `--branch` override) |
| `review-subagent-before-pr-create` (MCP surface) | `review-subagent:${TASK_ID}` | `toolArgs.taskId` on the `mcp__agent-tasks__pull_requests_create` call |
| `review-subagent-before-pr-create-bash` (gh-cli surface) | `review-subagent:${BRANCH}` | the local `.git` checkout's current branch at the moment `gh pr create` fires (or an explicit `--branch` override) |
| `dogfood-before-release` | `dogfood:${SESSION_ID}` (within 24h) | the current session id |

**Substring matching and the advisory trust model.** `requires.ledger_tag` is a *substring* match against evidence-ledger entries, not an exact one — so `review:4` also matches a stored `review:42`, and any text a `record` verb writes verbatim (a `<summary>` / `--verdict` string) that happens to embed another tag's literal text (`review:99`, `dogfood:<some-session-id>`, ...) can satisfy that OTHER tag's gate too. This is not a new capability the `record` verbs introduce: the same substring match already applies to any `ledger_add` call an agent can make directly. Per `docs/writing-custom-policies.md` (tripwire 4, "the trust model"), `requires.ledger_tag` is advisory against the agent it gates by design — whoever can write the ledger can open the gate. Treat everything `record` writes as an audit trail an agent can also fabricate, not as a security boundary.

**Tag-injection validation.** The verbs refuse the values that would plant a second tag through the verb itself (task `237cc609`). Every ref-like or id-like value that is embedded in a ledger tag (`--branch`, including a branch resolved from git when no `--branch` is given; `--base`, including the origin/HEAD fallback; `--task`; `--pr`; and the session id `record dogfood` writes as `dogfood:<session>`, passed as `--session`) is refused with exit `64`, naming the flag, when the trimmed value contains a `:` or any ASCII whitespace (space, tab, CR, LF, VT, FF). Git ref names forbid both, so a real branch (`feature/x`, `fix/237cc609-record-tag-injection`, `release/1.2.3`, `user/some_name-2.x`) is never refused, and the structural rule closes every tag namespace for these values, custom ones included (`clean-check:master`), without listing them; free text (below) is checked only against the six gate-opening namespaces listed below, so a custom namespace such as `clean-check:` in a verdict or summary is not refused. Unicode whitespace without a `:` (for example a no-break space) cannot form a tag token under substring matching and stays accepted. Free text (`--verdict`, the summaries of all three verbs) stays free: it is refused with exit `64`, rather than rewritten so the recorded audit text is never altered silently, only when it contains one of `review-subagent:`, `review:`, `dogfood:`, `preflight:`, `risk-approved:` or `risk-override:` immediately followed by a non-whitespace character (case-sensitive, like the gate matcher, so `xreview:master` is refused too); prose such as `code-review: approved` or `preflight: green` is kept. Task, PR and branch values share tag namespaces (`record review-subagent --task master` writes `review-subagent:master`, and `record review --pr master` or `--task master` writes `review:master`, the same tags a branch named `master` produces), so the validation does not stop a value that is itself a valid branch name; `ledger_add` and the substring matcher are unchanged, so the advisory trust model above still holds.

**The merge-surface trap.** A gate is evaluated against whichever tool call actually fires — the PR number on an MCP merge, or the local `.git/HEAD` branch on a `gh pr merge` — and the runtime has no way to cross-reference the two at gate time (a checkout's branch is not guaranteed to match the PR number an operator has in mind, and either surface, or both, may be wired). That is why `harness record review` and `harness record review-subagent` each write a **multi-tag fact** — `review:<pr>` and `review:<branch>` together, not one or the other — in a single ledger write: recording a review once satisfies whichever surface's gate fires at merge/PR-create time, instead of requiring the operator to predict which surface will be used and record twice.

**Base-checkout coarsening (bash surface, deliberate).** `review-before-merge-bash` matches `review:${BRANCH}` against whatever branch is checked out at `gh pr merge` time, and `record review`'s own `review:<base>` tag lives in that exact same string space. Consequence: once ANY `record review` call in a session has a base that resolves to (or was passed as) `<X>`, that fact ALSO satisfies `review-before-merge-bash` for a `gh pr merge` fired from a checkout of `<X>` — for a PR that was never reviewed. For example, review a feature PR whose base auto-resolves to `master` once; every later `gh pr merge` run from a `master` checkout in that same session now passes the gate too, regardless of which PR it merges. This is a deliberate consequence of the bash surface already being session-coarse and branch-keyed rather than PR-exact (`gh pr merge`'s arguments carry no PR number a hook can extract, so the surface was never per-PR-precise; `--base` just adds one more string that can accidentally land on it). The MCP surface (`review-before-merge`) stays PR-exact because it keys on `toolArgs.prNumber`, never on a branch name. If per-PR precision on the bash surface matters, avoid merging unrelated PRs from a base-branch checkout within the same session as a `record review` call, or prefer the MCP merge surface.

**`--pr` / `--task` are namespacing sugar on the bash surfaces.** `record review --pr <number>` and `record review-subagent --task <id>` (unless `--adhoc` is used instead) are required on every surface, but `review-before-merge-bash` and `review-subagent-before-pr-create-bash` key on `${BRANCH}` alone, so they never read the PR number or task id back out of the fact. On those two surfaces the value only namespaces the `review:<pr>` / `review-subagent:<task>` tag (useful for audit, harmless if it does not match a real PR/task) and any non-empty placeholder satisfies the CLI's own syntax; the branch tag is what actually opens the gate. Only the MCP surfaces (`review-before-merge`, `review-subagent-before-pr-create`) key on the PR number / task id for real.

**`--task` for the task-scoped merge surfaces.** `mcp__agent-tasks__task_merge` and `mcp__agent-tasks__task_finish` with `autoMerge: true` both merge the PR attached to a task, and both derive owner/repo/PR number from the task, so the only identifier in their tool payload is `taskId`. Their gates therefore key on `review:<task-id>`, which no other tag family carries: without `--task`, a recorded review satisfies the `pull_requests_merge` and `gh pr merge` gates but not those two. The id is validated loosely (non-empty, no `:`, no ASCII whitespace) because it only namespaces a tag; a value with internal whitespace is rejected because it would split into two tags in the fact content and satisfy a gate keyed on the first half, and a `:` because it would turn the value into tag text of another namespace.

**`--base` for non-default-base PRs.** `record review`'s `review:<base>` tag defaults to the repo's remote default branch (read from `refs/remotes/origin/HEAD`, packed-refs fallback — including through a linked worktree's `commondir` indirection), which is correct for an ordinary feature PR merging into `main`/`master`. A PR that targets a non-default base — for example a `release/*` branch — needs an explicit `--base <branch>` so the recorded `review:<base>` tag reflects the PR's actual target instead of silently recording against the wrong base; omitting `--base` when neither the flag nor origin/HEAD resolves prints a loud stderr warning rather than dropping the tag silently.

Warn-only, same as the sibling pack-level floor: a below-floor pack-contributed hook still runs in degraded mode rather than failing the check outright, and the section stays silent when nothing to report.
- Ledger tag vocabulary used by gate-mode policies: `review:`, `risk-override:`, `risk-approved:`. Only the Risk Gate's `requires.ledger_tag` actually consults a ledger tag to unblock (scoped to a Claude session id, not the agent-tasks task UUID, see `feedback-agent-grounding-merge-gate-ledger`). ### `--project` name validation

Every command that takes `--project <name>` (and every caller that builds `LoaderOptions.project` by hand) feeds the name into path joins and `{project}` substitutions. This note covers how that name is screened.

**SINK GUARD (task `1c4eb3ea`; task `e904f25a`):** `isValidProjectName` (`src/io/project-name.ts`, moved from `src/runtime/git-context.ts`, task `b5e6ccb0`, which now re-exports it) screens a project name at the SOURCE, on two independent grounds: the shapes that escape a path segment (the empty string, `.`, `..`, a forward slash, a backslash) and, since task `e904f25a`, any control character (C0 `U+0000` to `U+001F`, which includes NUL, LF, CR and ESC; DEL `U+007F`; C1 `U+0080` to `U+009F`, NEL included). It is exported for reuse at each of `{project}`'s four interpolation sinks; three are guarded, one remains open. Leaving that one open is accepted rather than a live escape: it is reached ONLY through an explicit `--project <name>` flag an operator passes by hand, never through a cwd-derived name (`deriveProjectName` validates its own return value before any sink sees it). That sink calls the validator nowhere, so it inherits NEITHER screen; the control-character rule stated below is a property of the guarded paths, not of the whole codebase.

- `resolvePaths`' `path.join` sink (`src/cli/loader.ts`) — guarded since task `1c4eb3ea` (defense in depth: `deriveProjectName` already validates its own return value before this sink is reached from anywhere else); an invalid name resolves `projectLayer: null`, same as "no layer on disk".
- `substituteProject` (`src/probes/memory.ts`) — guarded since task `e904f25a`; an invalid name degrades to the "no project supplied" branch, so `{project}` survives substitution and reports `unresolved: true` instead of escaping the intended directory. Substitution runs AFTER `expandHome` and uses a literal `split`/`join` (never `replace`+regex), so `$'`/`` $` `` insert literally and `~` never re-anchors a relative pattern to the home directory.
- `generate-memory-index.ts`'s own `{project}` substitution — unguarded; that file is reserved for a separate slice (see [CHANGELOG.md](../CHANGELOG.md) for the reservation), so guarding it is left to that slice rather than worked around here. Reached only through an explicit `--project`, never through a cwd-derived name.
- `buildLockEntries` (`src/io/harness-lock.ts`): guarded since task `b5e6ccb0`; an invalid name skips the templated directory's lock entry the same way an absent `opts.projectName` already did, so the raw value never lands in `harness.lock` and can never resurface in `harness diff --since-apply`'s drift list on a later run that passes no `--project` at all.

A rejected `--project` value (one that fails `isValidProjectName`) is reported distinctly from the ordinary "no project supplied" case: `harness doctor` renders it as its own warn line, gated on at least one memory directory actually carrying the `{project}` placeholder (`MemoryReport.projectRejected`, `src/probes/memory.ts`), while `harness list memories` carries the same value only as a conditionally present `project_rejected` row field (present only when rejected, absent otherwise, since `renderText` derives its columns from the first row) and prints no warning of its own; only `harness doctor` warns. Two complementary rules, not an enumeration of rendering sites, keep a crafted `--project` value out of `harness doctor`'s and `harness list memories`' rendered output. First, an ACCEPTED name cannot carry a control character at all, because `isValidProjectName` refuses one at the source (see SINK GUARD above); that also covers the surfaces that render the SUBSTITUTED directory path rather than the name itself, doctor's `memory directory missing` line and `list memories`' `path` row field, which no per-site escaper of the name would have reached. Second, a REJECTED name is by definition unvalidated and is still echoed back so the operator can see WHICH value was refused, so every such echo goes through `sanitizeProjectForDisplay` (`src/io/project-name.ts`, moved from `src/runtime/git-context.ts`, task `b5e6ccb0`, which now re-exports it), which strips the same control characters: doctor's rejection warning, its per-directory note, its header `project:` clause (which renders the raw `--project` whether it was accepted or rejected), and `list memories`' `project_rejected` field (and with it the text table derived from it). Report DATA keeps the raw value (`DoctorReport.project`, `MemoryReport.projectRejected`), carried over `--json` by JSON's own escaping rather than by a raw control byte. A cwd-derived name containing a control character is rejected exactly the way a `..` basename already was: `deriveProjectName` returns `null`, no project override layer resolves for that repository, and the base/machine value applies, with no error and no warning.
