## Context

### The problem

The `understanding-before-execution` pack (UG) blocks Edit / Write / Bash until an operator has approved the agent's Understanding Report. Every one of the pack's modes ends in the same human step: `harness approve understanding`, run from a shell the hooks do not gate (`docs/policy-packs/understanding-before-execution.md:666-678#"the flipped report and the ledger row are the audit records beside it."`, "Approving an Understanding Report"; `docs/okf/understanding-gate-lockout-recovery.md`, "Recovery: exact steps").

Agent harnesses also run in modes where no human sits in the loop mid-run: Claude Code `--permission-mode bypassPermissions` and `--dangerously-skip-permissions`, Codex full-auto, opencode `--auto`, and headless `claude -p` child processes (harness's own smoke runner spawns exactly that shape: `src/cli/smoke/runner.ts:64-70#"bypassPermissions"`). In those modes the human approve step has nobody to perform it. Today the outcome is a hard block on the first gated tool call, and for a `-p` child a run that ends in `permission_denials`.

A `claude -p` child is the sharpest case: it has its own session id (each `-p` run gets a fresh one, `dogfood/ug-auto-mode-signals/README.md` results section (d); a launcher may choose it via `--session-id`), so it finds neither a marker nor a persisted report for itself, and the Stop-hook report capture fires only once at the end of the run, after every tool call it would have needed approval for.

### Invariants that must survive

1. **The signed marker is the only approval authority** (task 7402301d, agent-tasks/88ca4bb3, harness/f9485cc7). The gate decides on `checkOperatorApprovalMarkers` and nothing else; persisted report and ledger row are audit evidence (`src/cli/pack/hook-pre-tool-use.ts:4-8#"JSON to stdout when no valid marker approves."`; `docs/okf/evidence-ledger-trust-boundary.md`, "The invariant").
2. **Agent-writable evidence never opens a gate.** The ledger is agent-writable via `ledger_add`; the persisted report is written by the agent's own Stop hook. Neither may become an approval source again (`docs/okf/evidence-ledger-trust-boundary.md`, "What breaks it").
3. **Fail closed on ambiguity.** A missing, unknown, or unlisted signal must resolve to today's behaviour (block), never to an approval. This is the same posture `checkApprovalMarker` already takes for a malformed session id or an unverifiable signature (`src/policy-packs/builtin/understanding-before-execution/markers.ts:139-154#"forged: false,"`, `src/policy-packs/builtin/understanding-before-execution/markers.ts:213-237#"forged: true,"`).
4. **The report stays mandatory.** Auto mode replaces the human approve step, not the Understanding Report.
5. **Pause is a different mechanism.** `harness pause` is an unsigned, all-hooks mute with its own operator-only enforcement (`docs/okf/pause-vs-gate-kill-switch.md`). Nothing here touches it.

### Out of scope

- Implementation (this is a concept ADR; slices are proposed below).
- Any change to `harness pause` / `harness resume`, including the pre-existing presence of `pause` on the read-only Bash allowlist (`src/runtime/read-only-bash.ts:530-532#"pause"`).
- The `solution-acceptance` verdict marker (unsigned today, tracked separately).
- The report-hash cross-check at gate time (task `fa423e9b`). It is named below only as the dependency that would make report binding enforceable at gate time.

## Options

### Option A: `approval.source` policy with a hook-written signed auto-marker

Add an operator opt-in to the pack config (strict schema, next to `approval_lifecycle`):

```yaml
policy_packs:
  - name: understanding-before-execution
    config:
      auto_approve:
        when: [bypassPermissions]   # allowlist of payload literals
        require_report: true        # v1: only `true` is accepted by the schema
```

The auto path runs ONLY on a call the gate was about to block: after the ordinary marker check has declined, and after every existing exemption branch (read-only Bash, recovery commit, escape `ask`) has declined too, immediately before the final block (decision-order table below). When that is the case and ALL of the following hold at PreToolUse time, the harness hook itself writes the signed marker with `approvedBy: auto-mode:<harness>:<mode>` (for example `auto-mode:claude-code:bypassPermissions`), writes the ledger fact `understanding-auto-approved:<sid>`, and then re-runs the same marker check, which finds the fresh marker and decides exactly as today:

1. `auto_approve` is present in the applied manifest and `when` is non-empty.
2. The payload carries `permission_mode` and its value is a member of `when` (string equality against the allowlist; absent, empty, or unlisted value means no auto-approval).
3. The NEWEST persisted Understanding Report for the session, and only that one (the `selectReportForSession` first strict match, `src/policy-packs/builtin/understanding-before-execution/persisted-reports.ts:238-246#"return { report: r, fallbackAdopted: false, staleRejected: [] };"`; the auto path never scans further down the list for some other `pending` report), has a `sessionId` that strictly equals the payload's `session_id` (no sessionId-null fallback), an `approvalStatus` that is exactly `pending` (any other status, `approved` and `expired` included, makes the session ineligible even when an older `pending` report is still on disk), and parses and passes the same content validation `harness approve understanding` applies (the canonical parser, then `validatePersistedReport`, `src/cli/approve/understanding.ts:828-840#"validatePersistedReport(parsed)"`; the second half's strength is mode-dependent, see cons below).
4. The marker is written through the identical `writeApprovalMarker` / HMAC path with `reportContentHash` computed the same way as the approve CLI does (`src/cli/approve/understanding.ts:959-968#"markerResult = { ok: true, filePath, approvedAt: approvedAtMarker };"`). The auto path writes the SESSION marker only: `writeTaskApprovalMarker` stays a human-only writer, because a task scope is an operator choice (`--task`, or the active-claim file the operator's approve run reads, `src/cli/approve/understanding.ts:985-994#"readActiveClaim(generatedDir)"`) and there is no operator on the auto path to make it. Task-boundary expiry still clears both marker kinds, so nothing is weakened by the narrower write.
5. **The auto path consumes the report.** In the same pass it rewrites the report it used to `approvalStatus: "approved"`, stamping `approvedAt` / `approvedBy` exactly as `harness approve understanding` does (`src/cli/approve/understanding.ts:571-595#"delete parsed["`). Consumption, plus the `pending`-only rule in condition 3, is what makes one report mintable at most once.
6. **Step 3 did not report a forged marker.** When `checkOperatorApprovalMarkers` rejected a forged or unsigned marker (`markerForged`, `src/cli/pack/hook-pre-tool-use.ts:723-725#"markerForged = markers.forged;"`; the forged returns in `src/policy-packs/builtin/understanding-before-execution/markers.ts:209#"forged: true,"`, `src/policy-packs/builtin/understanding-before-execution/markers.ts:237#"forged: true,"`), the auto path declines and does not write. Two reasons: a detected forgery is a stronger signal than the ambiguity invariant 3 already blocks on, so it must not be auto-approved past; and `writeApprovalMarker` would `atomicWriteFiles` the auto-marker onto the very path the forged body sits at (`approvalMarkerPathFor`, `src/policy-packs/builtin/understanding-before-execution/markers.ts:53-61#"return filePath;"`, `src/policy-packs/builtin/understanding-before-execution/markers.ts:145#"approvalMarkerPathFor(generatedDir, sessionId);"`), overwriting the forged artifact and erasing the `forged/unsigned marker rejected` diagnostic that the compensating-control story depends on reaching the operator. Declining leaves the forged file and its diagnostic intact, and the call falls through to the final block.

#### Why the report must be consumed

Without condition 5 the auto path would re-mint a marker from the same still-`pending` report on every gated call, and `approval_lifecycle` would stop meaning anything, because neither of its boundary shapes touches a `pending` report:

- `max_age`: `checkApprovalMarker` only returns `expired: true`. It deletes no marker file and rewrites no report (`src/policy-packs/builtin/understanding-before-execution/markers.ts:246-258#"expired: true,"`).
- Task boundary: `applyPostToolUseExpiry` deletes the session and task markers and calls `expirePersistedReport`, which returns early for any report whose status is not already `approved` (`src/policy-packs/builtin/understanding-before-execution/post-tool-use-boundary.ts:203-245#"persistedReportExpired: reportExpiry.ok,"`; `src/policy-packs/builtin/understanding-before-execution/persisted-reports.ts:409-428#"already has approvalStatus="`).

An unconsumed auto path would therefore mint the next marker on the very next tool call, with two concrete failures: a task-completion boundary would clear a marker that reappears immediately, which is a bypass rather than a boundary; and `markerExpired` would never be observable, so the recovery-commit exemption that keys off it (`src/cli/pack/hook-pre-tool-use.ts:815-829#"hard-gated regardless."`) could never fire under auto mode. With consumption both behave as designed. After a task boundary the boundary's own `expirePersistedReport` call now has an `approved` report to act on and moves it to `expired`, provided no newer `pending` report has been written for the session in the meantime (the case two paragraphs down); after a `max_age` overrun the report stays `approved` and the marker stays expired. In both cases the same report cannot mint again, a fresh report is required, and the recovery-commit exemption still sees a true `markerExpired`.

`approval_lifecycle` (`expire_on_tool_match`, `expire_on_bash_match`, `max_age`) then applies to the auto-marker through the same mechanism it uses on a human one, but not with the same effect, and the difference matters enough to state plainly. Mechanically it is identical: an ordinary signed marker with a distinguishable `approvedBy`, and, because the report behind it was consumed, an expiry or a task boundary really does end THIS approval instead of being re-minted away on the next call. What differs is what re-arming costs. A human marker's expiry needs a human act to re-arm, `harness approve understanding` run from an ungated shell; an auto-marker's expiry needs only a fresh `pending` report, which the agent produces unilaterally. So under `auto_approve` the lifecycle bounds the reach of ONE report and reintroduces no human touchpoint. Operators should read `max_age` here as "how much work a single Understanding Report may cover", not as "how often a human is asked again".

One consequence follows directly from how a report is selected, and it is recorded here so that it is a chosen behaviour rather than one discovered in production. Report lookup takes the NEWEST report for the session: `listPersistedReports` sorts newest-first (`src/policy-packs/builtin/understanding-before-execution/persisted-reports.ts:152#"reports.sort((a, b) => b.createdAtMs - a.createdAtMs);"`) and `selectReportForSession` returns the first strict match (`src/policy-packs/builtin/understanding-before-execution/persisted-reports.ts:238-246#"return { report: r, fallbackAdopted: false, staleRejected: [] };"`). `expirePersistedReport` acts on that same newest report (`src/policy-packs/builtin/understanding-before-execution/persisted-reports.ts:418#"findLatestReportForSession"`) and returns early unless its status is already `approved` (`src/policy-packs/builtin/understanding-before-execution/persisted-reports.ts:425-428#"already has approvalStatus="`). So as soon as a second `pending` report exists for the session (a later Stop capture, or a slice 3 transcript re-scan), it shadows the consumed one: a task boundary's expiry call finds the newer `pending` report and no-ops, and the next gated call re-arms the auto path from it. That is intended. Single-use binds a REPORT, not a session, and a fresh report is exactly what re-arming is meant to cost under auto mode. Slice 1 asserts the re-arm as a control so that a later change cannot silently turn it into something else.

| 10. final block | the block and its reason string (`src/cli/pack/hook-pre-tool-use.ts:1248#"harness pack hook: BLOCK"`) | unchanged; it is what a failed auto path falls through to |

Placing the auto path at step 9 rather than beside the marker check is deliberate, and it is the ordering the slice 1 acceptance criteria and controls encode. At step 9 the call in hand is one the gate was about to block, so the first read-only `ls` or `git status` of a session, a recovery `git commit`, and a bare `harness approve understanding` mint no marker, write no ledger fact and consume no report. Three consequences follow that an earlier position would have given away: the single report is spent on the first call that actually needed an approval rather than on whatever read-only call happened to come first; `max_age` starts counting from that call, so the approval window covers gated work instead of being eaten by reconnaissance; and the escape `ask` keeps the behaviour measured for it under `-p` (a denial, hardening item 7) instead of being overtaken by an auto-approval on the same call.

- Pros: gate code path unchanged (still marker-only); signed and report-hash-bound artifact; expiry and forensics keep their mechanism, because the auto path consumes the report it used and so cannot re-mint around a boundary from the same report (what re-arming costs afterwards is a fresh report, not a human, see the lifecycle paragraphs above); audit can tell auto from human approvals; opt-in is operator-owned and diff-visible.
- Cons: the hook gains a write path into `.approvals/`, which today only the approve CLI has, and with it a signing oracle (see residues); the report precondition is agent-authored content (acceptable because it is a precondition, not the authority, but it means "auto-approval" is "operator policy applied by a trusted process to an agent report"); that precondition is also weaker than it reads, because `validatePersistedReport` returns `ok` immediately unless the report's `mode` is `grill_me` (`src/cli/approve/understanding.ts:514-516#"return { ok: true, mode };"`), so under `fast_confirm` or a missing/unknown mode any structurally parseable report satisfies it; the opt-in lives in a file the agent can edit after its own approval, as does the settings file that can select the mode (see residues).
- Risk: medium. Contained by the allowlist, the strict session binding, the shared signing path, the marker check running first, the single-use report, and the fail-closed rule on every missing input.

### Option B: A plus post-hoc human review

Everything in A, plus: auto approvals are listed as "unreviewed" by `harness doctor` and by the session-start preflight, and the operator can `confirm` or `flag` each one (a small verb writing a ledger fact `understanding-auto-approval-reviewed:<sid>:<verdict>`).

- Pros: restores a human touchpoint without blocking the run; produces a reviewed/unreviewed metric that tells the operator whether auto mode is being used as intended.
- Cons: two new verbs and a listing state to maintain; the review happens after the fact, so it changes nothing about what the run already did.
- Risk: low on top of A. The confirm/flag verbs must be ledger-only (audit), never a second approval source.

### Option C: auto mode = block-until-report, without a marker

In an allowlisted mode the hook allows once a structurally valid pending report exists for the session, writing no marker.

- Pros: smallest code change; no hook-side write path.
- Cons: the decision rests on an unsigned, agent-written file, exactly the shape task 7402301d removed; no `reportContentHash` binding; audit cannot distinguish an auto-approved session from one where a report merely exists; `approval_lifecycle` boundaries (which clear markers) and the recovery-commit exemption (which keys off a marker's `expired` state, `src/cli/pack/hook-pre-tool-use.ts:815-829#"hard-gated regardless."`) have nothing to act on; it reintroduces a second approval authority beside the marker and therefore breaks invariant 1.
- Risk: high. Rejected.

### Option D: operator pre-approval via CLI without report binding

`harness approve understanding --task a b c` (batch markers, `docs/policy-packs/understanding-before-execution.md:680-682#"writes one task-scoped marker per id in a single operator action"`), or a fixed `--session-id` that a launcher reuses so one approval covers every run (`docs/policy-packs/understanding-before-execution.md:564#"pins a fixed session id and approves once"`), or a hypothetical duration-scoped variant (`harness approve understanding --for 2h --any-session`).

- Pros: exists today (first two shapes); no new trust surface.
- Cons: the approval is not bound to the child's own report, so the "report stays mandatory" invariant is satisfied only nominally (the operator's report covers the batch, the child writes none that matters); a duration- or any-session-scoped variant is a marker without a report and without a session, weaker than A on every axis; a `-p` child with a fresh session id gets nothing unless the launcher pins the id, which is the "scripted runs reuse a session id" property the pack docs already flag as something to make deliberate.
- Risk: low as a status quo, but it does not solve the stated problem. Rejected as the answer; the batch and pinned-id shapes stay available as they are.

### Recommended decision (proposed)

Option A as the core. From B, only the visibility half in slice 1: the doctor listing of auto approvals and the metric "auto approvals in the last N sessions". B's `confirm` / `flag` verbs are a named follow-up, not part of slice 1. C and D are rejected for the reasons above.

Rationale in one line each:

1. A is the only option where the gate's decision input stays exactly one signed marker.
2. The trusted signal (T1 payload field) plus an operator opt-in is the minimal pair that is not controllable for the running session before approval, and that needs no human mid-run. Neither half is a boundary AFTER approval: the mode can be selected by `permissions.defaultMode` in a settings file the post-approval agent can write, and so can the opt-in (threat model (c)).
3. The report precondition keeps the "report stays mandatory" invariant real rather than nominal, and consuming the report keeps it real on the second call too.
4. How much of the report's CONTENT that precondition enforces is pack-mode dependent, and the operator has to choose accordingly: `validatePersistedReport` returns `ok` at once unless the report's `mode` is `grill_me` (`src/cli/approve/understanding.ts:514-516#"return { ok: true, mode };"`). Recommendation: pair `auto_approve` with `grill_me`, or with a mode whose validation the operator has actually read; paired with `fast_confirm`, or with a report carrying no mode field, key two degrades to "a parseable report file exists for this session".
5. `approvedBy` as the carrier of the source keeps the signing scheme and the no-migration precedent intact (see "Audit and doctor").

## Threat model

Inputs to the auto decision and who controls each one at the moment the hook runs:

| Input | Written by | Agent influence before its own approval | Agent influence after its own approval |
|---|---|---|---|
| `permission_mode` in the payload | Claude Code process, from a launch flag or from `permissions.defaultMode` in a settings file | none: the flag belongs to whoever launched the process, and the settings file needs Edit / Write / Bash, all gated | none for the running session; for every LATER session in the repo, full, by writing `permissions.defaultMode` into `.claude/settings.json` or `.claude/settings.local.json` (see (c)); full for children it spawns (they are separate sessions) |
| `session_id` in the payload, `$CLAUDE_CODE_SESSION_ID` in the hook env | Claude Code process | none | none for the running session; full for processes it spawns |
| `auto_approve` opt-in in `harness.yaml` | operator | none (Edit / Write / Bash gated) | full (post-approval write class; drift visible via `harness diff --since-apply`) |
| Persisted report | the agent's own Stop hook, or the PreToolUse transcript scan (slice 3), or the launcher in the fallback channel | full over content, except in the fallback channel where the parent fixes it; none over the binding of its OWN session id, which it does not choose; full for any session id it chooses for a child it spawns, since the strict-session check compares the report's `sessionId` field to the payload and never asks who wrote the report; none over reuse, since it is single-use once consumed | same |
| Signing key | `harness init` / `harness approve` (operator side) | readable via `Read`, not writable | readable; writable only through the uncovered-write residue |
| Session transcript | Claude Code process | readable, not writable through gated tools | readable; writable through Bash (a forged transcript entry is the same class as a forged report: it only supplies key two, never key one) |

The design holds because key one (mode or delegation) is never in the agent's hands for its own session, and key two (the report) is a precondition that grants nothing on its own. This is a within-session property, not a cross-session one: after its own approval the agent can arrange for later sessions to start with key one already true (see (c)).

### (a) What an agent in auto mode cannot trigger

- It cannot change the running session's `permission_mode` through any channel it has. Under `-p` the mode is set at launch, by a CLI flag or by `permissions.defaultMode` in a settings file, and a headless run has no in-run selector; in an interactive session the mode is operator-controlled and can be switched mid-session by the operator, not by the model (asking Claude in chat to change the mode does not work). Either way the payload is composed by the Claude Code process and piped into the hook (`docs/okf/understanding-gate-auto-mode-signals.md`, section "Measured: `permission_mode` in the hook payload, by event x mode", plus the interactive entries under "Unverified / not measured"; `dogfood/ug-auto-mode-signals/README.md`, results sections (a) and (b); Claude Code docs, "Choose a permission mode", sections "Which mode a session starts in" and "Switch permission modes").
- It cannot make the hook see a different payload for its own session. The hook reads stdin from Claude Code, not from the model.
- Before approval it cannot run `harness pack hook pre-tool-use` with a fabricated stdin: that is a Bash call, Bash is gated, and `pack` is not on `HARNESS_READ_ONLY_SUBS` (`src/runtime/read-only-bash.ts:530-532#"pause"`), so the call is blocked by the very gate it would be trying to satisfy. After approval that same call is the signing oracle named in (c).
- It cannot enable the opt-in, or plant a `permissions.defaultMode`, for the running session before approval: editing `harness.yaml` or `.claude/settings*.json` needs Edit / Write / Bash, all gated. Both files become writable after approval (see (c)).
- Without a persisted, session-bound, structurally valid report no marker is written. A report for another session is never adopted (strict match only, no tolerant fallback on the auto path).
- Under `-p`, the hook's `ask` escape resolves to a denial in every permission mode, so a headless agent cannot self-approve via the escape path (`docs/okf/understanding-gate-auto-mode-signals.md`, section "Measured: hook `permissionDecision: \"ask\"` resolution under `-p`"; `dogfood/ug-auto-mode-signals/README.md`, results section (f)).

### (b) Additional hardening to specify

1. **Session consistency**: the auto-marker is written only when `payload.session_id` equals the hook process's `$CLAUDE_CODE_SESSION_ID`. This is a consistency check, not a boundary (a post-approval agent controls both for processes it spawns), but it forces a cross-session forgery to fake two inputs at once and makes it forensically distinct.
2. **`when` is an allowlist of payload literals.** Membership is exact string equality. Unknown value, empty string, or absent field means no auto-approval. No wildcards, no "anything but default".
3. **`require_report: false` is rejected by the schema in v1.** The key exists so the contract is explicit in the manifest, and so a future relaxation is a visible schema change rather than a silent default.
4. **Identical signing path.** The auto-marker goes through `writeApprovalMarker` / `signMarker`. No second marker format, no second key.
5. **Fail closed on key problems.** The auto path must never create the signing key (key creation stays an operator-side act of `harness init` / `harness approve`). Key missing, unreadable, or marker unwritable means no marker and the normal block. This does NOT fall out of hardening item 4 on its own, and the two would conflict if left implicit: `writeApprovalMarker` calls `signMarker` (`src/policy-packs/builtin/understanding-before-execution/markers.ts:53-61#"return filePath;"`), which reaches `getOrCreateSigningKey`, and that function treats a missing key file as a case to REPAIR rather than to refuse, generating a fresh key on ENOENT and writing it (`src/runtime/approval-signing.ts:177-210#"mode: 0o600, flag:"`). Calling the shared write path on a machine with no key would therefore mint a key and a marker in one step, which is the operator-side act this item forbids. So the auto path needs an explicit key-exists precheck in front of the call, or a non-creating sign variant that takes an existing key handle and fails when there is none; slice 1 acceptance criterion 2 carries that precondition. (The pre-existing marker check reaches the same function at `src/runtime/approval-signing.ts:386#"getOrCreateSigningKey(generatedDir)"`, but only when a marker FILE exists to verify; the auto path's write would reach it unconditionally, which is the difference.) This adds no allow path to the hook's fail-open contract.
6. **Hook infrastructure errors keep the existing posture.** Malformed stdin, manifest load failure, and undeclared pack still resolve exactly as today (`src/cli/pack/hook-pre-tool-use.ts:17-22#"(Phase 4 #6) surfaces the runtime audit trail when configured."`). The auto path is reached only after those checks, after the existing marker check has declined, and after every existing exemption branch has declined as well (decision-order table, step 9); it adds a marker write and then defers to that same marker check for the verdict. It never short-circuits to allow, and it never runs on a call the gate was already going to open: read-only Bash, the recovery commit and the escape `ask` all sit above it and return first.
7. **The escape path under auto modes: measured under `-p`, one interactive case left.** A bare `harness approve understanding` from the agent's Bash tool is deferred to the interactive prompt via `permissionDecision: "ask"` (`src/cli/pack/hook-pre-tool-use.ts:842-848#"ASK: operator-approval command, deferring to the interactive permission prompt"`). Under `-p` a hook `ask` resolves to a denial in every mode, `bypassPermissions` and `--dangerously-skip-permissions` included: the command does not run, no PostToolUse fires, and the run's result JSON lists the call under `permission_denials` (`docs/okf/understanding-gate-auto-mode-signals.md`, section "Measured: hook `permissionDecision: \"ask\"` resolution under `-p`"; `dogfood/ug-auto-mode-signals/README.md`, results section (f); script `dogfood/ug-auto-mode-signals/ask-probe.sh`; fixtures `payloads/ask-probe-<mode>.PreToolUse.json` and `payloads/ask-probe-<mode>.result.json`). So a headless agent cannot self-approve through the escape path. The remaining gap is the interactive (non-`-p`) session under `bypassPermissions`, where a prompt-less mode might resolve `ask` differently; slice 1 measures that one case. If it resolves to allow there, the escape path must return `deny` whenever `permission_mode` is present and is a non-prompting mode. That is a shipping precondition for the interactive case only. The ordering above protects this: because the escape branch sits ahead of the auto path (decision-order table, step 8), an escape call keeps whatever the prompt resolves it to and is never turned into an auto-approval by the same hook invocation. The operator's own `harness approve understanding` from their terminal never passes through the hook and is unaffected.

### (c) Residues, named honestly

- **Self-spawned children.** After its own approval the agent can run `claude -p --permission-mode bypassPermissions ...` from Bash. Each child has a fresh session id, and the child's own report is the only remaining precondition; that is not friction, because the parent can choose the child's session id (`--session-id`) and write a structurally valid `pending` report carrying that id into the reports directory before spawning, and the child's first gated call then satisfies every slice 1 condition (opt-in, `when` match, strict-session `pending` report, and the session-consistency check, which Claude Code is expected to satisfy for the child because it exports `CLAUDE_CODE_SESSION_ID` into the child's environment; that agreement was captured only for a `-p` run whose session id Claude Code generated, not for a `--session-id`-pinned or interactive launch, see the evidence doc's "Unverified / not measured" list). Under slice 1 alone a post-approval agent can therefore mint auto-approved child sessions at will, with no delegation, no key read and no settings plant, and none of the compensating controls surface it: the settings drift lines cover settings files only, `--since-apply` covers `harness.yaml` and locked target paths only, and the auto-approval listing cannot tell an agent-launched child from an operator-launched one. This is not an authority escalation over the post-approval write class, which can already forge markers with the readable key, but it is the cheapest cross-session path, and it is named so that operator decision 4 is taken with it in view: requiring a delegation for EVERY auto-approved child (slice 3) is the control that binds a child to an approved parent, and shipping slice 1 without slice 3 accepts this residue explicitly. The agent gains nothing for its own session.
- **Opt-in is agent-editable after approval.** `harness.yaml` is an ordinary file; post-approval the agent has full write access (the existing "post-approval full write" class). `harness diff --since-apply` and `harness doctor` make a drift visible. Mitigation to consider: read `auto_approve` from the applied snapshot in `harness.generated/.last-apply` (which carries a manifest snapshot, `src/cli/diff/since-apply.ts:4-6#"per-file index."`) instead of the live manifest. Its limit: `.last-apply` lives under `harness.generated/`, which the same post-approval write class reaches, so it moves the target rather than closing the class. Named as an operator decision below.
- **The permission mode itself is settings-derived, and settings files are agent-editable after approval.** Claude Code takes a new session's mode from `--permission-mode` / `--dangerously-skip-permissions` first, and otherwise from `permissions.defaultMode` in a settings file (`.claude/settings.json`, `.claude/settings.local.json`, `~/.claude/settings.json`); `bypassPermissions` is one of the values a settings file can set, and setting it there also puts that mode into the interactive cycle (Claude Code docs, "Choose a permission mode", sections "Which mode a session starts in" and "Switch permission modes"). The project-scoped ones are in exactly the same post-approval write class as `harness.yaml`, and `harness apply` already targets one of them (`src/cli/apply/next-steps.ts:147-150#"settings.local.json --merge"`). So a post-approval agent can plant `permissions.defaultMode: "bypassPermissions"` beside the `auto_approve` opt-in, and every later session started in that repo begins with the trusted signal already true. Classified honestly: it is NOT an escalation over what that write class already allows, since the same access could simply remove the pack's hooks from `settings.json` and turn the gate off outright, and it buys the writing session nothing (that session is already approved). What it does collapse is the "two owners" reading of the design, that key one belongs to the operator and key two to the agent: across sessions, one write class owns both. The payload cannot separate the two, because it carries the mode and not its provenance: a flag-set `bypassPermissions` and a settings-set one are the same string, and harness has no `defaultMode` awareness anywhere in the codebase to compare against. Compensating control: doctor and a `harness diff --since-apply`-style drift check report a `permissions.defaultMode` that was not present at apply time, so the plant is visible rather than silent (slice 1 negative control and doctor check below). Whether a settings-derived mode is accepted as a valid signal at all is operator decision 7, which also carries the one ENFORCING lever available here, an administrator-owned managed setting that removes the mode outright.
- **The same settings write also reaches the hook roster, which supplies key two.** `permissions.defaultMode` is not the only shape of this plant and the ADR would be understating it by naming only that one. A settings file also carries the hook configuration, so the same post-approval write class can ADD a `UserPromptSubmit` or `SessionStart` hook entry whose command writes a `pending` Understanding Report bound to each new session's id. That supplies key two for every later session in the repo without any reasoning happening in that session, in the same way the `defaultMode` plant supplies key one. Combined, the two plants pre-satisfy both keys for every later session started there, and the auto path then mints a marker on a session that produced no understanding at all. This is the same access class as before, not an escalation over it (that access can also simply delete the pack's hooks and switch the gate off), but it is what the "two owners" reading loses across sessions, and it is the reason the drift surface has to cover more than one key. What the EXISTING drift surface actually covers, checked rather than assumed: `harness apply --target <path>` records the file it wrote as a lock entry of kind `target` carrying a sha256 of the whole file (`src/cli/apply/apply.ts:1100-1114#"crypto.createHash("`; `src/io/harness-lock.ts:48-57#"sha256: string;"`), and `harness diff --since-apply` re-hashes that path and reports `modified` on any difference (`src/cli/diff/since-apply.ts:135-152#"currentSha,"`). So a plant into the applied target file is detected as a change, but the surface names no key: it cannot tell an added hook entry from an added `permissions.defaultMode` from an ordinary edit by the operator. And it covers every path `--target` has written across applies and still finds on disk (`src/cli/apply/apply.ts:1118-1140#"return [...entries, ...carried];"` carries prior `target` entries forward and re-hashes each); a settings file that was never an apply target carries no lock entry at all and is invisible to it. The doctor line proposed under "Audit and doctor" is therefore widened rather than left at `defaultMode`: doctor parses every settings file in the precedence chain it can reach and reports both a `permissions.defaultMode` and any hook entry absent at apply time, comparing the live hook roster against the applied one. It remains a warning, not an enforcement.
- **Slice 1 turns the PreToolUse hook into a marker-signing oracle.** Once the hook itself can mint markers, any process that can invoke `harness pack hook pre-tool-use` with a stdin payload of its choosing and a `CLAUDE_CODE_SESSION_ID` of its choosing obtains a validly signed marker for that session id without ever reading the signing key. That changes a written invariant: `src/runtime/approval-signing.ts:32-45#"a bare unsigned-JSON write no longer is)."` states the residual as a CONJUNCTION, read the key with `Read` AND write into `.approvals/` through a primitive the `Edit|Write|Bash` matcher does not enumerate. With the oracle it becomes a disjunction: read the key, or make the hook sign for you. Scope, honestly: pre-approval the oracle is unreachable (invoking it is a Bash call, and `pack` is not on `HARNESS_READ_ONLY_SUBS`, `src/runtime/read-only-bash.ts:530-532#"pause"`); post-approval the agent can already forge markers by the key-read route, so this is not an escalation of what is reachable. It is an unnamed change to a documented invariant, and it makes the post-approval route cheaper and less forensically visible (no key read to notice). The oracle caller still has to satisfy every condition in Option A, including the opt-in, the `when` match, a strict-session `pending` report, and the `session_id` / `$CLAUDE_CODE_SESSION_ID` agreement check. Slice 1 must update the honest trust model in `approval-signing.ts` in the same PR so the invariant on disk matches the code (slice 1 acceptance criterion below).
- **Key read plus uncovered write.** Unchanged from `src/runtime/approval-signing.ts:20-45#"a bare unsigned-JSON write no longer is)."`: an actor that can read the key with `Read` and write into `.approvals/` through a primitive the blocker does not enumerate can forge any marker, auto or human.
- **Hook-command hijack via shell startup files.** Pre-existing all-hooks residue (the hook is `harness ...` resolved through the shell); not specific to this ADR.
- **`pause` on the read-only allowlist** (`src/runtime/read-only-bash.ts:532#"pause"`). Pre-existing; out of scope, noted so nobody reads its absence here as a claim that it is closed.
- **Parent-linkage fidelity in slice 3.** A post-approval agent can point `harness delegate` at any approved session id it can read from `.approvals/`. The delegation verb must require a valid signed marker for the recorded parent, which makes the linkage a derivative of a real approval, but a wrong-but-approved parent remains an audit-fidelity gap, not an authority gap.

### (d) Human-only, explicitly NOT relaxed by auto mode

| Surface | Why it stays human-only |
|---|---|
| `operator_only` policies (`deny-kill-switch-bypass`, `deny-session-env-strip`, `deny-pause-sentinel-forgery`) | Unconditional denies that consult no evidence (`src/schema/policies.ts:184-220#"it, since there is no undocumented evidence source to flag."`); there is nothing for auto mode to satisfy. |
| Risk-gate `require_approval` in prod contexts (`harness approve risk`) | Different gate, different marker, different blast radius; not touched. |
| Deletion-arm | Same. |
| Branch-protection override marker (`harness approve branch-protection`) | Shares the signing primitive but is a separate operator decision about editing a protected branch. |
| Solution-acceptance verdict marker | Written by a trusted process (grounding-mcp), not by an operator; unsigned today; out of scope. |
| Pause sentinel | Operator-only kill switch (`docs/okf/pause-vs-gate-kill-switch.md`). |
| Orchestrator-workflow review invariant | The reviewer subagent stays mandatory for every change. Auto mode changes who approves the Understanding Report, not whether the change is reviewed. |

## `claude -p` child processes

### Two candidate models

| Model | Mechanism | What it gives | What it lacks |
|---|---|---|---|
| Auto mode by construction | Parent spawns `claude -p --permission-mode bypassPermissions`; the child's payload carries `bypassPermissions`; slice 1 applies as-is. | Trusted mode signal, no new verb. | No parent linkage (audit cannot tell an operator-launched child from an agent-launched one); no report exists before the child's first tool call, so slice 1 alone blocks every `-p` child. |
| Parent-issued delegation | At spawn time the parent runs `harness delegate --child-session <uuid> [--cwd <path>] [--task <id>] --ttl <duration>`, which writes a signed delegation marker bound to the parent session id, the child session id (chosen via `--session-id`), cwd and/or task id, and an expiry. The child's hook finds it. | Parent linkage, TTL, cwd/task binding, works even if the mode field were absent. | On its own it is a pre-approval without the child's report, i.e. Option D in a new coat. |

### Decision: two-key design

The delegation is a **pre-authorization**, not an approval. It supplies the trusted signal and the parent linkage; the child's auto-marker is written only after the child's own report exists. Both keys are required:

1. Key one, the trusted signal: `permission_mode` in `when`, or a valid, unexpired, cwd/task-matching delegation marker for this child session id (the delegation counts as the trusted signal because it is a signed artifact written by a `harness` process on behalf of an already-approved parent, and it is bound to the child's session id so it cannot be reused).
2. Key two, the child's own report: persisted, bound to the child's session id, structurally valid.

Only when both hold does the hook write the child's auto-marker, with `approvedBy: auto-mode:<harness>:<mode>` and the parent linkage appended (see "Audit and doctor").

### Delegation marker shape

The delegation carries more bindings than an approval marker does, and this ADR rules out adding signed fields (a change to `canonicalPayload` is a `SIGNING_ALG` bump, see "Audit and doctor"). The signing primitive signs exactly the tuple `(markerId, approvedAt, approvedBy, reportContentHash)` (`src/runtime/approval-signing.ts:276-286#"JSON.stringify({ markerId, approvedAt, approvedBy, reportContentHash });"`), and the reader on the other side keeps only `approvedAt`, `approvedBy`, `reportContentHash` (`src/policy-packs/builtin/understanding-before-execution/markers.ts:240-244#"const marker: ApprovalMarker = { approvedAt, approvedBy, reportContentHash };"`): there is no `expiresAt` field for `checkApprovalMarker` to enforce. So every binding has to travel inside that tuple:

| Field | Delegation value | Why |
|---|---|---|
| `markerId` (signed, not stored in the file body) | `delegation-<child-sid>` | Binds the artifact to one child session the same way `task-<id>` binds a task marker (`src/policy-packs/builtin/understanding-before-execution/task-markers.ts:78-86#"mode: 0o600"`): a validly signed delegation cannot be copied onto another child id, or onto a session marker's id, and still verify. |
| file path | `harness.generated/.delegations/<child-sid>` | A separate directory, NOT `.approvals/`. Delegations are pre-authorizations, not approvals; keeping them out of `.approvals/` keeps the marker scans and the doctor `approvedBy`-prefix listing free of artifacts that never opened a gate. |
| `approvedAt` (signed) | the timestamp the delegation was ISSUED, in the same ISO form an approval marker uses | Not optional and not decorative: `verifyMarkerSignature` rejects a payload whose `approvedAt` is missing or empty before it computes any HMAC (`src/runtime/approval-signing.ts:365-366#"return { ok: false, reason:"`), and `canonicalPayload` signs it as part of the tuple (`src/runtime/approval-signing.ts:276-286#"JSON.stringify({ markerId, approvedAt, approvedBy, reportContentHash });"`), so the delegation must carry it or it cannot verify at all. It is NOT the expiry carrier: it records issue time only, and the delegation's lifetime lives in the `expires` segment of `approvedBy` below, because the marker reader keeps no `expiresAt` field (`src/policy-packs/builtin/understanding-before-execution/markers.ts:240-244#"const marker: ApprovalMarker = { approvedAt, approvedBy, reportContentHash };"`) and the dedicated verifier is what enforces it. |
| `approvedBy` (signed) | `delegated:<parent-sid>;cwd=<sha256 of the child's expected cwd>;task=<task id, or a literal dash when none>;expires=<iso timestamp>`, plus `;report=<sha256 of the launcher-supplied report file's path>` in the fallback shape | The one free-text field inside the signed tuple. Packing parent, cwd, task and expiry here makes all four tamper-evident with no schema change. The cwd is hashed rather than written literally so the file does not carry a machine path. The `report=` segment exists because `reportContentHash` binds the fallback report file's CONTENT and nothing else: without a path binding the child's hook would accept any readable file whose bytes hash to the recorded value, including a copy the child placed at a location of its own choosing, so the parent's choice of WHERE would not be part of what was signed. The path is hashed for the same reason the cwd is. |
| `reportContentHash` (signed) | `null` in the base shape; the sha256 of the launcher-supplied report file's CONTENT in the fallback shape ("Report capture under `-p`"), paired with the `report=` path segment above | A delegation normally binds no report, because the child's report does not exist yet, and `null` is already the accepted value for a marker with nothing to bind (`src/runtime/approval-signing.ts:313-314#"?? null;"`). The one case where it does have something to bind is the fallback channel, where the parent writes the report at spawn time; then the same field carries its hash and the child's hook can check the file against it. The two uses of this field in this ADR cover DIFFERENT artifacts and the difference has to be read off the artifact kind, not off the field name: on an approval marker (human or auto) it is the sha256 of the PERSISTED report under the reports directory that the approval was granted against; on a delegation it is the sha256 of the launcher-supplied report FILE the parent wrote at spawn time, which is not a persisted report yet and need not ever become one byte-for-byte. Tooling that reads `reportContentHash` must therefore branch on `.approvals/` versus `.delegations/`, or on the markerId prefix, before deciding what the hash refers to. |

A delegation is therefore NOT consumable by `checkApprovalMarker`. Slice 3 adds a dedicated verifier that (1) verifies the signature against markerId `delegation-<child-sid>`, (2) parses the `approvedBy` segments, (3) refuses on a missing or unparseable segment, (4) refuses when `expires` is in the past, (5) refuses when `cwd` does not hash-match the payload's `cwd` or when `task` does not match the child's task, (6) refuses a delegation that binds neither a cwd nor a task, and (7) in the fallback shape, refuses when the launcher-supplied report file's path does not hash-match the `report=` segment or when its content does not hash-match `reportContentHash`, so both WHERE the parent put the report and WHAT it contains are part of what was signed. Every refusal is a block with a distinct diagnostic, never a fall-through to allow.

### Report capture under `-p`

Under `-p` the Stop hook fires once, at the end of the run, and its `last_assistant_message` carries only the final text, not a report emitted mid-turn; the Stop capture therefore cannot supply key two in time.

The session transcript is the other candidate channel, and it lags. A report the agent emits before its first tool call is NOT in the transcript JSONL at the instant PreToolUse fires; it appears shortly afterwards. The sample, the timings, and the note on a first, confounded version of that probe live in `docs/okf/understanding-gate-auto-mode-signals.md`, section "Transcript visibility of a mid-turn report" (`dogfood/ug-auto-mode-signals/README.md`, results section (e); scripts `transcript-probe.sh` and `transcript-probe.py`). No numbers are restated here. Consequences:

- **The transcript channel stays viable only with an explicit lag strategy, and which strategy is now measured rather than assumed.** A hook that scans once, at the instant it fires, finds nothing on the first gated call. What a lone block-and-retry does about that has since been measured (`docs/okf/understanding-gate-auto-mode-signals.md`, section "Measured: block-and-retry under `-p`"; `dogfood/ug-auto-mode-signals/README.md`, results section (g); script `dogfood/ug-auto-mode-signals/retry-probe.sh`). Two findings, and they point in opposite directions. The instruction channel works: the child reads the deny reason, writes or re-writes its report, and retries the command, in every run. But the retry only gets through when the report had already been flushed to the transcript before the first attempt; when the report is written in the same turn as the retry, the second scan hits the same lag and denies again, and whether the child then tries a third time varied between two independent samples of the same script (in one sample most runs stopped after the single retry the deny text asked for, in the other every run retried again unprompted and got through). So block-and-retry is a working instruction channel and NOT a sufficient capture strategy on its own: a single retry is reliable in neither direction. Slice 3 therefore ships the bounded poll as the default and block-and-retry as the behaviour past the bound, not as an alternative to it.
- **The scan is role-aware and session-scoped.** Only `assistant` entries of the transcript the payload names (`transcript_path` / session id) count, and only for this session; a report the agent quoted back in a user message, or one sitting in another session's transcript, is not a hit. The hook, not the agent, chooses which transcript to read. Sidechain (subagent) assistant entries are not eligible; only main-line assistant entries of the session count (see "TTL, cwd, and subagents").
- **Default: the bounded poll.** The hook scans, and while the report is absent it re-scans until an operator-tunable bound elapses (`report_scan.max_wait`, added to the `auto_approve` block by slice 3, conservative default, hard ceiling in the schema so a hook can never hang a session). The timeout is fail-closed: bound elapsed and still no report means block. This is the default precisely because it is the shape that covers the measured failure case, a report written in the same turn as the call that needs it: the hook waits for the flush itself instead of handing the wait back to an agent that has already done what it was asked.
- **Past the bound: block with an instruction that asks for repeated retries.** When the poll times out the hook blocks with the standard instruction, and that instruction asks the child to emit or re-emit its report and to retry the call again if it is denied again, in as many words. A text asking for a single retry was measured, across two samples, to produce sometimes a single retry and then a stop and sometimes a further unprompted retry that succeeded, so asking once leaves the outcome to run-to-run variation; asking for repeated retries is what the combined sample argues for. The case this covers is the measured success case, a child whose report was already flushed and whose retry then got through. It costs blocked tool calls rather than a hung hook, and it is what happens AFTER the bound, not a shape slice 3 may pick instead of the poll.
- **In both the poll and the block past it, absence means block, never allow.** There is no branch in which a missing report opens the gate; that is invariant 3 applied to this channel.
- **Fallback channel if the lag is not bounded.** If slice 3's re-measurement shows the lag is not reliably bounded (other modes, interactive sessions, longer reports, other machines), the transcript is dropped as the capture channel and the launcher supplies the report instead: the parent writes the child's Understanding Report to a file at spawn time, and the delegation binds that file by hash in `reportContentHash`, a field the signing tuple already carries, with the file's PATH bound alongside it by the `report=` segment of `approvedBy` so the child cannot substitute a same-content copy of its own at a path of its choosing. The child's hook then reads content the parent, not the child, fixed. That is strictly stronger than the transcript scan; it is the fallback rather than the default only because it requires the launcher to hold the report, which the smoke-runner shape does not today.
- **The Stop flush race is moot for the gate decision**: the gate never waits on Stop, and the Stop capture stays the audit copy at run end.
- **The existing statements are refined, not overridden.** `src/cli/pack/approve-escape.ts:20-26#"for a human reading the prompt"` and the lockout runbook (step 4) both say that current Claude Code builds do not reliably persist mid-turn assistant text to the transcript. The measurement agrees with them at the moment that decides the gate: at the hook instant, the report is not there. What it adds is narrower, that in the runs measured the report does land shortly afterwards. Neither statement is to be rewritten on the strength of this ADR. If slice 3 confirms a bounded lag, the refinement (present shortly after, not at the instant) belongs in those two places at that point, citing the evidence doc.

### Missing report in the child

The UserPromptSubmit injector already runs under `-p` (the payload capture shows the event firing under `-p` with `permission_mode`; `docs/okf/understanding-gate-auto-mode-signals.md`, section "Measured: `permission_mode` in the hook payload, by event x mode"), so the child receives the report instruction. If it calls a gated tool before writing a report, the hook blocks with the standard instruction, the run ends with `permission_denials` in the result JSON, and the parent sees the failure. No marker, no auto-approval. The instruction channel behind that block is measured to work rather than merely hoped for: a `-p` child denied with the standard instruction does read the deny reason, does write a report, and does retry the command (`docs/okf/understanding-gate-auto-mode-signals.md`, section "Measured: block-and-retry under `-p`"; `dogfood/ug-auto-mode-signals/README.md`, results section (g)). What the instruction does not solve is the lag: the retry lands in the same turn as the freshly written report, the next scan is still too early, and whether the child tries again after that varies from run to run unless the deny text asks for repeated retries or the hook waits for the flush itself. That is why the bounded poll is the default rather than a refinement of block-and-retry. The poll waits at most `report_scan.max_wait` for a report whose transcript write is in flight and then blocks; it is a lag allowance, not a retry loop, and no branch of it turns an absent report into an allow.

### TTL, cwd, and subagents

- **TTL / expiry**: the expiry travels in the signed `approvedBy` string as the `expires` segment (see "Delegation marker shape"), because the marker reader keeps no `expiresAt` field (`src/policy-packs/builtin/understanding-before-execution/markers.ts:240-244#"const marker: ApprovalMarker = { approvedAt, approvedBy, reportContentHash };"`). The dedicated verifier enforces it, and the child's hook refuses an expired delegation exactly like an expired marker (block, distinct diagnostic). Recommended default: the pack's `approval_lifecycle.max_age` when set, else one hour; operator-overridable via `--ttl`.
- **Different cwd**: the `cwd` segment of the same signed string holds the sha256 of the child's expected cwd, and the `task` segment its task id; the child's hook hashes the payload's `cwd` and refuses on mismatch. A delegation that binds neither cwd nor task is rejected by the verb.
- **Subagents (Agent tool)** are assumed to share the orchestrator's session id and therefore to be covered by the orchestrator's existing marker, so that nothing here applies to them. Measured, not merely assumed: a subagent's own turns live in a SEPARATE agent transcript file (named by `SubagentStop`'s `agent_transcript_path`), never in the payload's own `transcript_path`, and every entry in the payload's own transcript that carries the field is `isSidechain: false`; the measured shape never puts a `true` entry there. For slice 3's transcript scan the rule follows that shape directly: the scan opens only the payload's own `transcript_path` (never a directory or multi-file scan that could reach the subagent's file), and only main-line assistant entries of that one file count. An `isSidechain: true` entry encountered there is still excluded, as defence in depth against a shape this measurement did not produce, not as the mechanism the separation actually relies on. See `docs/okf/understanding-gate-auto-mode-signals.md`, section "Measured: subagents (Agent tool) and the parent session id".
- **`harness delegate` from the agent's Bash tool** is gated like any other Bash call, so it is only reachable post-approval; the verb additionally requires a valid signed marker for the parent session it records. The harness smoke runner (an operator-run CLI that already chooses the child's session id, `src/cli/smoke/runner.ts:73-85#"...CLAUDE_FLAGS,"`) is the natural first consumer.

## Audit and doctor

- **`approvedBy` carries the source**: `auto-mode:<harness>:<mode>` for slice 1, with `;delegated:<parent-sid>` appended for slice 3. It is already part of the signed payload (`src/runtime/approval-signing.ts:276-286#"JSON.stringify({ markerId, approvedAt, approvedBy, reportContentHash });"`), so the source is tamper-evident with no new signed field. A new signed field would change `canonicalPayload`, which under the strict no-migration precedent (`src/runtime/approval-signing.ts:134-143#"gate) still holds."`) means a `SIGNING_ALG` bump and forced re-approval on every install; not worth it for a string that the existing field already carries. The delegation packs its own bindings into the same field ("Delegation marker shape"): one convention, two artifact kinds, no schema change for either.
- **Ledger fact** `understanding-auto-approved:<sid>` (plus `understanding-delegated:<child-sid>:<parent-sid>` for slice 3), distinct from `understanding-approved:<sid>`, following the `...:forced:<field>` suffix precedent. Audit only, like every other ledger row.
- **Doctor**: one summary line in the understanding-gate section (which already exists for the mode/env advisory, `src/cli/doctor/format.ts:106-107#"modeEnv.message"`) listing auto approvals found in `.approvals/` by `approvedBy` prefix, and the metric "auto approvals in the last N sessions" (N configurable, default 20). With B: an "unreviewed" count beside it. Delegations are counted separately, from `harness.generated/.delegations/`: because they never live in `.approvals/`, the prefix listing stays approvals-only and no marker scan ever meets an artifact that opened no gate.
- **Doctor, settings drift**: a second line reports a `permissions.defaultMode` in `.claude/settings.json` or `.claude/settings.local.json` that was not there at apply time, and a third reports hook entries in those files that were absent at apply time, comparing the live hook roster against the applied one. Both cover key plants that the existing `harness diff --since-apply` surface flags only as an unnamed whole-file change, and only for the single path `--target` last wrote (threat model (c)). This is the compensating control for the settings-derived-mode and settings-hook residues there. It is a warning, not an enforcement; the enforcing lever is the managed setting in operator decision 7.
- **`harness audit`** shows the ledger facts above, so an operator filtering the last 24 hours sees which sessions were auto-approved and under which mode.
- **Hook diagnostic**: the existing "approved via marker ... by <approvedBy>" detail (`src/policy-packs/builtin/understanding-before-execution/markers.ts:266#"signature verified"`) already prints the source; no change needed.

```json
  "reportContentHash": "<sha256 of the child's persisted report>",

```

Illustrative doctor lines (shape only; the section already exists for the mode/env advisory):

Every auto approval remains revocable the same way as a human one: delete the marker file, or let `approval_lifecycle` expire it.

## Slice plan

Three slices, hard cap. They are ordered, not independent: slice 1 is a prerequisite for both slice 2 and slice 3, which build on its config block, its auto path, and its marker conventions. What each slice does have is its own review boundary and its own payoff: each one is reviewable on its own, and each is useful the moment it ships, without waiting for the next.

Format rule for every mutation probe below: a probe names the mutant, the ONE test that must go red under it, and the fixture state that test needs in order to discriminate. A probe whose named test would stay green under its mutant is a defect of this document, not a nuance, and is the class that review rounds kept finding until this rule was written down.

### Slice 1: Claude Code `bypassPermissions`, opt-in, signed auto-marker, ledger fact, doctor metric, dogfood

- **Goal**: Option A for Claude Code, plus B's visibility half.
- **Acceptance criteria**
  1. Pack config accepts `auto_approve: { when: [...], require_report: true }`; `require_report: false`, unknown keys, and an empty `when` are schema errors surfaced by `harness validate`.
  2. With opt-in and a payload `permission_mode` in `when` and a strict-session, `pending`, structurally valid report, the hook writes a marker via `writeApprovalMarker` with `approvedBy: auto-mode:claude-code:<mode>` and `reportContentHash` set, writes `understanding-auto-approved:<sid>`, and the same PreToolUse call allows. Only the session marker is written; no task marker is created on the auto path. Precondition on that write: the auto path first checks that the signing key file exists and is usable, and blocks when it is not, BEFORE calling `writeApprovalMarker`. This is the mechanism that makes hardening item 5 true rather than a restatement of it, because the shared write path would otherwise create the key it is supposed to require (`src/policy-packs/builtin/understanding-before-execution/markers.ts:53-61#"return filePath;"`; `src/runtime/approval-signing.ts:177-210#"mode: 0o600, flag:"`). A non-creating sign variant that takes an existing key handle and fails when there is none satisfies this criterion equally; what is not acceptable is leaving the check to `getOrCreateSigningKey`.
  3. The auto path is reached only after `checkOperatorApprovalMarkers` has run and not matched, AND after the read-only Bash, recovery-commit and escape-`ask` branches have each declined, so it only ever acts on a call that would otherwise reach the final block (decision-order table, step 9). A call that any of those four branches allows or defers writes no auto-marker, writes no ledger fact, and consumes no report.
  4. The auto path consumes the report it used: the report is rewritten to `approvalStatus: "approved"` with `approvedAt` / `approvedBy` stamped, and only reports whose status is exactly `pending` are eligible in the first place.
  5. `checkApprovalMarker` verifies the auto-marker exactly like a human one (same signature, same `max_age`, same expiry hooks), and a `max_age` expiry of an auto-marker leaves `markerExpired` true, so the recovery-commit exemption behaves as it does after a human approval.
  6. The honest trust model in `src/runtime/approval-signing.ts:20-45#"a bare unsigned-JSON write no longer is)."` is updated in the same PR to name the hook as a second minting path, so the conjunction it states no longer reads as the only route to a validly signed marker (threat model (c), signing-oracle residue).
  7. Doctor prints the auto-approval line, the last-N metric, and both settings-drift warnings, the `permissions.defaultMode` one and the hook-roster one that reports hook entries absent at apply time (threat model (c)); `harness audit` shows the fact.
  8. Escape-path measurement, interactive case: dogfood records what a hook `ask` resolves to in an interactive (non-`-p`) `bypassPermissions` session. The `-p` case is already measured as a denial in every mode (`docs/okf/understanding-gate-auto-mode-signals.md`, section "Measured: hook `permissionDecision: \"ask\"` resolution under `-p`"; `dogfood/ug-auto-mode-signals/ask-probe.sh`). If the interactive case resolves to allow, the escape path returns `deny` for non-prompting modes before this slice merges.
  9. Dogfood includes an interactive `bypassPermissions` capture (the PreToolUse payload of a live interactive session), not only `-p`.
- **Negative controls** (each a test that must stay green)
  - Agent-set environment variable (any name, including `CLAUDE_CODE_ENTRYPOINT`, `AI_AGENT`, an invented `HARNESS_AUTO_MODE`) with no payload field: no marker, block.
  - Agent-written file (a hand-written "approved" report, a fake marker without signature, a fake `.last-apply`): no auto-marker, block with the existing forged/unsigned diagnostics.
  - **A forged marker plus a valid pending report and the opt-in does not launder the forgery.** A forged or unsigned marker at the session marker path, together with the opt-in, a `when`-listed `permission_mode` and a valid strict-session `pending` report on disk: no auto-marker, block with the `forged/unsigned marker rejected` diagnostic, and the forged file is still on disk afterwards (condition 6). Fixture state: the forged marker file, the opt-in, the mode, and the pending report all present at once.
  - No report: no marker, block.
  - Report for another session id (strict mismatch, including the sessionId-null shape): not adopted, block.
  - `permission_mode` absent, empty, `default`, `acceptEdits`, `plan`, or an unknown literal, with opt-in present: block.
  - Opt-in absent, or `when` does not contain the payload value: block.
  - Signing key absent: no key is created, no marker, block.
  - `payload.session_id` differs from `$CLAUDE_CODE_SESSION_ID`: no marker, block.
  - **After a task-boundary clear, the same report yields no second auto-marker.** Auto-approve, then fire a boundary tool so `applyPostToolUseExpiry` clears the marker and expires the (now `approved`) report, then make another gated call with the same report on disk: no new marker, block.
  - **After `max_age`, the same report yields no second auto-marker.** Auto-approve, advance the clock past `approval_lifecycle.max_age`, then make another gated call: the marker check reports expired, the auto path finds no `pending` report, no new marker, block (and `markerExpired` stays true, so the recovery-commit exemption still applies to a bare `git commit`).
  - Report already `approved` or already `expired` for this session and nothing else on disk: not eligible, no marker, block.
  - **A consumed newest report plus an older `pending` report for the same session yields no second auto-marker.** Eligibility is evaluated on the newest strict-session report only; an older `pending` report further down the list is never scanned for, so: block.
  - **A call the gate was already going to open mints nothing.** A read-only Bash call (`ls`, `git status`), a bare recovery `git commit` on an expired marker, and a bare `harness approve understanding` escape call, each made while a valid `pending` report and the opt-in are on disk: no auto-marker, no ledger fact, and the report is still `pending` afterwards, so the next gated write is the call that spends it. This is the control that fixes the auto path below the exemptions rather than above them.
  - **A successful auto-approval leaves no stale `.pending-approval` entry.** After the auto path mints, `harness.generated/.pending-approval` does not carry the auto-approved session id (cleared or never written), so an arg-less `harness approve understanding` from a shell without session env does not resolve to it.
  - **A second `pending` report re-arms the auto path, by design.** Auto-approve, fire a task boundary so the marker is cleared, write a second `pending` report for the same session, then make another gated call: a new auto-marker IS written from the second report. Asserting the intended behaviour keeps it a decision (see "Why the report must be consumed"): report lookup takes the newest report for the session and `expirePersistedReport` no-ops on a newer `pending` one (`src/policy-packs/builtin/understanding-before-execution/persisted-reports.ts:152#"reports.sort((a, b) => b.createdAtMs - a.createdAtMs);"`, `src/policy-packs/builtin/understanding-before-execution/persisted-reports.ts:238-246#"return { report: r, fallbackAdopted: false, staleRejected: [] };"`, `src/policy-packs/builtin/understanding-before-execution/persisted-reports.ts:418#"findLatestReportForSession"`, `src/policy-packs/builtin/understanding-before-execution/persisted-reports.ts:425-428#"already has approvalStatus="`), so this is what the design does, and a change to it has to break this test first.
  - Agent-planted `permissions.defaultMode` in `.claude/settings.json` / `.claude/settings.local.json` that was absent at apply time: doctor and the `--since-apply`-style drift check report it (this control asserts the drift line, not a block; the mode itself is accepted as a signal per operator decision 7).
  - Agent-planted hook entry (`UserPromptSubmit` / `SessionStart`) in `.claude/settings.json` / `.claude/settings.local.json` that was absent at apply time: doctor's hook-roster line reports it. Same shape as the control above, aimed at the key-two plant named in threat model (c); it asserts the warning, not a block.

Fixture state: `permission_mode: default` (not in `when`), the opt-in present, AND a valid strict-session `pending` report on disk, so the only thing standing between the call and a marker is the allowlist check the mutant deletes.

### Slice 2: Codex and opencode signals

### Slice 3: `claude -p` delegation

- **Goal**: the two-key design for `-p` children: `harness delegate` verb, signed delegation marker in its own directory, a report-capture channel that survives the transcript lag, child auto-marker with parent linkage.
- **Acceptance criteria**
  1. `harness delegate --child-session <uuid> (--cwd <path> | --task <id>) [--ttl <duration>]` writes `harness.generated/.delegations/<child-sid>` through the shared signing path, signed under markerId `delegation-<child-sid>`, with parent session id, hashed cwd, task and expiry packed into `approvedBy` as specified in "Delegation marker shape", plus the `report=` path hash and a non-null `reportContentHash` when the launcher supplies the child's report file; it refuses when no valid signed marker exists for the parent session, and it refuses a delegation that binds neither cwd nor task. Delegations never land in `.approvals/`. The verb also writes the ledger fact `understanding-delegated:<child-sid>:<parent-sid>` (audit only), which the slice 3 mutation probe below asserts on.
  2. A dedicated verifier reads that file: signature against markerId `delegation-<child-sid>`, then the parsed `approvedBy` segments, then expiry, then cwd/task match, and in the fallback shape the launcher-supplied report file's path against the `report=` segment and its content against `reportContentHash`. A missing or unparseable segment is a block, not a default.
  3. The child's PreToolUse hook, on a valid delegation, obtains the child's Understanding Report through the lag strategy chosen in "Report capture under `-p`" (role-aware, session-scoped transcript scan with the bounded fail-closed poll as the default, and block-and-retry only as the behaviour past the bound, its deny text asking for repeated retries), persists it bound to the child session id as `pending`, and only then writes the child's auto-marker with `approvedBy` carrying `delegated:<parent-sid>`. The auto path's `pending`-only rule and report consumption from slice 1 apply here unchanged.
  4. Missing report in the child (including "not yet in the transcript when the bound elapsed"): block with the standard instruction; the run's result JSON shows `permission_denials`.
  5. The smoke runner issues a delegation for the session id it already chooses, as the first consumer (subject to operator decision 5).
  6. Re-measurement covers the RETRY BEHAVIOUR and the poll bound, not only the lag, since the lag alone is already measured and block-and-retry is already measured not to close it reliably (a single retry got through in some runs and not others). Recorded in the evidence doc: (i) transcript visibility at PreToolUse time, `-p` and interactive; (ii) the retry-attempt distribution under both deny texts (single-retry and repeated-retry), with enough runs to separate them, since the two existing samples of the single-retry text disagree on whether the child stops or tries again; (iii) the chosen `report_scan.max_wait` default, justified against the observed flush behaviour, with the deciding case being a report written in the same turn as the call that needs it; and (iv) an explicit verdict that the bound is long enough to cover that case and short enough not to be felt as a hang. If no bound satisfies both, this slice switches to the launcher-supplied report file bound by hash in the delegation's `reportContentHash` rather than shipping a scan that can race.
- **Negative controls**
  - No delegation and no `when`-listed mode: no auto-approval, block.
  - Expired delegation: block, distinct diagnostic.
  - Delegation for another cwd or task: block.
  - Forged or unsigned delegation file: block with the forged diagnostic.
  - Delegation for a parent with no valid marker: `harness delegate` refuses.
  - Delegation present but no child report: no marker, block.
  - Delegation present and the report has not landed in the transcript within the bound: no marker, block (the fail-closed timeout, not an allow).
  - Report present in the transcript only as user-role text (the prompt echoing it back), never as an assistant entry: not adopted.
  - Report present only in a sidechain (subagent) assistant entry synthetically placed in the payload's own transcript, never in a main-line assistant entry: not adopted (see "TTL, cwd, and subagents"). The measured shape never puts an `isSidechain: true` entry in the payload's own transcript on its own (a subagent's turns live in a separate file, `docs/okf/understanding-gate-auto-mode-signals.md`, section "Measured: subagents (Agent tool) and the parent session id"), so this control needs a synthetically placed entry in the fixture to exercise the filter at all; the shipped detectors do not yet filter sidechain, so implementing the filter is still work the slice must do, not one the probes already exercise.
  - Report in a transcript belonging to another session: not adopted.
  - A delegation file placed in `.approvals/` instead of `.delegations/`: not treated as an approval by the marker check (its markerId does not match the session marker's), and not found by the delegation verifier either.
- **Mutation probes**
  - Drop the `delegated:<parent-sid>` segment from the `approvedBy` string the verb signs (this is the field that actually carries the parent binding; there is no separate signed parent field): the DELEGATION HAPPY PATH must fail, on two assertions, the child auto-marker's `approvedBy` no longer carrying `delegated:<parent-sid>` and the audit assertion on the ledger fact `understanding-delegated:<child-sid>:<parent-sid>` no longer finding the parent id. Pointing this probe at a "delegation for another parent" control would be inert and is deliberately not done: the verifier checks the signature over markerId `delegation-<child-sid>` and then the parsed segments (acceptance criterion 2), and no branch of it compares the recorded parent against an expected one, so there is no such control for the mutation to break. If a parent-identity check AT VERIFY TIME is wanted (refuse a delegation whose `delegated:` segment names a parent with no valid signed marker on disk when the child's hook runs, not only when the verb issues it), it has to be added as its own acceptance criterion with its own negative control first, and this probe repointed at that control.
  - Remove the `expires` segment check in the verifier: "expired delegation blocks" must fail.
  - Accept sidechain assistant entries in the scan (drop the main-line filter): the "report present only in a sidechain assistant entry is not adopted" control must fail. Fixture state: the payload's own transcript file carrying a synthetically placed `isSidechain: true` assistant entry with the report and no main-line assistant report; the measured shape never produces such an entry there on its own, so without the synthetic placement the control is vacuously green regardless of the filter and the probe would be inert.
  - Adopt the transcript report without the session check: "report from another session is not adopted" must fail. Fixture state: the scan is implemented over the reports/transcript directory (not the single `transcript_path` the payload names), and a report carrying a foreign `sessionId` sits there; the session check is the field comparison, and removing it is what adopts the foreign report. If instead the scan only ever opens the payload's own `transcript_path` (the file-level reading at "Report capture under `-p`"), a foreign session's transcript is never opened and this probe is inert, so the discriminating fixture must be the directory-scan shape.
  - Accept user-role transcript entries in the scan: the user-role negative control must fail.
  - Write the child marker before the report check: "delegation without report yields no marker" must fail.
- **Dependencies**: slice 1; a decision whether the transcript scan lands in `@lannguyensi/understanding-gate` (which owns the parser) or in harness (which owns the hook); `fa423e9b` for gate-time hash enforcement.
- **Risk**: medium to high, and concentrated in the report channel. The transcript scan is known to race the hook, and block-and-retry on its own is now measured not to close that race reliably (it worked in some runs and not others across two samples), so the slice ships the fail-closed bounded poll as the default with block-and-retry only past the bound, and holds the launcher-supplied report file in reserve. The delegation verb adds an operator surface that must be documented next to `harness approve`.

## Operator decisions requested

1. **Slice 1 scope: A, or A plus B's visibility half?** Recommendation: A plus visibility (doctor listing and last-N metric); `confirm` / `flag` verbs as a named follow-up.
2. **Default `when` list.** Recommendation: `[bypassPermissions]` only. `auto` and `dontAsk` are documented values that were not observed in a payload; they need a captured fixture before they may appear in an allowlist. There is a stronger reason than the missing fixture: per the Claude Code docs `auto` is the built-in starting mode on several plans, so listing it would make auto-approval the default for ordinary interactive sessions rather than an opt-in headless lane; a captured fixture is necessary but not sufficient for listing it.
3. **Where the opt-in is read from.** `harness.yaml` only, or `harness.yaml` plus a check against the applied snapshot in `.last-apply`? 4. **Is slice 3's delegation required for harness-spawned children even when they run in bypass mode?** Recommendation: yes, and once slice 3 ships, for EVERY auto-approved child, not only harness-owned launchers, because a delegation is the only control that binds a child to an approved parent (threat model (c), self-spawned children: under slice 1 alone a post-approval agent can pre-write a child's report for a session id it chose). Until slice 3 ships, a child launched in bypass mode without a delegation gets slice 1 behaviour, and shipping slice 1 alone accepts that residue explicitly; the smoke runner and any harness-owned launcher should delegate from the day slice 3 exists.
5. **Smoke runner as the first delegation consumer?** Recommendation: yes; it already spawns with `--session-id` and `bypassPermissions`, so it is the cheapest end-to-end dogfood.

If the interactive case also denies, no decision is needed here.
7. **Is a settings-derived permission mode accepted as a valid signal?** A session's mode can be set by `permissions.defaultMode` in `.claude/settings.json` or `.claude/settings.local.json`, not only by a CLI flag, and those files are in the same post-approval agent-write class as the `auto_approve` opt-in (threat model (c)). Recommendation: accept it, because the payload cannot tell the two sources apart (it carries the mode, not its provenance), so "flag only" would be a rule harness cannot enforce and would only read as stronger than it is; take the doctor and `--since-apply` drift line on `permissions.defaultMode` as the compensating control instead. The alternative, if the operator wants a real separation, is to stop treating the mode as key one for repos where settings are agent-writable and require a slice 3 delegation there instead, which is decision 4 tightened to "always". There is also an ENFORCING lever outside harness that the operator should weigh before answering, because it changes the question rather than the answer: Claude Code lets an administrator block `bypassPermissions` outright by setting `permissions.disableBypassPermissionsMode` to `"disable"` in managed settings, and remove auto mode the same way with `permissions.disableAutoMode` (Claude Code docs, "Choose a permission mode", the `bypassPermissions` safety note and the section "Eliminate prompts with auto mode"). Managed settings sit at the top of the settings precedence chain, above the command line and above every project-scoped and user-scoped file (Claude Code docs, "Claude Code settings", settings precedence), which is exactly the layer the post-approval write class inside the repo does not reach. In a repo where the operator does not want the mode at all, that makes the settings-derived-mode plant impossible rather than merely visible, which no doctor line can. The cost is that it switches the slice 1 auto path off in that repo too: with the recommended `when: [bypassPermissions]` no payload there can ever carry a listed value, so a slice 3 delegation becomes the only remaining auto path. It is therefore an alternative to this design for repos that want bypass gone, not a hardening to combine with it, and the choice between the two is what decision 7 is really asking.

## Reopen criteria

Reconsider this decision if any of the following become true:

- Claude Code stops carrying `permission_mode` on PreToolUse, or changes its vocabulary, so that the T1 signal disappears or becomes ambiguous.
- A hook `ask` in an interactive `bypassPermissions` session turns out to resolve to allow and cannot be closed on the harness side (the `-p` case is measured as a denial); auto-approval would then add no security for interactive auto-mode sessions and the escape path itself would need redesign first.
- Task `fa423e9b` lands and makes gate-time report-hash enforcement available; the auto path should then adopt it rather than keep audit-only binding.
- The agent gains a way to mint a marker that needs neither the operator nor the key. Two shapes, and after slice 1 the second is the cheaper one: a filesystem-write primitive outside `Edit|Write|Bash` (a configured MCP with local writes) combined with a key read, which is the pre-existing residue; or an ungated route to invoke `harness pack hook pre-tool-use` with chosen stdin, which is the signing oracle slice 1 creates (threat model (c)). Either way the marker's operator-only property collapses for human and auto markers alike, and the whole approval design, not only this ADR, needs revisiting.
- Any change that makes the hook's marker write reachable pre-approval, for example `pack` appearing on the read-only Bash allowlist, or a `harness` subcommand that proxies hook invocation. That would move the oracle from post-approval to pre-approval and break invariant 2 outright.
- Codex measurement in slice 2 shows that `permission_mode` is derived from an agent-settable source; Codex then stays excluded from `when`.
- The slice 3 re-measurement shows the transcript lag is unbounded or version-dependent; `-p` support then moves to the launcher-supplied report file the delegation binds by hash, and the transcript scan is dropped rather than tuned.

## Consequences

- The gate's decision input stays exactly one signed marker; auto mode adds a second, distinguishable writer of that marker, not a second authority.
- A persisted report becomes single-use on the auto path. It is eligible only while `pending`, and the auto path consumes it, which is what keeps `approval_lifecycle` boundaries and the recovery-commit exemption meaningful under auto mode. What that does not do is restore a human touchpoint: re-arming after an expiry or a boundary costs a fresh `pending` report, which the agent writes itself, and a second `pending` report for the same session re-arms the auto path by design. Under `auto_approve` the lifecycle bounds how much work one report may cover, not how often a human is asked.
- `approvedBy` becomes a structured string by convention (`auto-mode:<harness>:<mode>[;delegated:<parent-sid>]` for markers, and the `delegated:...;cwd=...;task=...;expires=...[;report=...]` form for delegations) without a schema change; tooling that reads it must treat any other value as a human approval, and must read `reportContentHash` against the artifact kind, since it names the persisted report on an approval marker and the launcher-supplied file on a delegation.
- The pack config gains one strict nested block, `auto_approve`, following the `approval_lifecycle` pattern (`src/policy-packs/builtin/understanding-before-execution.ts:263-284#"max_age: z.string().min(1).optional(),"`).
- The auto path sits at the very end of the hook's decision order, below every existing exemption, so it acts only on calls that would otherwise be blocked; a read-only command, a recovery commit and an escape call mint nothing and spend no report.
- The hook gains a write into `.approvals/` guarded by the checks in "Threat model (b)"; its fail-open infrastructure contract is unchanged. The same write path is a signing oracle for anyone who can already invoke the hook, which is a post-approval-only reachability today and is named as a residue rather than argued away; the honest trust model in `approval-signing.ts` is updated in the same PR.
- Delegations get their own directory, `harness.generated/.delegations/`, so `.approvals/` keeps meaning "artifacts that opened a gate" for both the marker scans and the doctor listing.
- Operators running headless pipelines get a documented, auditable path instead of pinned session ids or batch pre-approval.
- The evidence for every number behind this document lives in `docs/okf/understanding-gate-auto-mode-signals.md` and `dogfood/ug-auto-mode-signals/`; this ADR is the rule-and-decision layer and must stay free of measurement data.
- This document is the canonical reference for the decision; the agent-tasks thread on f6be48cf is the longer-form discussion log.

## Amendment: Platform scope, `claude -p` delegation (2026-09-01, task `be9faf70`)

**Consuming a delegation (slice 3: `harness delegate`'s CHILD side, the `.delegations/` marker read, the adoption ledger, the PreToolUse key-one-by-delegation branch) stays Claude Code only.** It is not ported to Codex now, and it is not wontfix either: the boundary is named here, and correspondingly in the pack doc, `docs/CLI.md`, and the `delegate` verb's own `--help` text, because leaving the gap an OKF re-verification pass found (`docs/okf/codex-adapter-parity-gaps.md`, gap 14) undocumented would read as an oversight rather than a decision. Consuming and issuing are separate questions, and only consuming is restricted: see the cross-runtime issuing surface below, which this amendment records as an accepted consequence rather than closes.

Three premises this amendment started from do not hold as stated once checked against the current tree, and the correction is recorded rather than carried forward silently. First, Codex is not without an auto-mode surface: slice 2 (gap 13) already ships a shared `attemptAutoApproval` call on the Codex hook, gated behind `auto_approve.harnesses` naming `codex`, minting `approvedBy: auto-mode:codex:<mode>` (`src/cli/pack/hook-codex-pre-tool-use.ts:468-473#"harness: CODEX_HARNESS,"`). What Codex lacks is delegation specifically: `hook-codex-pre-tool-use.ts` imports neither the delegation-marker module nor the transcript-report-scan module and carries no branch analogous to the Claude hook's key-one-by-delegation step (`src/cli/pack/hook-pre-tool-use.ts:882#"Step 9's key-one-by-delegation branch"`). Second, Codex's block contract already IS a deny-with-reason: every refusal is a non-zero exit plus a stderr reason string, the same shape a delegation refusal would need. What Codex has never carried is Claude's structured JSON decision envelope or an `ask`-defer-to-an-interactive-prompt branch; the Codex hook's own header states plainly that the JSON-decision shape Claude Code reads "is not part of Codex's hook contract today" (`src/cli/pack/hook-codex-pre-tool-use.ts:13-16#"is not part of Codex's hook contract today)."`). That particular absence matters less for delegation than it would for the escape path, because a delegation targets a headless, non-interactive child by definition; there is nobody for an `ask` to prompt in that shape on either runtime. Third, and the correction this round of review forced: delegation is not symmetrically Claude-only. `issueDelegation`'s parent-session resolution runs the same chain `harness approve understanding` uses (flag > `$CLAUDE_CODE_SESSION_ID` > `$CLAUDE_SESSION_ID` > `$CODEX_SESSION_ID` > staged `.pending-approval`), and its 4th tier reads `$CODEX_SESSION_ID` directly (`src/cli/delegate/index.ts:276#"const resolvedParent = resolveApprovalSessionId({"`, chain defined at `src/runtime/session-id.ts:264-268#"CODEX_SESSION_ID, sessionSource:"`). The parent-marker check that follows verifies signature, JSON structure and expiry only; its options accept `maxAgeMs` and `now`, nothing that names a harness or filters on `approvedBy` (`src/cli/delegate/index.ts:305#"const parentCheck = checkApprovalMarker(generatedDir, parentSessionId, {"`, checked function at `src/policy-packs/builtin/understanding-before-execution/markers.ts:100-138#"): MarkerCheck {"`). Markers are cross-runtime shared by design (gap 2), so a Codex session holding a valid signed marker, including one auto-minted by the Codex hook under `auto_approve.harnesses`, can issue a delegation for a Claude `-p` child TODAY, with no code change.

For a Codex session to ever be the delegated CHILD, both keys of the ADR's two-key design are still missing, not one. Key one is a verified `harness.generated/.delegations/<child-sid>` marker: without a `codex-pre-tool-use` branch that reads and verifies it, a Codex child has no pre-authorization signal to check at all, so the call falls through to whatever `attemptAutoApproval`'s own single-session check already resolves; nothing opens for lack of key one, the child simply cannot be delegated to, which is a fail-closed absence rather than a fail-open gap. Key two is the child's own Understanding Report, which for a delegated child must be captured through a channel that survives that child's own execution model's report-visibility lag; without a MEASURED capture channel for Codex, the honest choices are fail closed (no consumer at all, which is what ships today) or fail open on an unmeasured assumption (reusing Claude's bounded transcript poll against a differently-shaped Codex transcript/session model), and this amendment is what refuses the second option. The cross-runtime issuing surface above also inherits Codex's own weaker session-consistency evidence: gap 13's `attemptAutoApproval` call on the Codex hook authenticates a marker via the transcript file's own name and existence, not an environment variable, because Codex exports no session-id variable to hook processes (`src/cli/pack/hook-codex-pre-tool-use.ts:479#"sessionConsistency: { kind:"`). `checkApprovalMarker` does not distinguish how a marker was minted, so a marker minted through that weaker check is, today, a fully sufficient key one for `issueDelegation`.

The reason a port is a whole second auto-mode surface rather than a parity patch is therefore not "Codex has nothing to mint into" (it does, since slice 2). It is that delegation is a materially different mechanism from slice 2's single-session, `permission_mode`-gated approval: it binds a signed pre-authorization to a PARENT session, and the child side of it depends on a report-capture channel that survives that child's own execution model's report-visibility lag. The bounded transcript poll slice 3 ships (see "Report capture under `-p`" above) is calibrated to a lag measured only for Claude `-p`; Codex's own transcript/session shape has never been probed for an equivalent lag, and nothing here assumes the number, or even the existence of a bounded lag, transfers. Porting delegation to Codex would mean designing and measuring a Codex-specific child-report capture channel from a cold start, writing a Codex-specific delegation verifier, and re-deriving the fail-closed guarantees for that Codex-specific consumer from a cold start, not adapting the three pieces slice 3 already wrote for Claude. That is the shape of a second slice 3, not a follow-up patch, which is why this amendment records a documented consumption-side boundary rather than opening a port task.

**Decision on the cross-runtime issuing surface.** The Codex-parent, Claude-child issuing path named above is an accepted, understood consequence of gap 2's shared marker contract, not a defect: any marker that authenticates a parent session at all, on either runtime, already opens that runtime's own gate, so a Codex marker authorizing a Claude delegation extends an existing shared-trust boundary rather than opening a new one. No parent-runtime refusal (rejecting `$CODEX_SESSION_ID`-resolved parents in `issueDelegation`) is added under this task; the verb's behaviour is unchanged. Closing it, if a future decision wants to, is a separate task, since it would change `issueDelegation`'s refusal surface rather than only its documentation.

**Reopen criterion.** Revisit this scope decision when the Codex adapter gains BOTH of the following, not either alone: (1) a delegation-marker consumer, a `codex-pre-tool-use` branch that reads `harness.generated/.delegations/<child-sid>` and verifies it the way the Claude hook's delegation check does today, and (2) a measured report-capture channel for Codex's own child/session model backing that consumer, since the existing bounded poll's calibration is Claude-`-p`-specific and does not transfer on its own. Codex's pre-existing deny-with-reason exit contract and its pre-existing signed-marker consumption (shared with Claude since gap 2) are NOT the missing signal: both already exist today, so naming either as the reopen trigger would read as already satisfied and reopen this decision on the spot, which is not the intent.

`harness.generated/.permission-mode-observations/<sessionId>`) stays
unsigned. `harness doctor`'s `bypassPermissions`-without-`auto_approve`
finding (`checkBypassWithoutAutoApprove`) keeps reading it as advisory
evidence only, exactly as shipped; signing it the way the approval
marker is signed was considered and rejected.

**Reasoning.** The write point is the hook process itself: it takes
`session_id` and `permission_mode` verbatim off the PreToolUse payload
on stdin and persists them without any further attestation
(`src/cli/pack/hook-pre-tool-use.ts:1198#"event.permission_mode, stderr);"`).
Any actor able to invoke the hook binary with a stdin payload of its own
choosing, an already-approved session included, therefore obtains a
hook-written observation carrying whatever `session_id` /
`permission_mode` it supplies; nothing on the write path distinguishes a
genuine PreToolUse invocation from a crafted one. Signing that record
with the marker-signing key would not close that gap: an HMAC over
attacker-chosen input still only certifies that the hook signed the
record, not that the named session actually ran under the claimed
permission mode, which is the property the doctor finding needs. It
would also open a second, unconditional signing surface for the
marker-signing key (not a path to mint an approval marker, which stays
namespaced by markerId), the exact widening the threat model above
already names as a residue under "Slice 1 turns the PreToolUse hook
into a marker-signing oracle": today the hook mints an approval marker
only when the auto-approve preconditions hold, and a signed observation
write would give the same reachable caller a second signing surface
gated on nothing, for no gain against the stdin-forgery threat just
described.
The finding this record feeds also stays advisory only: it can never
gate a tool call or mint an approval
(`src/cli/doctor/index.ts:1127#"if (report.ugBypassWithoutAutoApprove) warningCount++;"`),
so the operator remains the one who decides what the evidence means,
and a signature on the record would not change that division of
authority either. Marker signing does close a narrow class on its own
side of the boundary, a write primitive without a matching key read
(`src/runtime/approval-signing.ts:32-45#"distinguishable event; a bare unsigned-JSON write no longer is)."`);
leaving that class open for this record is accepted here because the
observation is advisory only, never a gate input, and the finding's own
message already tells the operator to confirm it against their own
launch settings before acting on it.

**Reopen criterion.** Reconsider this decision if the observation ever
moves from advisory doctor output into anything that gates a decision,
for example an allow/deny input or an auto-approval precondition. At
that point the record needs an evidence source the invoking process
cannot author on its own stdin, not a signature over the same
self-report: signing an already-forgeable input does not supply the
missing property. The candidate to evaluate first is transcript-side
corroboration: the `transcript_path` consistency check the Codex
auto-approve path already uses (see the "Understanding gate" paragraph
in `docs/okf/evidence-ledger-trust-boundary.md`) and the transcript's
own permission-mode line the repo already parses in
`src/cli/session-export/transcript.ts`; honestly, that raises the cost
of forging the record rather than removing its forgeability.

## Amendment: the launcher-report channel is consumed by the child hook (2026-09-01, agent-tasks `49d1ee41`)

Slice 3 shipped `harness delegate --report` minting a fully signed, verifiable fallback-shape delegation, but the child's PreToolUse hook refused every report-bound delegation unconditionally: it never offered `verifyDelegation` a `launcherReportPath`, because the delegation stored only a hash of the operator's own `--report` argument, a path the hook has no channel to learn. This amendment closes that gap with a CONVENTIONAL path both sides derive from nothing but the child session id, which `harness delegate` already takes as a required argument at delegation time (never learned only when the child starts): `harness.generated/.delegation-reports/<child-sid>.md`. `harness delegate --report <path>` copies the operator's file there, mode 0600, refusing (a distinct refusal reason, never a silent overwrite) when a DIFFERENT file is already staged at that location for the same child session; an identical restage is a no-op. The `report=` segment of the signed `approvedBy` string then binds the sha256 of that CONVENTIONAL file's realpath, through the same `hashDelegationCwd` the cwd binding already uses, and `reportContentHash` binds its bytes, exactly as "Delegation marker shape" specifies; only WHERE the parent staged the copy changed, not what is signed or how.

The child's PreToolUse hook now offers this conventional path to `verifyDelegation` unconditionally, on every delegation it checks: doing so only affects the outcome for a delegation that actually binds a `report=` segment, since the verifier consults `launcherReportPath` solely when one is present, so an unbound or cwd/task-only delegation is unaffected. A guard that predates this amendment sits ABOVE the whole report-bound/transcript-scan split: it checks for an existing PENDING persisted report for the child session before either channel is consulted, so a child that was already denied once and already has a pending report captured mints from THAT report and never reads the launcher-supplied file, report-bound delegation or not; `verifyDelegation` still runs and still authorizes the call, but the report capture step it feeds is skipped entirely. On a report-bound delegation whose verification succeeds, the file's markdown is persisted through the same `persistStdinReport` path the transcript-scan channel already uses, bound to the child session id as `pending`; the once-per-session adoption ledger (`.delegation-adoptions/<child-sid>`, the same sibling directory the transcript scan's entry ids already share) records the report's CONTENT hash, namespaced `report:` so it can never collide with the scan's `uuid:`/`digest:` ids, and a content hash already present in that ledger is refused rather than re-adopted: without this, the SAME launcher report would re-mint a fresh auto-marker every time the marker's own (short) TTL aged out while the delegation itself (long TTL) stayed valid, silently turning the delegation's lifetime into the report's own re-mint budget. A missing, moved, or content-modified file at the conventional path is refused through the verifier's existing distinct reasons (`report_path_mismatch` / `report_content_mismatch`); no new refusal reason is added on the read side. The transcript scan never runs for a report-bound delegation: the two report channels are mutually exclusive per delegation, decided by whether `verifyDelegation` returns a `reportPathHash`, so this closes the interactive-session gap the evidence doc named ("Chosen `report_scan.max_wait` default", "Verdict (iv), interactive") without touching the `-p` transcript-scan channel at all.

Two residues remain, both named rather than silently accepted: the conventional per-child report file is never swept by `harness gc`'s existing delegation category (folded into that sweep's own follow-up, task `3ece079d`); and, as before this amendment, a post-approval agent can still point `harness delegate --report` at any file it can write, which is the same parent-linkage-fidelity residue "Decision: two-key design" already names for the delegation verb generally, not a new one this channel introduces. The measurement behind the design choices here (which report-fallback checks are exercised by mutation, the before/after doctor and citation state) is recorded in `CHANGELOG.md`'s `[Unreleased]` entry for task `49d1ee41`; this amendment states the rule it motivated, not the measurement itself.
