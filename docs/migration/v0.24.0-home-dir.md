# v0.24.0 home-dir migration

Starting in v0.24.0, harness reads and writes its operator-state under
`~/.harness/` instead of `~/.claude/`. The change is transparent for
existing v0.23.x installs (the legacy path still works during the
v0.24.x line), but you should run `harness migrate-home --apply` once
to move your state into the new location.

## Why

Through v0.23.x harness was a Claude Code companion, so colocating its
state under `~/.claude/` felt natural. Phase 6 #6 added Codex as a
first-class runtime, and an `opencode` adapter is on the roadmap
([task `f34eb233`](https://github.com/LanNguyenSi/harness/issues)).
For a Codex-only operator (no Claude Code installed) the `.claude/`
naming was misleading at best and surface-area-breaking at worst:
`harness init` would create a Claude-named directory in a home that
otherwise had no Claude artefacts, and recovery hints pointed at
Claude-specific paths that did not apply.

v0.24.0 cuts the dependency. The state root is now `~/.harness/`,
named after the tool itself.

## What moved

```
~/.claude/harness.yaml          ->  ~/.harness/harness.yaml
~/.claude/harness.generated/    ->  ~/.harness/harness.generated/
~/.claude/.understanding-gate/  ->  ~/.harness/.understanding-gate/
~/.claude/harness.lock          ->  ~/.harness/harness.lock
~/.claude/machines/<discriminator>.harness.overrides.yaml
                                ->  ~/.harness/machines/<discriminator>.harness.overrides.yaml
~/.claude/projects/<name>/harness.overrides.yaml
                                ->  ~/.harness/projects/<name>/harness.overrides.yaml
```

The override layers move file by file, because the loader reads them from the
state root: a layer left under `~/.claude/` would stop applying after the
move. Only those exact files move. `~/.claude/projects/` is also Claude Code's
own session-transcript directory, so its other contents stay where they are;
a layer directory that is empty after the move is removed. A project directory
whose name the loader refuses (a path separator, `..`, a control character) is
not moved.

What did NOT move:

- `~/.claude/settings.json` is Claude Code's own runtime config. It
  stays where Claude Code expects it. `harness apply --target
  ~/.claude/settings.json --merge` continues to work unchanged.
- `~/.codex/config.toml` is Codex's own runtime config. Same logic.
- Any other operator-authored content under `~/.claude/` is left
  untouched by the migration.

Subdirectory names inside the new root are unchanged from the v0.23.x
layout, so if you have any scripts that read `harness.generated/` or
`.understanding-gate/reports/` from the harness state root, the only
parent that changed is the immediate root.

## How to migrate

```sh
# Plan the move (dry-run by default)
harness migrate-home

# If the plan looks right, perform it
harness migrate-home --apply

# Re-emit any embedded paths (e.g. UNDERSTANDING_GATE_REPORT_DIR in
# settings.json hook commands) so they point at the new reports dir
harness apply
```

`harness migrate-home --apply` is idempotent: re-running on
already-migrated state is a clean no-op. If the run encounters an
existing item at the new path (a top-level item or an override layer) it
refuses to overwrite, moves nothing, and asks you to resolve the conflict by
hand.

If you ran `harness migrate-home --apply` with an earlier build, it left
the override layers (`machines/*.harness.overrides.yaml` and
`projects/<name>/harness.overrides.yaml`) under `~/.claude/`, where they
no longer apply. Run `harness migrate-home --apply` again to move them.

Layers move file by file, so other files in `~/.claude/projects/` (Claude
Code's session transcripts) stay where they are.

Symlinked override layers are never moved. A layer file that is a symlink,
a `projects/<name>` directory that is a symlink, and `machines/` or
`projects/` being a symlink are reported as
`move by hand: <path> (symlink to <target>)` and left as they are; nothing
inside a link target is moved or removed. When the link points into an item
the run moved (`harness.yaml`, `harness.generated/`, another layer), the
line goes on with `; that target now lives at <new path>`, because the
legacy link no longer resolves to it. Recreate each one under `~/.harness/`
yourself (copy the file, or create a link that resolves to the same file;
a relative link target copied as it is resolves from the new place, not the
old one), then re-run `harness migrate-home --apply`. While such an item is
open, `--apply` exits non-zero; the dry run reports it and exits 0.

An item counts as done the way the loader reads a layer: every layer it
holds must resolve at its destination, following links, to a regular file.
A destination that exists but does not (a dangling link, a directory) keeps
the item open and gets its own line,
`<dst> exists but does not resolve to a file, so harness cannot read it as a layer; ...`.
Once every layer resolves, the line becomes
`already at <dst>; the legacy <path> can go once nothing under <state root> resolves through it`
and no longer makes the run fail. `<state root>` is `~/.harness`, or
`$HARNESS_HOME` when that variable is set (an empty value counts as unset),
because that is the root the loader reads layers from; `harness migrate-home`
warns on stderr when `$HARNESS_HOME` resolves to another directory, since it
always moves into `~/.harness/`. For a symlinked `machines/` the note reads
`keep the legacy <path> while anything under <state root> resolves through it` instead,
and for a symlinked `projects/` it reads `keep the legacy <path>: Claude Code
uses it for its session transcripts`: do not remove `~/.claude/projects`. A
destination that is itself a link to the legacy link, a layer under a
destination that links through it, or a layer of another item that links
through it (for example a `default` layer copied as a link to the legacy
`mini` layer) is read as well, so the item is done, but only while that
legacy link stays: removing the legacy link would leave that layer
dangling. The command does not check for that, so check every layer under
the state root before you remove a legacy link.

The four top-level items are not covered by this rule. One that is itself a
symlink (for example `harness.yaml` linked into a dotfiles checkout) is
moved as a link: the link moves to `~/.harness/`, its target stays where it
is, and a relative link target may then no longer resolve. Check such a link
after the move and recreate it with an absolute target if it dangles.

Layers move before `harness.yaml`. If a move fails before `harness.yaml` has
moved, the command moves back everything this run already moved and removes
the directories it created under `~/.harness/` (`~/.harness/` itself too, if
this run created it), then exits non-zero with the error and "nothing was
changed". If a move fails after `harness.yaml` has moved, the run is left
partial: it exits non-zero and prints which items are now under
`~/.harness/` and which are still under `~/.claude/`; fix the error and re-run
`harness migrate-home --apply` to finish. If moving something back fails, the
command says so on a `ROLLBACK FAILED` line per step and prints the same
what-is-where summary instead of "nothing was changed". harness reads
`~/.harness/` whenever it exists, so when the failed rollback leaves items
of this run there, or a `~/.harness/` this run created, without
`harness.yaml`, one more line says that harness now reads `~/.harness/` and
does not find the manifest still under `~/.claude/`, and how to recover:
move the items listed as now under `~/.harness/` back to `~/.claude/`, then
remove `~/.harness/` if this run created it (or only remove it, when nothing
is listed under it), and re-run `harness migrate-home --apply`.

The command drops a small breadcrumb at
`~/.claude/MOVED_TO_~_DOT_HARNESS.txt` so an operator who later runs a
command from muscle memory has a paper trail pointing at the new
location.

## Resolution precedence

`harness` resolves the state root in this order:

1. `--home <path>` (or `--state <path>`) on `harness uninstall`, the only verb with
   those flags. Other verbs take `--config <path>`, which moves the manifest and its
   `harness.generated/` but not the state root the override layers load from.
2. `$HARNESS_HOME` env var (pin without flag).
3. `~/.harness/` if it exists on disk.
4. `~/.claude/` if the legacy `harness.yaml` or `harness.generated/`
   exists there. Triggers a one-line deprecation warning to stderr
   at most once per process (so embedded or daemon callers do not
   spam the operator), naming `harness migrate-home` as the
   recommended next step.
5. `~/.harness/` as the create-on-first-use target.

A bare `~/.claude/` directory that contains only Claude Code's own
`settings.json` does NOT trigger the legacy fallback. Only the
presence of `harness.yaml` or `harness.generated/` counts as evidence
that harness state lives there.

## Deprecation horizon

The legacy fallback ships in v0.24.0 and continues to work for now.
It will be removed in a future release; the CHANGELOG entry for that
release will name the version. Run `harness migrate-home` to move off
the legacy root before then.

If you maintain CI that runs harness commands, expect the legacy-state
deprecation warning to appear in stderr until you run
`harness migrate-home --apply`. Filtering on the warning line is fine
short-term; the cleanest fix is the migration itself.

## Troubleshooting

### `target-conflict` outcome

`harness migrate-home --apply` refuses to overwrite. Decide which side
is authoritative, remove the other, and re-run.

### `move by hand` keeps failing the run

`--apply` exits non-zero while a symlinked layer has no counterpart under
`~/.harness/` that resolves to a regular file. Create the destination the
line names: copy the layer file there, or create a link at that path that
resolves to the same file (for a symlinked `projects/<name>` or
`machines/`, the destination is the directory under `~/.harness/`). A link
copied with its relative target as it is resolves from `~/.harness/` and
often dangles; if the line says `that target now lives at <new path>`, the
old target moved, so link to the new path. An
`<dst> exists but does not resolve to a file` line names a destination that
is in the way (a dangling link, a directory): replace it. The next
`harness migrate-home --apply` prints an `already at <dst>` note and exits 0.
Remove a legacy layer link only when nothing reads through it any more
(keep `~/.claude/projects` itself, Claude Code uses it): if any layer under
`~/.harness` links to it, directly or through another link, replace that
layer with a copy or a link to the real target first. The command never removes a legacy link for you.

### "nothing was changed" after a failed run

A move failed before `harness.yaml` moved, so the command undid the run.
Fix the error on the `failed to move` line (for example a permission problem
on a legacy directory, or a regular file where `~/.harness/` needs a
directory) and re-run `harness migrate-home --apply`.

### Operator-facing messages still mention `~/.claude/`

This release touches the prominent surfaces (`--config <path>` defaults,
init template comments, the no-session-id error in `harness approve
understanding`). A few internal references remain in comments or in
runtime-specific code that legitimately reads Claude Code's config
dir (e.g. `~/.claude/projects/<id>/<id>.jsonl` transcripts). Those are
expected. Open an issue if you find an operator-facing message that
still names `~/.claude/` after v0.24.0 ships.

### Existing CI / wrapper scripts that hardcoded `~/.claude/harness.yaml`

Either update them to `~/.harness/harness.yaml`, or pin via
`$HARNESS_HOME=~/.claude/`. The latter makes the deprecation warning
silent for one process invocation but is just papering over the
underlying drift; prefer the explicit migration.
