## The invariant

No evidence sink the gated agent can write, above all the evidence ledger reachable directly via `mcp__grounding-mcp__ledger_add`, is sufficient to open a builtin enforcement decision. Since 1.0.0 the invariant is trivially true in one direction: the only builtin gate that enforces against the agent is the `branch-protection` pack hook, it decides from what git reports about the checked-out branch and consults no ledger, marker or session state, and there is no other engine evaluating ledger tags at all. The policy engine that consumed `requires.ledger_tag` (and with it the `operator_only` unconditional-deny primitive and the `review:` / `dogfood:` tag gates shipped in the templates) was removed in 1.0.0; while it existed, its tag gates were process gates by design: whoever could write the ledger could open them, so they were never enforcement against the agent they gated. What the ledger still holds: the pre-1.0.0 `policy_decision` rows (they stay in old ledgers; harness reads no ledger rows any more, since the `harness audit` command was removed in task 0231f90f and `harness session-export` with the ledger client in task 82169840), and whatever grounding-mcp records from the operator's or agent's own sessions (the pause verbs that wrote `harness-paused:` / `harness-resumed:` facts were removed in 1.0.0, task 973163a4, and no harness verb writes rows any more).

## Where it's enforced

**Branch-protection asks git.** The hook (`src/cli/pack/hook-branch-protection.ts`) runs `git symbolic-ref -q HEAD` itself for each directory a write touches and refuses on a protected branch, on any answer it cannot get, and on any error; the pack keeps no ledger tag, no session state and no override marker (`docs/policy-packs/branch-protection.md:31-32#"state or override marker"`). The protected-list comparison is `isProtectedBranch` in `src/policy-packs/builtin/branch-protection-runtime.ts:72#"export function isProtectedBranch"`. Because nothing the agent can write reaches the decision, an earlier design in which a ledger tag or an approval marker could override the gate is gone, and there is no CLI verb that mints one.

**Nothing else reads the ledger at a gate.** The engine that used to evaluate `requires:` shapes against ledger entries is gone (removed in 1.0.0, with its `producers:` warnings, its `harness record` front-door verbs and the `review:` / `dogfood:` tag gates the templates shipped). A manifest that still declares `policies:` loads with a warning naming the removed key and the entry is stripped, so no hook command consumes a ledger tag on a 1.0.0 install. If a future gate is proposed that accepts a ledger tag (or any agent-writable state) as sufficient to unblock an enforcement decision, that re-opens the self-approval hole this doc was written about; the pre-1.0.0 design kept such gates explicitly in the "process gate, advisory against the agent" category.

**Shared bounded reader.** Every hook-path read of a file by path goes through `src/io/read-regular-file.ts`. `readRegularFileBytesBounded` opens the path once, read-only, with `O_NOFOLLOW | O_NONBLOCK | O_NOCTTY`, decides on `fstat` of the opened descriptor and reads through that same descriptor, never a separate stat of the path (`src/io/read-regular-file.ts:179#"export function readRegularFileBytesBounded("`). A file over `MAX_REGULAR_FILE_READ_BYTES` (1 MiB) is refused as `unreadable` before any byte is read, and the read stops one byte past the cap (`src/io/read-regular-file.ts:58#"export const MAX_REGULAR_FILE_READ_BYTES"`). The result is one of five kinds (`ok`, `missing`, `symlink`, `not-regular`, `unreadable`), so a FIFO swapped in after any earlier look is refused at once instead of blocking the hook past its budget, which the runtime treats as an allow, and a symlink at the final path component is refused unless the caller opts in. `O_NOFOLLOW` covers only the last component; on a platform without it (Windows) an `lstat` runs before the open. A caller with a legitimately larger input passes its own `maxBytes` and justifies it at the call site (`src/io/read-regular-file.ts:120#"export interface BoundedReadOptions"`): the Claude Code user registry gets 32 MiB (`src/io/claude-mcp.ts:631#"const MAX_REGISTRY_BYTES"`). A caller that reads a file the operator keeps behind a link (a dotfiles-managed manifest) passes `followSymlinks`; the type of the opened descriptor still refuses a link to a FIFO. `readTextFileBoundedOrThrow` is the same read thrown as a `BoundedReadError` (`ENOENT` for an absent path, `E_<KIND>` otherwise) for call sites that already wrap a by-path read in a try/catch (`src/io/read-regular-file.ts:270#"export function readTextFileBoundedOrThrow"`). The importers (the manifest loader and the Claude registry reader) are listed by `rg "read-regular-file" src`; no hook-path code reads the content of a git file by path, because branch-protection asks the `git` binary (its presence walk in `src/runtime/git-branch.ts` only stats paths).

**Write side of the same rule.** A by-path `fs.writeFileSync` opens the path blocking, so a FIFO with no reader at a hook-path file would hold the write until the hook ran out of its budget. `writeRegularFileNonBlocking` opens once with `O_WRONLY | O_NONBLOCK | O_NOCTTY` (a FIFO with no reader fails `ENXIO` at once) and checks the type on the opened descriptor before a byte is written or the file is truncated (`src/io/write-regular-file.ts:93#"export function writeRegularFileNonBlocking("`). Its one production caller creates the lock target exclusively, so whatever already sits at that path is left alone (`src/io/lock.ts:47#"writeRegularFileNonBlocking(lockPath"`). Writes through `atomicWriteFile` were already safe: their temp file is created `O_EXCL`.

## What breaks it

- A new gate that accepts a ledger tag as sufficient to unblock an *enforcement* decision: it re-opens the self-approval hole the ledger-tag model had by design, which is why no shipped gate does it since 1.0.0.
- Giving the agent a filesystem-write path into state a gate trusts, or un-gating Edit/Write/Bash so it can write that state.
- A hook-path read that bypasses `src/io/read-regular-file.ts`, for instance a bare `fs.readFileSync` or `statSync` on a path the agent can influence: it loses the symlink, FIFO and size defenses, and a FIFO planted there blocks the hook until its budget runs out. The shared file's own contract says future defensive fixes land there and nowhere else.
- A by-path write on a hook path that bypasses `writeRegularFileNonBlocking`, for the same FIFO reason.
- Re-introducing a `requires.ledger_tag`-style gate and treating it as enforcement: the pre-1.0.0 engine was advisory against the agent it gated, and removing it was the fix.
