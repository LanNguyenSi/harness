# Codex runtime adapter

The understanding-gate and solution-acceptance gaps this doc used to enumerate ended with the removal of those packs and their Codex hooks (see the removal entries under `[Unreleased]` in `CHANGELOG.md`); this doc describes only what the adapter does now. Its file name is kept so existing links hold.

## What the adapter is

`harness apply --runtime codex` selects the Codex adapter instead of the default `claude-code`, and records `runtime: codex` in `harness.generated/.last-apply`, so a later `harness apply` without `--runtime` (including `--install`) reuses codex and prints `runtime: codex (from last apply; pass --runtime to change)` instead of switching back to `claude-code`. A `.last-apply` from an older release without the field is read through its files map (`inferRuntimeFromFiles`): only `codex/config.toml` means codex; with both `settings.json` and `codex/config.toml`, the recorded pack `instructions.md` entries decide when every one names the same runtime in its `## Runtime` section (only the packs the record's own manifest snapshot lists count, when it has a readable one), and the output says the runtime was inferred. `--target` without `--runtime` implies `claude-code` (`selectRuntime`, `src/cli/apply/apply.ts`).

`harness smoke` applies the `claude-code` variant into its own `<output-dir>/harness.generated/` (the `generatedDir` apply option, `src/cli/smoke/index.ts`), so the operator's generated files and `.last-apply` (a recorded `codex` included) stay byte-identical and the next plain apply has nothing to restore. `harness pack remove --force` prunes only the pack's entries from `.last-apply` and keeps its other fields, the recorded runtime included (`pruneRecord`, `src/cli/pack/remove.ts`). `harness doctor` expands packs against the runtime a plain apply would select (`selectRuntime`: recorded, inferred or default), not always `claude-code`, and the report names it (`Pack expansion runtime:`, `formatPackExpansionRuntimeSection`, `src/cli/doctor/format.ts`).

A codex apply does NOT write `settings.json`; it emits `harness.generated/codex/config.toml` (`CODEX_CONFIG_BASENAME = "codex/config.toml"`, `src/cli/apply/apply.ts`) containing only harness-managed hook stanzas, one `[[hooks.<Event>]]` table per hook with `hooks = [{ type = "command", command = "...", timeout = N }]` (`emitHook`, `emitCommandHook`, `src/cli/apply/generate-codex-config.ts`). The hooks come from the manifest's `hooks`, from the policy packs' expansion for the `codex` runtime (branch-protection is the only builtin pack) and from the `memory.router` projection, a `UserPromptSubmit` hook shared with the Claude Code projection (`buildMemoryRouterHook`, `src/cli/apply/generate-settings.ts`). `MEMORY.md` ships runtime-agnostic and unchanged; pack `instructions.md` ships under every runtime, but its content differs per runtime (the builtin pack's `buildInstructions()` writes a `## Runtime` section), which is why an apply under another runtime rewrites it.

With `--install`, only the marked harness-managed block inside `~/.codex/config.toml` is replaced; operator model, auth and sandbox config is never owned by harness (the generator's header comment). The install finds one replacement range through `findManagedRange` and `scanOwnedContentEnd` (`src/cli/apply/install-codex-config.ts`); it does not trust an END marker to own every intervening table. Operator hook tables directly after that range are named and checked through `collectKeptHookTables` and `assertKeptHookTablesAreOperatorOwned`. The refusal checks and remaining ownership boundaries are described below.

`harness doctor --target codex` checks the `harness` binary on `$PATH`, the generated TOML's banner, and command resolvability per hook (`runCodexTargetChecks`, `src/cli/doctor/codex.ts`). A hook command that calls a removed harness verb warns instead of passing as a healthy subcommand, and a manifest hook's warning is counted once, by the manifest warnings (`checkHookCommands`).

## Installer ownership boundaries

The installer uses one locator, `findManagedRange`, and one marker rule, `createMarkerLineProbe`: a marker is a whole trimmed top-level line, equal to END or starting with BEGIN, the source prefix, generated header, or hook-comment prefix. Marker text in a value, trailing comment, inline table, multi-line array, or multi-line string does not establish ownership. Header-shaped array elements are checked through `createTopLevelProbe`; opaque multi-line string lines are skipped. A generated header opens a legacy block only when a canonical `[[hooks.` header follows it within the ownership scan's range. That lookup stops at the range end, so header text in a later string costs no prefix parse.

`assertNoOperatorLineBeforeHookTable` refuses a key or value line between the opening line and first canonical hook table on the BEGIN, source-prefix, and generated-header paths. Such a line belongs to the table open above the marker; deleting it could remove an operator hook field that the semantic comparison outside hook arrays would not detect. The refusal names the opening, content, and hook-header line numbers without printing any value, and asks the operator to move the content above the opening line. The config stays untouched. A key after the first harness hook header is still read as that hook table's field and consumed with it.

`assertNoOrphanHarnessHookTable` checks the whole document outside the replacement range, including after a foreign table on either legacy path, before a BEGIN block, and after END. A top-level `# harness hook:` comment in the blank/comment run immediately above a canonical or resolved respelled hook-event header refuses: installing would retain a stale hook beside the fresh block. Delete a stale table together with its comment; for an operator-owned table, reword the ownership comment. Marker/header text inside a value is preserved, and marked tables inside the replacement range are replaced together. A trailing ownership comment above the newly appended block does not turn that block into an orphan.

`assertNoLaterGeneratedHeaderBlock` refuses a later generated-header line directly above a canonical hook table outside the range being replaced, whether the first generated header is stale or opens a genuine block. With a stale first header, delete that unused header comment; with an owned first block, delete the unwanted later block and its opening line. Two contiguous generated blocks that the scan owns in one range are replaced together. All these refusals name line numbers and leave the config untouched.

The remaining shapes have explicit boundaries:

| Shape | Behaviour and reason |
| --- | --- |
| Canonical legacy generated block before a later BEGIN block, separated by a foreign table, END, or both | Kept, so its stale hook still runs alongside the fresh hooks. `findManagedRange` gives BEGIN priority over legacy generated headers and owns only that replacement range; `assertNoLaterGeneratedHeaderBlock` searches after its end, not before BEGIN. Without a `# harness hook:` ownership comment, the earlier table is preserved rather than selected as a second range. Remove an obsolete earlier block explicitly; reapplying alone leaves it unchanged. |
| Later generated header above an uncommented respelled hook table, such as `[[ hooks.Stop ]]` | Kept. The legacy-block detector requires the canonical `[[hooks.` prefix; broadening it also treats preserved empty-legacy header comments above a genuine operator hook as a second block and breaks idempotent installs. A `# harness hook:` ownership comment above the respelled table does refuse. |
| Uncommented hook table running a harness command on the append path | Kept. With no owned range or ownership comment, the command alone cannot distinguish a stale generated table from an intentional operator hook. The existing command check applies to the run of hook tables directly after a managed range, not every hook in the document. |
| Later generated header with a key/value line before its first hook table, or a later source-prefix-only block with uncommented tables | Not recognised as another block. The later-header check needs a comment run directly above the header and does not select a second ownership range. |
| Hook table whose root key uses an escape sequence, such as `[["ho\u006fks".Stop]]` | Kept as a foreign section. `resolvedKeyName` does not decode escaped keys, so such a header is neither resolved nor checked as a hook-event header by the orphan lookup. |
| Unmarked hook table after a non-hook foreign table or below END | Kept without the direct-run command check. The scan owns one range; the global orphan lookup detects ownership comments, not arbitrary unmarked commands. |
| Trailing comment run at EOF of a block without END that mentions a harness marker mid-line | Consumed with the range. This comment-run check still matches marker text as substrings. |

The split-block check also still matches its candidate marker text as substrings, so a value containing marker text in its checked zone can refuse. A changed config that the TOML parser cannot read refuses before writing. The no-END refusal offers moving a foreign table below the last harness table only when a harness-commented table follows; otherwise it offers adding END before the foreign table. END never hides a remaining marked orphan: that table must then be deleted or its ownership comment reworded. These controls and boundary examples are in `tests/cli/apply/apply-codex-install-boundaries.test.ts` and `tests/cli/apply/apply-codex-install-residuals.test.ts`.

## Differences from the Claude Code target

1. **`--target` and `--runtime codex` are mutually exclusive.** `--target` wires the generated Claude Code `settings.json` to a destination path; the codex branch produces no `settings.json`, so the combination throws `HarnessExitError("--target is incompatible with --runtime codex (target wires Claude Code's settings.json)", EX_NOINPUT)` (`apply`, `src/cli/apply/apply.ts`, which refuses `--runtime opencode` the same way). Only an explicit `--runtime codex` reaches this refusal: without `--runtime`, `--target` implies `claude-code` even after a codex apply, and the apply output names the switch (`runtime: codex -> claude-code (--target implies claude-code)`). Covering one manifest under both runtimes takes two invocations into separate generated trees.
2. **No sandbox or permission translation.** The Codex generator emits hook stanzas only: it consumes no permission data and writes no Codex sandbox or approval stanza (the generator header says harness owns hook wiring only). Operators keep model, auth, sandbox profile and MCP servers in their own config.
3. **branch-protection's blocker matches `apply_patch` only on Codex** (`PRE_TOOL_USE_MATCH_CLAUDE = "Write|Edit"`, `PRE_TOOL_USE_MATCH_CODEX = "apply_patch"`, `src/policy-packs/builtin/branch-protection.ts`), and its command carries `--runtime codex` (`BLOCKER_COMMAND_CODEX`). A Codex shell write is not matched by this pack. The hook itself judges `apply_patch` by the paths named in the patch's `*** Add File:`, `*** Update File:`, `*** Delete File:` and `*** Move to:` header lines, and falls back to the event cwd when the patch has none (header comment of `src/cli/pack/hook-branch-protection.ts`).
4. **Risk Gate cross-runtime support is officially deferred, with partial de-facto Codex accommodation.** `docs/risk-gate.md` lists cross-runtime support (OpenCode, Codex) as deferred: "Phase 7 targets the Claude Code `PreToolUse` surface". Yet `src/cli/policy/intercept.ts` carries Codex plumbing: `isCodexShellTool` and `resolvePolicyCwd` resolve the policy cwd for a shell event without an event cwd from the per-call `workdir`/`cwd` of the tool input, then from the `codexCommandCwd` seam, which falls back in production to the `--command-cwd` argument in `/proc/1/cmdline` (`readCodexCommandCwdFromProc`); and the Codex generator appends `--hook <name>` to `harness policy intercept` commands so each spawned process self-identifies (see "Per-hook self-identification" below). The generator also pins a 2s timeout floor for `policy intercept` hooks, 1s otherwise, through the shared `hookTimeoutSeconds` (`src/cli/apply/generate-settings.ts`), which both runtime projections use.
5. **`path_match` / `bash_match` are not projected into the Codex TOML.** The generator warns per hook ("script-side filter only", `generateCodexConfig`, `src/cli/apply/generate-codex-config.ts`). This is not a parity gap: the Claude Code projection treats them identically as script-enforced documentation; the Codex warning only makes the silent drop visible.

## Wire format (Codex vs Claude Code)

- **Event envelope (stdin):** the tool-event JSON Codex sends, read by the branch-protection hook as `{ session_id?, tool_name?, tool?, tool_input?, raw_input?, input?, cwd? }`; `tool` is a tolerated synonym of `tool_name` and a missing tool name reads as `(unknown)` (`runPackHookBranchProtectionCli`, `src/cli/pack/hook-branch-protection.ts`). Session-id resolution for `harness approve risk` accepts `$CODEX_SESSION_ID` as step 4 after `$CLAUDE_CODE_SESSION_ID` and `$CLAUDE_SESSION_ID`, with source `"env-codex"` (`resolveApprovalSessionId`, `src/runtime/session-id.ts`).
- **Block contract (PreToolUse):** `--runtime codex` blocks with exit 2 (`CODEX_EXIT_BLOCK`) and the reason on stderr; an allow is exit 0 with a stderr diagnostic. There is no JSON decision envelope on Codex. The Claude Code variant answers a block with a JSON deny envelope on stdout and exit 0. An unknown `--runtime` value refuses with exit 2, which both runtimes read as a block.
- **Fail direction of branch-protection:** closed on every failure the hook can see. A stdin read that times out (no complete event within the idle bound), an event that is not a JSON object, a manifest that does not load, a git call that fails or times out, and a path that cannot be resolved within the hook's bound all block. Only a pack that is undeclared or `enabled: false` allows without asking git, and so do a detached HEAD and a directory outside every repository.
- **Config artefact:** TOML instead of JSON. Table keys are protocol event names (`[[hooks.PreToolUse]]`, the Codex 0.131.0 schema; `eventKey`, `src/cli/apply/generate-codex-config.ts`). `timeout` is in SECONDS: `max(floor, ceil(budget_ms/1000))`, floor 2 for `harness policy intercept`, else 1. Hook `match` patterns are alias-expanded at emit time: any simple token that is a shell alias expands to the full set `Bash|shell|exec_command|functions.exec_command`, and `mcp__server__tool` tokens expand hyphen/underscore server-name variants plus the `mcp__server__.tool` dotted form (`expandCodexHookMatchPattern`, `expandToolNameAliases`, `src/runtime/tool-name-aliases.ts`). Output is stable-sorted (event, then command) for byte-equivalent no-op re-applies; the first line `# Generated by harness apply --runtime codex.` is the pinned detection header (`CODEX_GENERATED_HEADER_LINE`).
- **Per-hook self-identification:** Codex `policy intercept` commands carry `--hook <name>` (names restricted to `^[A-Za-z0-9._:-]+$`; exotic names silently skip the flag, `commandWithHookTag`, `SAFE_HOOK_NAME_RE`, `src/cli/apply/generate-codex-config.ts`); Claude Code commands never carry it, because that generator dedupes by `(command, timeout)` and the flag would multiply audit writes (the `hookName` doc comment in `src/cli/policy/intercept.ts`).
