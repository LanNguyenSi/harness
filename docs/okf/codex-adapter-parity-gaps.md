# Codex runtime adapter — parity gaps vs Claude Code

## What the adapter is

`harness apply --runtime codex` (Phase 6 #6) selects the Codex adapter instead of the default `claude-code`. It does NOT write `settings.json`; it emits `harness.generated/codex/config.toml` (`CODEX_CONFIG_BASENAME = "codex/config.toml"`, `src/cli/apply/apply.ts`) containing only harness-managed hook stanzas — `[[hooks.UserPromptSubmit]]`, `[[hooks.Stop]]`, `[[hooks.PreToolUse]]`, `[[hooks.PostToolUse]]` (task a1348c89, see gap 1), each with `hooks = [{ type = "command", command = "...", timeout = N }]` (`src/cli/apply/generate-codex-config.ts`, `emitHook`/`emitCommandHook`). With `--install`, only the marked harness-managed block inside `~/.codex/config.toml` is replaced; operator model/auth/sandbox config is never owned by harness (generator header, lines 48–69). `MEMORY.md` and pack `instructions.md` ship runtime-agnostic and unchanged (`apply.ts` lines 393–394). The Codex hook entrypoints are harness CLI subcommands, not npm bins, because `@lannguyensi/understanding-gate` ships no Codex bins: `harness pack hook codex-user-prompt-submit` / `codex-stop` / `codex-pre-tool-use` / `codex-post-tool-use` (`understanding-before-execution.ts`; `docs/CLI.md` hook-entrypoints table). `harness doctor --target codex` checks the binary on `$PATH`, the generated TOML's banner, command resolvability per hook group, and reports-dir writability (`src/cli/doctor/codex.ts`; docs pack file "Doctor wiring").

Cross-runtime approval state is shared by design: both runtimes persist reports into the same `.understanding-gate/reports/` directory and use the same marker/approve flow, so `harness approve understanding` works identically after a Codex block (`understanding-before-execution.ts`, the shared `wrap`/`prefixCommandWithReportsDir` prefixing in `buildHooks`, lines 778–783).

The Codex generator (`generate-codex-config.ts`) already mapped `"PostToolUse"` to `[[hooks.PostToolUse]]` before this task (added in PR #211 against the real Codex 0.131.0 `hook_config.rs` schema, independently confirmed by the CHANGELOG `[0.24.0]` / PR #211 entry) — the schema support was real and already tested (`tests/cli/apply/generate-codex-config.test.ts`), it simply wasn't contributed by this pack yet. This was the buried residual of the CHANGELOG `[0.39.0]` task e7c2ec3c fix ("Known residual: the pack wires no Codex PostToolUse hook, so `expire_on_tool_match` boundaries still do not fire in Codex sessions"). **`expire_on_bash_match` routing was a separate gap — see gap 12, now CLOSED (task bea04a03).**

   **Sub-finding fixed in the same task (review, verified by mutation testing):** Codex can emit an MCP tool name in a variant form for the identical tool (server hyphen/underscore swap, the `mcp__server__.tool` dotted form) — `addMcpAliases` (`src/runtime/tool-name-aliases.ts`) and `harness policy intercept`'s `policyMatchesEvent` (`src/runtime/intercept.ts`) already handle this for the Risk Gate surface. The first version of this task's `match` field reused the Claude `postToolUseMatchPattern` helper (an anchored `^(?:...)$` regex); `expandCodexHookMatchPattern`'s "simple token" guard (`isSimpleToolPatternToken`, generate-codex-config.ts) rejects any token containing `^`, `(`, or `?`, so an anchored match string is passed through UNCHANGED at TOML-emit time — Codex's own dispatcher would never have invoked the hook for a variant `tool_name` at all. Fixed by a Codex-specific `codexPostToolUseMatchPattern` (bare `|`-joined list, same shape as `PRE_TOOL_USE_MATCH_CODEX`) so the emitted matcher DOES get alias-expanded. A second, independent half of the same bug lived in the hook body: `toolNameMatchesAny`'s raw `===` comparison against the config's `expire_on_tool_match` list would also have missed a variant `tool_name` even if the hook WAS invoked; now alias-aware via `expandToolNameAliases`. Both halves were mutation-verified separately (each reverts to red without its half of the fix). The legacy v1 `tasks_transition` status filter is alias-aware too, closing a status-filter-bypass an alias-aware general match but non-alias-aware status check would otherwise have introduced (a variant `tasks_transition` call would match generally but skip the `status === "done"` check, clearing the marker on ANY status).

## Wire-format differences (Codex vs Claude Code)

- **Event envelope (stdin, all Codex hooks):** `{ session_id?, tool_name?, raw_input?, event? }`. One tolerated synonym: `tool` for `tool_name`. `id` is deliberately NOT aliased to `session_id` — "`id` in most event-bus shapes is the event/message id, not the session id" (`hook-codex-pre-tool-use.ts` lines 116–121). Session-id fallback env chain when the field is absent: `$CODEX_SESSION_ID` → `$CLAUDE_CODE_SESSION_ID` → `$CLAUDE_SESSION_ID` (lines 267–272); the shared resolver lists `$CODEX_SESSION_ID` as step 4 with source `"env-codex"` (`src/runtime/session-id.ts` lines 178, 234, 265–268). Since slice 2 (gap 13), `codex-pre-tool-use` also tolerates `tool_input` beside `raw_input` for its read-only and recovery-commit exemptions, through its own `resolveCodexExemptionCommand` rather than the shared `resolveToolInput`: `tool_input` is preferred, a `null` or absent `tool_input` falls back to `raw_input`, and when both are present the pair must classify to the same command, otherwise (disagreeing commands, or only one side classifying) the exemption returns null and the call takes the block path. It also reads two more fields off the same envelope for the auto-approval attempt: `permission_mode` (the `auto_approve.when` allowlist input) and `transcript_path` (the session-consistency evidence; see gap 13 above).
- **Block contract (PreToolUse):** exit 2 (`EXIT_BLOCK`, the module-level const) + reason on stderr; allow is exit 0 with a stderr diagnostic. There is no JSON-decision envelope: "the JSON-decision shape Claude Code reads is not part of Codex's hook contract today" (`hook-codex-pre-tool-use.ts` lines 13–16). Claude Code hooks communicate decisions via structured stdout JSON.
- **Fail direction:** identical to Claude — malformed JSON, missing manifest, undeclared/disabled pack, or unresolvable session id all resolve to ALLOW with a loud stderr diagnostic (fail-open on infrastructure error; the gate itself fails closed on an unclassifiable `raw_input` for the read-only exemption).
- **Shell-command extraction:** `raw_input.command` / `raw_input.cmd` via the shared `extractShellCommand`; a conflicting `command` vs `cmd` pair returns null → falls through to block (`extractCodexShellCommand`). Bare-string `raw_input` is accepted as the command; the `tool_input`/`raw_input` pairing rules of `resolveCodexExemptionCommand` (envelope bullet above) sit in front of this extraction. Read-only single-`|` pipelines are exempted in both runtimes (`isReadOnlyBashPipeline`).
- **Injector contract (UserPromptSubmit):** plain-text instruction block on stdout (no JSON wrapper), which Codex prepends to `additional_instructions`; stdin envelope `{ session_id?, prompt? }` (`hook-codex-user-prompt-submit.ts` lines 11–19).
- **Stop contract:** stdin envelope `{ session_id?, last_assistant_message?, messages? }`; `last_assistant_message` preferred, else last `role === "assistant"` row of `messages[]`; persists `.understanding-gate/reports/<iso>-codex-<sessionhash>.json` with `approvalStatus: "pending"`; every error path is exit 0 + stderr (Stop must never block the response path) (`hook-codex-stop.ts` lines 1–28 for the envelope and fail-mode, 86–98 for the extraction logic, `buildReportFilename` at 283–287 and the persisted body at 400–409 for the filename/status).
- **PostToolUse contract (task a1348c89, `expire_on_bash_match` routing closed by task bea04a03):** advisory only — never blocks, exit 0 + stderr diagnostic on every path. Unlike the other Codex hooks it prefers `tool_input` over `raw_input` when both are present (`tool_input` is the field name the published Codex `PostToolUse` payload actually sends; `raw_input` stays accepted for shims built against harness's earlier portable format).
