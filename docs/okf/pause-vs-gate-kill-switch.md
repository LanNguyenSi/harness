# Kill switches: `harness pause` vs `harness gate disable`

harness has TWO separate kill-switch mechanisms. Do not conflate them: `pause` is a temporary, auto-expiring mute of the policy-intercept hook and the runtime-reality hook; `gate disable` is a surgical, persistent removal of specific hook groups from Claude Code's `settings.json`. They operate on different state (sentinel file vs settings.json), have different guardrails, and different restore paths. The one gate `pause` does not mute is branch-protection, so `gate disable` (Claude Code) or `enabled: false` on the pack (Codex) is the switch for it.

## Decision table

| Situation | Use |
|---|---|
| Lockout recovery from a wedged policy gate, debug A/B test, incident hotfix, short window | `harness pause --for <duration>` (the `harness policy intercept` and `harness pack hook runtime-reality` hooks go dormant, auto-resumes) |
| A deliberate edit on a protected branch (a hotfix on `master`), or one specific hard-blocking hook group that must go and that `pause` does not mute (branch-protection is the shipped one) | `harness gate disable --matcher <substring>` (removes only matching hook groups, reversible snapshot); on Codex set `enabled: false` on the pack and re-run `harness apply --runtime codex --install` (`docs/policy-packs/branch-protection.md:232#"Disable the gate (operator only)"`) |
| Permanently turn a policy off | NEITHER. Remove the policy's entry from `policies:` in the manifest; for the hooks a policy pack adds, set `policy_packs[].enabled: false` (`src/schema/policy-packs.ts:24#"enabled: z.boolean().default(true),"`). A policy has no `enabled` field: `PolicySchema` is strict, so validation rejects one (`src/schema/policies.ts:151-163#".strict()"`). Persistent, diff-able, source-controlled. Stated in the `harness pause` command help (`src/cli/register-operator-lifecycle.ts:36-41#"in the manifest."`) and `docs/for-humans.md:425-431#"source-controlled"` |
| "Move fast on a prototype branch" | A policy with a narrower trigger (for example a `bash_match` that names only what you guard), not a session-wide pause (`docs/for-humans.md:425-433#"session-wide pause"`) |

## Mechanism 1: `harness pause` / `harness resume` (sentinel)

**What it is.** One JSON file at `<generatedDir>/.harness-paused` (`SENTINEL_BASENAME` in `src/runtime/pause-sentinel.ts:38#"SENTINEL_BASENAME"`). `generatedDir` is `harness.generated/` next to the manifest in use, or `<homeDir>/harness.generated` with an override (`src/io/generated-dir.ts:32-38#"path.dirname(opts.manifestPath)"`). While the sentinel exists and is unexpired, `harness policy intercept` (the PreToolUse gate entrypoint) and `harness pack hook runtime-reality` check it before the manifest is loaded or any gate logic runs (`src/cli/policy/intercept.ts:593-600#"checkPauseFromLoader(pauseOpts).paused"` and `src/cli/pack/hook-runtime-reality.ts:234#"checkHookPause("`), emit one stderr line (`harness <hook>: PAUSED since Xm ago (reason: ...); auto-resumes in Ym. Run \`harness resume\` to re-enable.`, `src/runtime/pause-sentinel.ts:187-188#"PAUSED since"`) and short-circuit to allow without evaluating gate logic. Both go through `checkPauseFromLoader` (`src/cli/pause-check.ts:39#"checkPauseFromLoader"`) and `maybeAnnouncePause` (`src/runtime/pause-sentinel.ts:171#"maybeAnnouncePause"`); `checkHookPause` is the wrapper for pack hooks (`src/cli/pack/hook-bootstrap.ts:83#"checkHookPause"`). On the first hook fire AFTER expiry the sentinel is silently deleted (auto-resume) and gating resumes.

**Branch-protection does not yield to a pause.** It is the only builtin policy pack and its hook never reads the sentinel; the comment on its stdin-timeout refusal says so (`src/cli/pack/hook-branch-protection.ts:331-333#"this gate does not yield to a pause"`), and the pack doc states "The operator pause (`harness pause`) does not switch this gate off" (`docs/policy-packs/branch-protection.md:245#"does not switch this gate off"`). The `pause` command help still says "all harness hooks dormant" (`src/cli/register-operator-lifecycle.ts:36-37#"Temporarily make all harness hooks dormant"`); read it as the hooks that check the sentinel. `docs/for-humans.md:363#"Branch-protection does not yield to a pause"` and the `harness pause` row in `docs/CLI.md` give the accurate scope.

**Commands** (registered in `src/cli/register-operator-lifecycle.ts:35-95#"stdout("` (`pause`) and `src/cli/register-operator-lifecycle.ts:99-131#"stdout("` (`resume`)):
- `harness pause --for <duration>` - e.g. `5m`, `1h`, `PT30S`; default 15 minutes (`DEFAULT_PAUSE_SECONDS = 15 * 60`, `src/cli/pause/index.ts:36#"DEFAULT_PAUSE_SECONDS"`).
- `harness pause --indefinite` - refuses unless the separate verbose flag `--i-am-the-operator-and-accept-no-auto-resume` is also passed; the flag's verbosity is deliberate friction (`src/cli/pause/index.ts:269-279#"EX_USAGE"`).
- `--reason <text>` - recorded in the sentinel and announced on each hook fire.
- `harness resume` - deletes the sentinel. Idempotent: against an un-paused install it exits 0 with a notice and skips the ledger write (`src/cli/pause/index.ts:370-375#"no active pause"`).
- Re-running `pause` while already paused overwrites the sentinel with the new expiry and prints `note: harness was already paused` (`src/cli/register-operator-lifecycle.ts:76-77#"already paused"`).

**Operator-only, CODE-CHECKED but NOT CODE-ENFORCED.** Both `pause` and `resume` refuse (exit EX_USAGE) when any of `$CLAUDE_CODE_SESSION_ID` (canonical, what Claude Code exports), legacy `$CLAUDE_SESSION_ID`, or `$CODEX_SESSION_ID` is set (`refuseIfAgentShell`, `src/cli/pause/index.ts:172-221#"EX_USAGE"`), and refuse non-TTY stdin unless `--i-am-the-operator` is passed (`refuseIfNonTTY`, `src/cli/pause/index.ts:226-241#"EX_USAGE"`). Do NOT run it from inside Claude Code with the `! ` prefix: that shell INHERITS this session's env AND its non-TTY stdin, so it trips both checks exactly like an agent Bash call would (`docs/for-humans.md:371-379#"verified live"`). There is no in-session shell shape that satisfies both checks; the operator must use a terminal genuinely outside the agent session. Because of this, an agent can bypass both checks with one ordinary Bash-tool call and no `! ` involved: `env -u CLAUDE_CODE_SESSION_ID -u CLAUDE_SESSION_ID -u CODEX_SESSION_ID harness pause --for 1h --i-am-the-operator`. The actual enforcement point that runs BEFORE the agent's Bash executes is the PreToolUse deny-policy layer described below, not this CLI check.

**Enforcement layer.** `harness init --template full` ships three default `block` policies (`src/cli/init/templates.ts:609#"name: deny-kill-switch-bypass"`, mirrored in `docs/examples/full-manifest.yaml`) that deny, from the agent's Bash tool: `deny-kill-switch-bypass` (`harness pause` / `harness resume` / `harness gate disable` / `harness gate enable` themselves, tolerating `npx`/absolute-path prefixes and quoted verbs), `deny-session-env-strip` (the `env -u CLAUDE_CODE_SESSION_ID`, `env -uCLAUDE_CODE_SESSION_ID` (no space), `env --unset=CLAUDE_CODE_SESSION_ID`, `unset CLAUDE_SESSION_ID`, and bare `CLAUDE_CODE_SESSION_ID=` (empty-value reassignment) shapes that defeat `refuseIfAgentShell`), and `deny-pause-sentinel-forgery` (direct writes to `.harness-paused` via `>`, `>>`, `tee`, or `cp`; reads are unaffected). Each has a matching `harness policy intercept` hook (`deny-kill-switch-bash`, `deny-session-env-strip-bash`, `deny-sentinel-write-bash`, `src/cli/init/templates.ts:269-310#"same rationale as deny-kill-switch-bash above"`). Known gap, disclosed not hidden: a bash_match regex cannot see through a heredoc, `sh -c '...'`, `bash -lc`, `eval`, `python -c`, a base64-decoded payload, a script file the agent creates and then executes, a symlink swap, or the sentinel-write equivalents of `cp`/`>` done via `mv`, `ln`, `install`, or `dd`; closing that class needs signing the sentinel (HMAC) or a filesystem-level write guard, neither implemented (`src/cli/init/templates.ts:296-302#"neither of which is in scope"`).

**The three policies are `operator_only: true`, not ledger-gated.** `operator_only: true` is a schema-level primitive on `PolicySchema` (`src/schema/policies.ts:159#"operator_only: z.boolean().optional()"`): a policy carrying it declares no `requires:` and no `producers:` and must use `enforcement: block` (`src/schema/policies.ts:165-187#"must not also declare producers:"`). `evaluateOnePolicy` short-circuits to an unconditional `deny` BEFORE the requires pipeline runs (`src/runtime/intercept.ts:881-891#"if (policy.operator_only === true)"`): no ledger query, no template substitution, so no ledger write (`mcp__grounding-mcp__ledger_add` included), marker file, or env flag can ever flip it to allow. That matters because every `requires:`-based policy is satisfiable by the very agent it gates: `${SESSION_ID}` resolves to the agent's own session and the ledger is queried in that same session's bucket, so "whoever can write the ledger can open the gate" (`docs/writing-custom-policies.md`, tripwire 4). A filesystem marker was rejected as the fix because the agent's Bash/Write could create it just as easily. `harness validate`'s `checkPolicySelfAttestation` treats `operator_only: true` as correct-by-construction and emits no "declares no producers" warning (and no `--strict` error) for these three (`src/cli/validate/checks.ts:531-537#"p.operator_only === true"`). `tests/cli/init-full-template-kill-switch-deny.test.ts` drives the real `intercept()` against a ledger forging every evidence shape and asserts the block holds, and that the ledger is never queried for these three.

**Residual gap, still open: `bash_match` regex coverage.** `operator_only: true` closes the *evidence-satisfaction* hole, not the *trigger-matching* one: a bash_match regex is evaluated BEFORE `operator_only:` is consulted, so an agent that defeats the trigger match (a heredoc, `sh -c '...'`, `eval`, a base64-decoded payload, a script file it writes and then executes) never reaches the deny. What is covered and what is not, per policy:
- `deny-kill-switch-bypass` is wrapper-hardened. `peelWrapperPrefixes` (`src/runtime/command-normalize.ts:2450#"export function peelWrapperPrefixes"`) peels wrapper prefixes (`env`, `nice`, `command`, `sudo`, `doas`, `time`, `timeout`, `stdbuf`, `setsid`, `exec`, `nohup`, leading `VAR=value`) and collapses whitespace runs for the closed head-token set `git`/`gh`/`npm`/`harness` (`src/runtime/command-normalize.ts:863#"NON_GIT_HEAD_TOKENS"`), so `env harness pause`, `nice harness pause`, `exec harness pause`, `nohup harness pause` and `env -C /tmp harness pause` reach the deny via the raw-OR-normalised match (pinned in `tests/runtime/command-normalize.test.ts` and `tests/runtime/intercept-cli.test.ts`). Side effect, recorded not hidden: introspection spellings like `command -v harness pause` now deny too (over-block direction; on an `operator_only` deny no in-session evidence clears it, so reword the probe).
- `deny-session-env-strip` and `deny-pause-sentinel-forgery` are NOT covered: they key on `env`/`unset` and `tee`/`cp`, which are not in the closed head-token set, and `env` is structurally unreachable for the normaliser (its peeling loop consumes `env -u <VAR>` while hunting for a gated command behind it, erasing the very text the trigger keys on). One wrapper word still suffices: `nice env -u CLAUDE_CODE_SESSION_ID ...`, `nice tee <sentinel>` (pinned as explicit not-covered tests in `tests/runtime/command-normalize.test.ts`). A head-token drift guard (`tests/runtime/bash-match-head-token-drift.test.ts`) fails when a future `bash_match` policy gates a head token the normaliser does not cover.
- A bare `&` is a boundary in every shipped `bash_match`, so `A=x&harness pause` and `sleep 0 & harness pause` deny (pinned in `tests/cli/init-full-template-kill-switch-deny.test.ts`). An existing `full` install keeps the older `&&`-only triggers until its manifest is regenerated; `harness doctor` detects that itself (see Drift detection below). Measurement and the other affected gates: [Shell quote models, measured divergence against bash](quote-model-divergence.md).

Net effect: these three policies are a hard boundary against ANY in-session evidence; `deny-kill-switch-bypass` is additionally wrapper-hardened, while the other two remain best-effort against trigger evasion.

**Scope.** These three policies ship ONLY in `harness init --template full`. The `solo` and `team` templates carry no policy-layer protection against these bypasses, only the CLI checks in `src/cli/pause/index.ts` (`src/cli/init/profiles.ts:33#"does NOT carry the full template's operator_only kill-switch policies"`). `harness apply` does not retroactively add new default policies to an already-materialized manifest; re-run `harness init --template full --force` (it overwrites the manifest wholesale, so re-apply local edits; without `--force` it refuses an existing manifest, `src/cli/init/index.ts:109-111#"pass --force to overwrite"`) or hand-add the three policy/hook pairs from `src/cli/init/templates.ts`.

**Drift detection.** Because an aged manifest silently loses these defenses, `harness doctor` compares the installed manifest against the shipped `operator_only` set (`shippedOperatorOnlyPolicyNames()`, derived from `FULL_TEMPLATE` so it cannot drift from what `init` writes, `src/cli/init/templates.ts:733#"shippedOperatorOnlyPolicyNames"`) and reports each missing or downgraded kill-switch policy as an ERROR naming the policy and the rehydration path (`checkTemplatePolicyDrift`, `src/cli/validate/checks.ts:596#"checkTemplatePolicyDrift"`; counted into the doctor error total at `src/cli/doctor/index.ts:899-902#"errorCount += report.templateDrift.errors.length"`). The check applies regardless of profile, so a fresh `solo`/`team` install reports all three as drift by design. A deliberate opt-out is `doctor.ignore_template_drift: [<policy-name>, ...]` in the manifest (`src/schema/doctor.ts`): it silences only the report line and changes no enforcement. It is deliberately NOT a `policies[].enabled: false` flag, which the engine would ignore.

**Trigger-boundary drift detection.** The check above misses a shipped-by-name `bash_match` trigger whose regex still opens with a stale boundary alternation. `checkTriggerBoundaryDrift` (`src/cli/validate/checks.ts:784#"export function checkTriggerBoundaryDrift"`) compares, by name, the leading boundary group of every shipped-by-name `bash_match` (hook-level and policy-level) against the template's (`shippedBashMatchBoundaries()`, `src/cli/init/templates.ts:800#"shippedBashMatchBoundaries"`), never the rest of the regex an operator may have customized. A mismatch is a doctor ERROR (`src/cli/doctor/index.ts:905-910#"errorCount += report.triggerBoundaryDrift.errors.length"`) whose message gives the rehydration path: `harness init --template full --config /tmp/harness-full.yaml` (a throwaway path; `init` resolves its target from `--config` or the home directory, never `cwd`, and `--force` against the live manifest is not the safe way to get just the regex) and copy the boundary from there (`src/cli/validate/checks.ts:743-753#"harness-full.yaml"`). The same `doctor.ignore_template_drift` field is the opt-out for a trigger name.

**Audit trail.** Pause/resume write `harness-paused:<pausedAt>` / `harness-resumed:<pausedAt>` facts to the evidence ledger via grounding-mcp, under the synthetic session bucket `default` (`OPERATOR_LEDGER_SESSION`, `src/cli/pause/index.ts:48#"OPERATOR_LEDGER_SESSION"`) since no agent session id exists in an operator shell. `harness audit --since 24h` surfaces them. Ledger failure does not block the pause; it is reported as `ledger: ⚠ skipped` (`src/cli/register-operator-lifecycle.ts:89-91#"skipped"`).

**Trust caveat.** The sentinel is plain JSON with NO signature (`docs/for-humans.md:447-448#"no signature"`). Neither the CLI checks nor the PreToolUse deny-policy layer above is a true boundary against an agent that already has Write access under `harness.generated/` (the Bash-surface deny does not see a non-Bash tool's write). Defence: deny agent writes to `harness.generated/` (a blanket deny is simplest; the agent surface normally never needs to write there). Fail-open note: a malformed sentinel is treated as absent (never escalates to a block), and so is one that cannot be read as a regular file (a FIFO, a device or a directory at the path, or a file over 1 MiB): `readSentinel` reads it through one bounded, non-blocking descriptor read (`src/runtime/pause-sentinel.ts:60-69#"readTextFileBoundedOrThrow(sentinelPath"`), so planting one neither hangs the hook past its budget nor counts as a pause that switches the gates off. A forged `expiresAt` that is not a non-empty string or null is rejected as malformed rather than silently read as indefinite (`normalizeSentinel`, `src/runtime/pause-sentinel.ts:90-105#"expiresAt must be a non-empty ISO string or null"`).

## Mechanism 2: `harness gate disable` / `harness gate enable` (settings.json surgery)

**What it is.** Reads `~/.claude/settings.json` (override: `--settings <path>`; default resolved via `os.homedir()` + `.claude/settings.json`, `src/cli/gate/disable.ts:31#"DEFAULT_SETTINGS_REL"` and `src/cli/gate/disable.ts:82-86#"os.homedir()"`), removes hook groups whose `matcher` field substring-matches `--matcher <pattern>` - LITERAL substring, not regex, so operators can paste the exact matcher from `settings.json` or the gate's deny message (`matcherMatches`, `src/cli/gate/disable.ts:184-192#"m.includes(pattern)"`). Before mutating it: (1) backs up the original to `<settings.json>.bak.<ISO>`, (2) writes a snapshot of the removed groups to `<settings-dir>/harness.gate-disable.<ISO>.json` (ISO stamps use `-` for `:`, `src/cli/gate/snapshot.ts:65-76#"bak."`), then (3) atomically rewrites settings.json. Ordering is deliberate: backup before any mutation, snapshot before the live rewrite (`src/cli/gate/disable.ts:230-265#"atomicWriteFile(settingsPath, newSettings);"`). Refuses to operate on non-JSON or non-object settings files rather than "fixing" them (`src/cli/gate/disable.ts:110-115#"restore from a backup"`).

**Dry-run.** With NO `--matcher`, `harness gate disable` is a pure listing: it prints every candidate hook group (`event[index] matcher=... : commands`) and exits without writing anything (`src/cli/gate/disable.ts:197-202#"return { mode"`). A `--matcher` that matches nothing errors and points you at the no-args listing (`src/cli/gate/disable.ts:222-224#"no args"`).

**Restore.** `harness gate enable` (`src/cli/gate/enable.ts`) picks the NEWEST `harness.gate-disable.*.json` snapshot next to settings.json (mtime-sorted, `listSnapshots` in `src/cli/gate/snapshot.ts:85-105#"candidates.sort"`) and splices the removed groups back at their original indices. Two safety behaviors:
- **Hash-mismatch refusal** (`src/cli/gate/enable.ts:166-171#"pass --force to restore anyway"`): if the on-disk settings.json sha256 differs from the snapshot's recorded `settingsAfterSha256`, you edited the file since the disable; enable refuses so it does not overwrite your edits. Inspect the diff against the recorded `settingsBackupPath`, then pass `--force` to restore anyway.
- **Idempotent**: if the current sha equals `settingsBeforeSha256` (already restored), it exits 0 without writing (`src/cli/gate/enable.ts:160-163#"already-restored"`).

**Guardrail asymmetry.** Unlike `pause`, `gate disable`/`gate enable` have NO agent-session env-var or TTY refusal in code. `GateDisableOptions` is only `settingsPath | homeDir | matcher | now` (`src/cli/gate/disable.ts:33-50#"now?: Date"`); `GateEnableOptions` is only `settingsPath | homeDir | force`. Its operator-only nature is by intent and documentation ("operator escape hatch", `src/cli/register-gate-gc-group.ts:11#"operator escape hatch for hard-blocking hooks"`), not enforced in the CLI. What does protect it: `harness gate disable` / `harness gate enable` are among the commands the `deny-kill-switch-bypass` PreToolUse policy denies from the agent's Bash tool (see "Enforcement layer" above), so an agent with Bash access under a `full`-template install is blocked at the hook layer even though the CLI itself has no check. If your policy set does not gate Bash (or the operator installed a manifest without that policy), nothing stops `harness gate disable`, and the reversible snapshot plus `.bak` file are the recovery record either way. `gate disable` edits the Claude Code settings only; it does not touch Codex.

## Quick recovery recipes

- Bash locked out by a `harness policy intercept` gate (recovery command itself blocked): `harness pause --for 15m --reason "recovery"` from your OWN terminal outside the agent session silences it. If a custom hook group blocks and `pause` does not mute it, run `harness gate disable` (list), find the group's matcher, `harness gate disable --matcher <substring>`, fix the underlying state, then `harness gate enable`.
- Edit or write refused on a protected branch (branch-protection; its hook matches only `Write|Edit` on Claude Code and `apply_patch` on Codex, `src/policy-packs/builtin/branch-protection.ts:70-71#"PRE_TOOL_USE_MATCH_CODEX"`, and does not yield to a pause). Claude Code: `harness gate disable` (list), `harness gate disable --matcher Write|Edit`, do the edit, then `harness gate enable`. Codex: set `enabled: false` on the pack and run `harness apply --runtime codex --install`, do the edit, then revert both.
- Debugging whether harness causes a behavior: `harness pause --for 15m --reason "A/B test"`, reproduce, `harness resume` (or let it auto-expire).
- Check pause state: stat `<generatedDir>/.harness-paused`, or just run any hooked tool and read the stderr notice; audit history via `harness audit --since 24h` (session bucket `default`).
