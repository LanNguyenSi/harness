## The invariant

`harness add <type> <name>` and `harness remove <type> <name>` never validate just the entry being changed. Both apply the mutation to the full YAML text (`applyAdd` / `applyRemove` on a `parseDocument` of the whole file) and then validate the **entire resulting manifest**. There are two distinct gates with **different scopes**, and conflating them is what makes the errors confusing:

1. **Schema gate** (add AND remove): `validateBeforeWrite(parseYaml(proposed))` - a thin wrapper around `parseManifest` (`src/io/validate-before-write.ts:12-26#"throw"`) that zod-parses the whole document. **No baseline comparison.** A pre-existing schema error anywhere in `harness.yaml` (a typo'd key under `.strict()`, a duplicate `tools.mcp`/`tools.cli` name from `ToolsSchema.superRefine` at `src/schema/tools.ts:70-84#"seen.add"`, a duplicate hook/policy name, a policy referencing an undeclared hook via `ManifestSchema.superRefine` at `src/schema/index.ts:45#"which is not declared in hooks[]"`, a workflow step naming a missing review template at `src/schema/index.ts:57#"is not defined in review_templates"`, or a wrong `version:`) blocks an otherwise-valid add or remove of a completely unrelated entry. Error text: `proposed manifest fails schema validation:` followed by `path: message` lines that name the *broken* entry, not the one you touched. A key or pack name that a release removed does not trip this gate: `parseManifest` strips those entries before the strict parse and reports them as warnings (`src/schema/index.ts:134#"ManifestSchema.safeParse(stripped.raw)"`, table in `src/schema/removed-keys.ts`), so only a key that was never valid, or a malformed value, blocks.

2. **Asset gate** (add ONLY, `src/cli/add/index.ts:92-130#"newErrors.length"`): `runAssetChecks(withDerivedPolicies(parseManifestWithWarnings(parseYaml(proposed)).manifest))` also runs against the **full manifest** (in its derived view, `workflows[]`-derived merge-gate policies folded in on both the proposed and the baseline side, the same view `harness validate` checks), but its result is **diffed against a baseline**. Add re-runs the identical checks on the *original* manifest (`src/cli/add/index.ts:106-120#"the gate fails closed"`) and keys each error-severity diagnostic as `severity|path|message` (`src/cli/add/index.ts:115#"baselineErrors.map"`). Both sides remap a diagnostic path with `remapDiagnosticPath` before it is keyed, so a dropped policy or policy pack does not shift the index a later entry is reported under: proposed and baseline errors both name the index as written in the file, the way `harness validate` reports it. Only diagnostics **not present in the baseline set** block (`newErrors`, `src/cli/add/index.ts:123-124#"!baselineKeys.has"`; the error text `proposed manifest fails asset validation:` is thrown at `src/cli/add/index.ts:132-134#"EX_FAIL"`). Pre-existing asset errors are demoted to a warning on the result - `harness manifest has N pre-existing asset error(s) unrelated to this add; run `harness validate` to see them` (`src/cli/add/index.ts:141-142#"pre-existing asset error(s)"`) - and the add proceeds. So for asset problems the true semantics is: **pre-existing does NOT block, newly-introduced does.**

`harness remove` runs **no asset checks at all** - only the schema gate (`src/cli/remove/index.ts:186-190#"EX_FAIL"`) plus a schema-only recheck after lock acquisition (`src/cli/remove/index.ts:223-227#"EX_FAIL"`). Add has the same schema-only post-lock recheck (`src/cli/add/index.ts:158-162#"EX_FAIL"`); asset checks are not repeated under the lock.

What the asset gate actually checks (`runAssetChecks`, `src/cli/validate/checks.ts:989-1006#"...checkWorkflows(manifest),"`), all against the whole manifest. Only the **error-severity** diagnostics can block an add; the rest are warnings and are dropped by add's `severity === "error"` filter:
- `checkMcp` (`src/cli/validate/checks.ts:82-98#"return diags;"`): for every `tools.mcp[]` entry whose command's **first token is a rooted path** (absolute or `~/`), `statSync` the path (after `expandHome` against `opts.homeDir`); missing path → error `tools.mcp[<name>].command: path does not exist: <resolved>`. Note the bracket key is the **tool name, not an index**.
- `checkCli` (`src/cli/validate/checks.ts:101-167#"return diags;"`): binary resolvable (absolute-and-executable, or found on `PATH`); `required: true` missing binary is an error. An installed version below `min_version` is an error only when the caller supplies `versionProbe`; without a probe, the `tools.cli[].min_version` floor warns that it was not checked and refers to `harness doctor`. The shipped validate action supplies no probe and never executes manifest version commands; `--strict` still promotes warnings to errors.
- `checkSkills` (`src/cli/validate/checks.ts:170-188#"SKILL.md not found in any"`): every `tools.skills.required[]` name must have a `SKILL.md` under some `source_dirs` entry.
- `checkHooks` (`src/cli/validate/checks.ts:195-222#"not executable (chmod +x)"`): rooted hook command paths must exist, be regular files, and be executable.
- Policy-pack source and config resolution (`checkPolicyPacks` `src/cli/validate/checks.ts:926-930#"message: issue.message,"`, `checkPolicyPackConfigsAsDiagnostics` `src/cli/validate/checks.ts:943-952#"message: issue.message,"`), keyed at `policy_packs[N]...`.
- `checkPolicyTriggerPathMatch` (`src/cli/validate/checks.ts:970-983#"documentation only, so the hook"`): a `policies[].trigger.path_match` is an error, because the policy engine never evaluates it. Keyed at `policies[N].trigger.path_match`.
- `checkHookBudgetLedgerMargin` (`src/cli/validate/checks.ts:885-918#"return diags;"`): once `grounding-mcp` is wired, a `blocking: hard` hook that runs `harness policy intercept` and carries a `budget_ms` below the margin its ledger timeout requires is an error at `hooks[<name>].budget_ms`.
- The workflow checks, `checkWorkflows` (`src/cli/validate/checks.ts:494-501#"...checkWorkflowDerivedNameCollision(manifest),"`). Error severity: `checkWorkflowGateWiring` (`src/cli/validate/checks.ts:294-339#"checkTaskVerbGateWiring(manifest, offending)"`; a `spawn: "required"` review-then-merge workflow whose evidence hooks are missing, or declared under the right name but wired to the wrong trigger surface or command, see the function's own header comment) and `checkWorkflowDerivedNameCollision` (`src/cli/validate/checks.ts:472-484#"Rename the hand-authored policy."`). Their warning-severity siblings (the task-verb wiring gap, the weak-overlap and merge-before-review checks) never block.
- Warning-severity only, so never blocking: `checkBuiltinDrift`, `checkPolicyGroundingMcp` (evidence-consuming policies declared but `grounding-mcp` not wired) and `checkPolicySelfAttestation`.

Why the baseline diff is stable across the mutation: `applyAdd` **appends** to the sequence (`addToSequence` → `node.add`, `src/cli/add/mutate.ts:64-79#"sequence"`), and diagnostic paths for mcp/cli/skills/hooks are **name-keyed** (`tools.mcp[foo].command`), so existing entries' diagnostic keys are byte-identical between baseline and proposed and dedupe correctly.

## Where it's enforced

- Schema gate, add: `src/cli/add/index.ts:72-74#"EX_FAIL"` (pre-lock) and `src/cli/add/index.ts:160-162#"EX_FAIL"` (post-lock recheck).
- Asset gate + baseline diff, add: `src/cli/add/index.ts:92-142#"to see them"` (`proposedErrors` `src/cli/add/index.ts:96-99#".filter((d) => d.severity"`, `baselineKeys` `src/cli/add/index.ts:106-120#"the gate fails closed"`, `newErrors` split `src/cli/add/index.ts:123-124#"!baselineKeys.has"`, `preExistingErrors` split `src/cli/add/index.ts:126-127#"baselineKeys.has"`, block `src/cli/add/index.ts:132-134#"EX_FAIL"`, warning `src/cli/add/index.ts:141-142#"pre-existing asset error(s)"`).
- Schema gate, remove: `src/cli/remove/index.ts:186-190#"EX_FAIL"` (pre-lock) and `src/cli/remove/index.ts:223-227#"EX_FAIL"` (post-lock recheck). `--force` on a hook referenced by policies only skips the human-readable pre-check (`src/cli/remove/index.ts:142-147#"EX_FAIL"`); the schema gate still rejects the resulting dangling `policy.hook` reference (`src/cli/remove/index.ts:181-185#"still fires"`). A SECOND pre-check sits right after the policy one (`src/cli/remove/index.ts:151-168#"EX_FAIL"`): a hook a `workflows[]`-derived merge gate depends on (see `derivedGateReferencingWorkflows`, `src/cli/remove/index.ts:66-116#"affected.has(wf.name)"`) is refused the same way, EXCEPT `--force` here has no schema-level safety net (a derived gate is not a static YAML reference the schema can see) - see that function's header comment; the CLI prints a `(forced removal disables the workflows[]-derived merge gate for: ...)` stderr line on both the `--dry-run --force` and the real `--force` path (`derivedGateReferences`).
- Whole-manifest parse both gates share: `validateBeforeWrite` → `parseManifest` (`src/io/validate-before-write.ts:12-26#"throw"`, `src/schema/index.ts:158-160#"return parseManifestWithWarnings(raw).manifest;"`).
- Fail-closed backstop: if the *original* manifest cannot be parsed (`parseManifestWithWarnings`) when computing the baseline, `baselineKeys` stays empty and **every** proposed asset error counts as new, i.e. on a broken base the asset gate blocks on everything (`src/cli/add/index.ts:117-119#"baselineKeys stays empty"`). In practice `applyAdd`/the schema gate throw first, so this branch is rare.

## What breaks it

The symptom: **"`harness add mcp foo` fails with an error naming a different tool or an unrelated path."** Diagnose by reading the first line of the error:

- `proposed manifest fails schema validation:` → this is the no-baseline whole-manifest gate. The named entry is a **pre-existing** schema problem elsewhere in `harness.yaml` (or one your add just created, e.g. a duplicate name — `tools.mcp.N.name: duplicate mcp entry name: foo` means an entry named `foo` already exists, since `applyAdd` appends rather than replaces; `harness adopt`'s `mcp_replace` path is what replaces in place). Fix or remove the broken entry first; your add is otherwise fine. Same story for `harness remove`.
- `proposed manifest fails asset validation:` → this diagnostic is **new relative to the original file**, so it *is* caused by your call even when the path looks unrelated to what you typed. The live example: `tools.mcp[x].command: path does not exist: /bin/true` from `harness add mcp x`: the bracket key is the tool **name** (`checkMcp`, `src/cli/validate/checks.ts:82#"function checkMcp("`), so `x` is the entry being added; `checkMcp` stat'd the first token of its command on the machine running `harness add` and it wasn't there. A genuinely different-entry asset error can only block as "new" in three ways: the baseline manifest failed to parse (fail-closed backstop above), your add changed an interaction check's outcome (e.g. `checkHookBudgetLedgerMargin` is keyed at `hooks[<name>].budget_ms`, not at any mcp entry, and flips on whether `grounding-mcp` is wired: `harness add mcp grounding-mcp` into a manifest whose `blocking: hard` policy-intercept hook has a small `budget_ms` blocks on that hook's path; and adding a hook can change the outcome of `checkWorkflowGateWiring`, keyed at `workflows`), or the diagnostic's `severity|path|message` key shifted between runs (name-keyed paths make this a non-issue for appends). Policy-pack diagnostics (keyed at `policy_packs[N]...`) can appear in add output only as the pre-existing warning: no supported add mutation (`mcp`/`cli`/`skill`/`hook`, `src/cli/add/mutate.ts:32-36#"entry: HookEntry };"`) touches `manifest.policy_packs`, so those checks' outcome is identical on the baseline and the proposed manifest and can never block as new.
- Pre-existing asset errors do **not** block add — they arrive as a warning telling you to run `harness validate`. If you see the asset-validation *failure*, stop looking for someone else's breakage and check the entry you just added, the `homeDir` in effect, and whether the command's first token is an absolute path that exists here.
- `harness remove` can never fail on asset existence (no asset gate); if remove blocks, it is schema-shaped — most commonly the dangling `policy.hook` reference after removing a hook that policies still name, which `--force` deliberately does not bypass.
