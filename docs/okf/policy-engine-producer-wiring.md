# Policy engine needs its producers wired

## The invariant

A custom `policies:` entry can only be POSITIVELY satisfied if its evidence producer is reachable. The `requires:` evaluator answers "is the ledger evidence present?" by querying the evidence ledger through the grounding-mcp server, and the runtime finds that server by exact name in the manifest: `manifest.tools.mcp.find((m) => m.name === "grounding-mcp")` (`findGroundingMcp`, `src/cli/policy/intercept.ts:125-127`). If no such entry exists, `runInterceptCli` substitutes `degradedLedgerClient("grounding-mcp not declared in manifest")` and every `requires` evaluation degrades. What that MEANS is tier-dependent since task f1aea826: a `warn` policy lands on the never-blocking `warn-degraded`, while a `block`/`require_approval` policy fails CLOSED as `deny-degraded` — so the old allow-everything footgun (policies fire, record, but cannot deny anything) now exists only under the explicit `risk.degraded_fail_posture: fail_open` opt-out. The new footgun points the other way: a manifest with block-tier policies and no grounding-mcp wiring denies every matching event until the producer is wired (the envelope and stderr say so loudly, and a blocking decision on this path gets a "has NO audit row" stderr line instead of a silent no-op). See [gate-fail-posture-matrix.md](gate-fail-posture-matrix.md).

Evaluation order per PreToolUse event (all in `src/runtime/intercept.ts`): `trigger:` and `when:` are ANDed — a policy fires only when `policyMatchesEvent` (event name, `match` tool-name substring with alias expansion, `bash_match` regex) holds AND, when declared, every `when:` clause holds. Since task `ea8becf5` (run 2026-07-27-gate-target-repo-resolution), the `bash_match` regex is no longer tested against the raw command string alone: `policyMatchesEvent` tests it against the raw command first and, only on a raw miss, against a NORMALISED form (`normalizeCommand`, `src/runtime/command-normalize.ts`) with wrapper prefixes peeled (`VAR=value`, `env`/`command`/`nice`/`sudo`/`doas`/`time`/`timeout`/`stdbuf`/`setsid`/`exec`/`nohup`) and a git invocation's own global options collapsed — additive matching only, so a command that matched before still matches via the raw test alone. This closes a silent, zero-audit-signal bypass for `bash_match` triggers whose peeled head token is in the normaliser's closed set — originally only `git` (task `ea8becf5`, e.g. `preflight-before-investigation`), widened to `git`/`gh`/`npm`/`harness` by task `432db3d3` (2026-07-28), which also collapses whitespace runs across the token run for those heads (`gh pr  merge`). Since task `aabbad63`, there is a THIRD arm: only when that normalised form ALSO misses, `policyMatchesEvent` tries a second, independent, ampersand-aware normalisation pass (`normalizeCommandAmpAware`, same file) that additionally treats a bare `&` as a shell boundary — closing the background-job family the primary pass cannot see (`echo hi & nice git status`, `A=x&env -C /tmp git status`) — same additive-only construction, never a replacement for either earlier arm. Two shipped `bash_match` head-token families remain deliberately OUTSIDE the set and stay wrapper-bypassable: `deny-session-env-strip`'s `env`/`unset` (structurally unreachable — the peel loop consumes `env -u <VAR>` while hunting for a gated command behind it) and `deny-pause-sentinel-forgery`'s `tee`/`cp`; both are pinned as explicit not-covered tests, and `tests/runtime/bash-match-head-token-drift.test.ts` fails loudly when a future policy gates a head token the set does not cover. `${REPO}`/`${BRANCH}`/`at_head` (`src/cli/policy/intercept.ts`) no longer stay cwd-only: since task `98ad072f` (shipped 0.44.0), a policy whose `requires:` references any of them is evaluated per REPOSITORY, not once per event. Attribution is UNIVERSAL-ADDITIVE (operator decision D-021), never a replacement: the session's cwd is ALWAYS one of the evaluated contexts, and when a trigger-satisfying segment of the matched command also names — or inherits from a preceding `cd` — a distinct, resolvable git target (`-C`, `env -C`, `--git-dir`), that target's context is evaluated TOO, alongside cwd's, never instead of it — `git -C <B> push` from a checkout of A now demands evidence in BOTH A and B, closing the gap where a `preflight:${REPO}` fact recorded for A used to authorise a command that explicitly read or mutated B. A command whose distinct evaluated contexts for one policy would exceed 4 — cwd always counts as one, so at most 3 foreign targets — fails CLOSED (`MAX_ATTRIBUTED_CONTEXTS`; one synthetic decision naming the ambiguity, zero ledger queries, respecting the policy's own `enforcement:`) rather than evaluating an unbounded number. `resolverGit`/`riskContext` (the Risk Gate's own resolution, further down in `runInterceptCli`) is untouched by any of this — attribution only ever feeds `${REPO}`/`${BRANCH}`/`at_head`. An own-target REPLACE design (attribute to a segment's own target and evaluate ONLY that context) was tried and reverted twice before landing on additive: first during the original `ea8becf5` gate-hardening task (three review rounds, each finding a different regression — Risk Gate declassification, a push-gate fail-open, a non-git verb inheriting a decoy repo's target), then again as `98ad072f`'s own first approach (four MORE adversarial review rounds finding four distinct recurrences of the same class, the fourth triggering this repo's structural-regression-halt convention) — additive-not-replacing is safe by construction instead of by enumerating git's composition knobs, since the cwd demand is never dropped. See `docs/writing-custom-policies.md`'s "Per-policy target resolution" section for the full attribution/fallback rules and `CHANGELOG.md`'s `98ad072f` entry (0.44.0) for the complete four-pass history. `when:` is evaluated by `evaluateWhen` (`src/runtime/when-eval.ts`) against the *enriched* Action Envelope: `enrichEnvelope` runs `buildActionEnvelope` → `classifyRisk(envelope, manifest.risk.classifiers)` → `resolveEnvironment` → `resolveDeletionTarget` (task `d03af8f6`; a purely syntactic, per-segment static resolution of the raw command alone — no `riskContext` consulted, unlike `resolveEnvironment`), so `when.risk.*` / `when.environment.name` / `when.action.reversible` / `when.action.deletion_target_unresolvable` see post-classification values. Enrichment happens only when at least one policy declares `when:` (`riskGateActive`); an unclassified action satisfies `risk.category_in` / `action.reversible` unconditionally ("unknown is not safe", fail-closed, flagged `unclassifiedFallback`) and satisfies `risk.severity_at_least` up through `high` but never `critical` on its own (task `2929c5b7`, 2026-09-01 — see `docs/risk-gate.md`'s "Unclassified actions and the fail-close rule") — `action.deletion_target_unresolvable` is the one clause EXEMPT from that fail-close: it reads `resolveDeletionTarget`'s own verdict, not the Risk Classifier's `classified` state, so an action the resolver does not recognize as a deletion verb at all never falls back to matched=true the way the risk-derived clauses do (see `src/runtime/when-eval.ts`'s own doc comment and `docs/risk-gate.md`'s "Dev-context deletion gate" section). Only after trigger+when does `requires:` — the part needing the producer — decide allow/warn/deny. One exception, added in task 2cc73f55: a policy declaring `operator_only: true` carries NO `requires:` at all and is short-circuited to an unconditional `deny` before the requires pipeline ever runs — no ledger query, no producer, no dependency on grounding-mcp being wired. This is the one way a `policies:` entry can enforce without any evidence producer; see `docs/okf/pause-vs-gate-kill-switch.md` for the primitive's full rationale.

Since task `cf3dff51` (shipped 0.45.0) `policyMatchesEvent` gained a FOURTH matching arm, tried only when the amp-aware pass above also misses: `normalizeCommandQuoteAware`, a quote-tracking boundary finder that skips a shell-boundary character sitting inside an open quote. It closes the class `VAR='a; b' git push origin master`, a shell-boundary character inside a quoted assignment value, additive-only like the two arms before it. All four arms now live in `policyMatchesEvent`, `src/runtime/intercept.ts:538-623`. `harness dry-run`'s own independently-copied matcher (`src/cli/dry-run.ts`) mirrors all four arms as of task `f561e44c`, closing the parity gap this bundle's debug-verb-selection.md tracks.

## Where it's enforced

- **`harness validate` — warning only.** `checkPolicyGroundingMcp` (`src/cli/validate/checks.ts`): if `manifest.policies.length > 0` and no `tools.mcp` entry named `grounding-mcp`, emits a severity `warning` whose message states the tier-split consequence (warn policies degrade non-blocking, block/require_approval policies DENY every matching event until the producer is wired, `risk.degraded_fail_posture: fail_open` as the availability opt-out) and points at this bundle's gate-fail-posture-matrix.md. The exact wording is pinned by the apply test and deliberately not quoted here — quoting message literals in docs is how this bundle went stale twice (review 2026-08-08, rounds 2-3).
- **`harness apply` — hard refusal (since v0.35.0).** `src/cli/apply/apply.ts` runs the same `checkPolicyGroundingMcp` in apply's gate phase and throws `HarnessExitError` (EX_FAIL) telling the operator to wire grounding-mcp under tools.mcp or remove the policies; the code comment carries the tier-aware rationale (validate only WARNS; apply must fail loud so an operator who runs apply without validate cannot ship the misconfigured manifest either way). Documented in `docs/CLI.md` Notes: "Since `v0.35.0`: `harness apply` fails loud (refuses) when the manifest declares `policies:` without `grounding-mcp` wired under `tools.mcp`".
- **Adjacent, stricter check for the consumer pack:** `checkSolutionAcceptanceProducer` (`src/cli/validate/checks.ts:306#"export function checkSolutionAcceptanceProducer("`) makes solution-acceptance-enabled-without-grounding-mcp a validate **error**, because there the failure direction inverts: the producer (`solution_evaluate`) can never write a verdict, so the completion-gate deadlocks on a permanent deny (fail-closed), rather than fail-open.

Name matching is by `name === "grounding-mcp"` only; neither the checks nor `findGroundingMcp` consult `enabled` (`enabled: z.boolean().default(true)` on MCP entries, `src/schema/tools.ts:20`). An `enabled: false` grounding-mcp entry therefore satisfies the apply gate while not being projected into the runtime's `mcpServers` — the agent-side producer verbs (`mcp__grounding-mcp__ledger_add` etc.) are then unavailable even though the gate side can still spawn the server from the manifest command.

## What breaks it

Three distinct failure modes; do not conflate them:

1. **Producer not wired at all.** `apply` refuses since 0.35.0, so on the apply path this can no longer ship. Residual routes to a deployed-but-degraded config: hand-editing `harness.yaml` to remove grounding-mcp *after* hooks are already deployed (`runInterceptCli` loads the manifest fresh on every intercept, and no apply runs to catch it), or relying on `harness validate` alone, which still only warns.
2. **Producer wired but dead at runtime** (binary missing, initialize handshake fails, calls time out). `realLedgerClient` (`src/cli/policy/intercept.ts`) degrades per the documented contract: a degraded/failed query degrades the policy's evaluation — `warn-degraded` (non-blocking) for `warn` tier, `deny-degraded` (blocking) for `block`/`require_approval` since task f1aea826 — and the first degraded summary is deliberately cached so all K policies degrade together instead of retrying per policy. Fail direction differs per gate; see [gate-fail-posture-matrix.md](gate-fail-posture-matrix.md) (e.g. solution-acceptance's dead producer means permanent deny, not fail-open).
3. **Producer wired and alive, but enforcement drowns under load (fixed in 0.39.0).** Before 0.39.0, `harness policy intercept` spawned grounding-mcp subprocesses sequentially — two per matching policy (query + audit record) — which under load approached the 30s hook budget; a hook timeout is conventionally fail-open, "so enforcement silently stopped exactly when contention was highest" (CHANGELOG [0.39.0], task a2589fa3). Since 0.39.0 `openLedgerSession` (`src/policies/ledger-client.ts:499`) lazily spawns ONE subprocess per intercept invocation, does the initialize handshake once, and multiplexes every `ledger_summary`/`ledger_add` over the same stdio pipe; a per-session summary cache collapses the K textually-identical per-policy queries into one round-trip, and a session-level timeout latch short-circuits all calls after the first timeout, bounding worst-case ledger time at ~1×timeoutMs (default 5000ms; the resolution chain `opts.ledgerTimeoutMs ?? server.health?.timeout_ms ?? 5_000` lives at the call site, `src/cli/policy/intercept.ts:387`). Decision semantics unchanged by the pooling itself: serial evaluation, first blocking decision in manifest order owns the deny envelope. (Since task f1aea826 a degraded evaluation blocks for `block`/`require_approval` tier as `deny-degraded`; `warn-degraded` — the warn-tier and opt-out mapping — still never blocks.)

Also remember (tripwire 3, `docs/writing-custom-policies.md`): the producer being wired is necessary but not sufficient — a custom policy additionally needs its own hand-written `hooks:` entry with `command: harness policy intercept`; `harness init` auto-generates hook wiring only for its named builtin patterns.

## Version history that matters

- **< 0.35.0:** the misconfig deployed silently. `checkPolicyGroundingMcp` existed only in `validate` (a warning); `apply` succeeded and every policy warn-degraded at runtime. Any doc, comment, or memory describing "apply succeeds and policies silently degrade" describes this era only.
- **0.35.0 (2026-06-14):** `harness apply` fails loud on `policies:` without grounding-mcp (task 09120efb, discovery H3, PR #288). CHANGELOG operator action: "wire grounding-mcp or remove the policies."
- **0.39.0 (2026-07-02):** PreToolUse gate pools one grounding-mcp session per intercept, replacing the K sequential spawn pairs and closing the hook-timeout fail-open under load (task a2589fa3, harness-review-2026-07-01). Same release wires `grounding.evidence_ledger.path` → projected as `EVIDENCE_LEDGER_DB` env on the grounding-mcp entry (task 129e1b94), so a wrong path there is now a live way to point the producer at the wrong ledger; and `validate` gains `checkPolicySelfAttestation`, warning on `block` policies that declare no `producers:` at all (task 43b107f2).
- **0.43.0 (2026-08-01):** `bash_match` policy triggers gain a normalised second matching arm (raw-OR-normalised, strictly additive), closing the wrapper-bypass class where `env -C <repo> git status`, `nice git push`, or a doubled space defeated the raw regex with zero audit signal — no ledger query, no decision, no `harness audit` row (task `ea8becf5`; widened from `git`-only to the closed set `git`/`gh`/`npm`/`harness` by task `432db3d3`; a quoted-assignment-value bypass on both arms closed by task `13e55484`). Separately, the shipped policy templates' own trigger regexes gain bare `&` in their boundary alternation (task `d834a065`): the alphabet knew `&&` but not single `&`, which had defeated every `bash_match` gate including an operator-only deny — template-level only, and an existing `full` install picks it up only after re-running `harness init --template full --force`. `${REPO}`/`${BRANCH}` explicitly stayed cwd-only in this release — a per-command target-directory resolution was built, reviewed, and reverted after three review rounds each found a different security regression (Risk Gate declassification, a push-gate fail-open, a non-git verb inheriting a decoy repo's target); see the 0.44.0 entry below for the follow-up that shipped it correctly.
- **0.44.0 (2026-08-03):** two changes land on top of 0.43.0's trigger-matching engine. (1) A THIRD, independent matching arm: `normalizeCommandAmpAware`, tried only when both the raw command and the primary normalised form miss, closes the bare-`&` background-job bypass family (`echo hi & nice git status`, `A=x&env -C /tmp git status`) (task `aabbad63`). Widening the primary normaliser's own boundary alphabet instead had been tried during 0.43.0, measured to regress 140/140 sampled quoted-assignment spellings, and reverted (task `d834a065`); the separate third arm gets the same coverage without touching the primary pass. (2) `${REPO}`/`${BRANCH}`/`at_head` stop being cwd-only: a policy referencing any of them is now evaluated per REPOSITORY, universal-additive, cwd is always demanded, and each distinct attributed target adds its own demand alongside it, never instead of it, capped at 4 distinct contexts per policy per event (task `98ad072f`, operator decision D-021, see "The invariant" above for the full account). Also this release: post-merge-gate blocker precedence reversed so `deny` wins over the escape allowlist (task `19356be7`), and the same bare-`&` boundary fix extends to the post-merge-gate and solution-acceptance policy packs' own regexes (task `76671e5a`), both are separate, freestanding matchers from the `policyMatchesEvent` engine this doc otherwise describes, named here only because they touch adjacent bash-matching surfaces in the same release.
- **0.45.0 (2026-08-19):** two more changes land, both already reflected in "The invariant" and the fourth-arm paragraph above. (1) The `degraded_fail_posture` semantic change (task `f1aea826`): `evaluateOnePolicy`'s degraded family now routes through a tier-aware outcome, `warn` policies keep the non-blocking `warn-degraded`, `block`/`require_approval` policies now produce the blocking `deny-degraded`, an accepted semantic change from the pre-0.45 availability-first mapping; the explicit opt-out `risk.degraded_fail_posture: fail_open` (schema default `preserve_enforcement`, `src/schema/risk.ts`) restores the old mapping for every tier. `checkPolicyGroundingMcp`'s warning wording is now tier-aware to match. (2) The FOURTH `bash_match` matching arm, `normalizeCommandQuoteAware` (task `cf3dff51`), described above. Consult `CHANGELOG.md` directly for anything shipped after 0.45.0 not named in this bundle.
