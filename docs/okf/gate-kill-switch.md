# Kill switch: `harness gate disable` / `harness gate enable`

harness ships ONE operator kill switch: `harness gate disable` takes the hook groups or hook units whose matcher matches a substring out of the live runtime config with a reversible snapshot, and `harness gate enable` puts them back. `harness pause` and `harness resume` were removed in 1.0.0 (task 973163a4), and the gate verbs are their replacement: both are `REMOVED_COMMANDS` entries now, so a hook or `ux.run` line that still calls one is reported by validate, doctor and apply (`src/schema/removed-keys.ts:568-569#"the operator pause is removed"`).

## When to use this

- Lockout recovery: a hard-blocking hook refuses the calls you would use to recover.
- "Is this harness or my code?" debugging: switch one hook off, reproduce, enable it again.
- A deliberate edit on a protected branch (a hotfix on `master`): branch-protection is the shipped gate this is for.
- One specific hook group must be off for a while and you want the file state back afterwards.

To turn a shipped gate off permanently use NEITHER verb: set `policy_packs[].enabled: false` on the pack (`src/schema/policy-packs.ts:24#"enabled: z.boolean().default(true),"`) or remove the hook entry from the manifest, then re-run `harness apply`. Persistent, diff-able, source-controlled.

## Guardrail note

The gate is the "operator escape hatch for hard-blocking hooks" (`src/cli/register-gate-gc-group.ts:41-41#"operator escape hatch for hard-blocking hooks"`), but nothing enforces that in the CLI: `GateDisableOptions` is only `settingsPath | homeDir | matcher | now` (`src/cli/gate/disable.ts:61-79#"now?: Date"`), with no agent-session env-var or TTY refusal. An agent with Bash access can run the verb; the snapshot plus `.bak` file are the recovery record either way.

## Claude Code: settings.json surgery

Flags: `harness gate disable [--matcher <pattern>] [--settings <path>] [--runtime claude|codex]`, default runtime `claude`; `--config` belongs to `--runtime codex` and is refused here (`src/cli/register-gate-gc-group.ts:28-28#"only applies to --runtime codex; use --settings"`). The verb reads `~/.claude/settings.json` (`DEFAULT_SETTINGS_REL`, `src/cli/gate/disable.ts:59-59#"DEFAULT_SETTINGS_REL"`) and removes the hook groups whose `matcher` contains the pattern, a literal substring and not a regex (`m.includes(pattern)`, `src/cli/gate/disable.ts:210-219#"m.includes(pattern)"`). With no `--matcher` it is a pure listing of the candidate groups and writes nothing (`src/cli/gate/disable.ts:22-22#"pure listing"`); a `--matcher` that matches nothing errors and points at that listing (`src/cli/gate/disable.ts:309-311#"no hook groups matched"`). A settings file that is not a JSON object refuses the operation rather than being "fixed" (`src/cli/gate/disable.ts:148-149#"restore from a backup"`).

What it writes, in order: a backup of the original to `<settings.json>.bak.<ISO>`, a snapshot of the removed groups to `<settings-dir>/harness.gate-disable.<ISO>.json` (ISO stamps use `-` for `:`, `src/cli/gate/snapshot.ts:116-119#"bak."`), then the atomic rewrite of settings.json; the backup lands before any mutation and the snapshot before the live rewrite, so a crash between the writes never leaves settings.json mutated without its way back (`src/cli/gate/disable.ts:355-429#"atomicWriteFile(entry, newSettings);"`). The snapshot records the settings file and the backup as absolute paths; a relative `--settings` is resolved against the working directory at disable time. A `settings.json` that is itself a symlink (a dotfiles setup) is written through, not replaced: the backup, the snapshot and the rewrite all go to the file the link leads to, so the link stays a link and the snapshot records that file's path and name, whichever spelling the disable was run through (`src/cli/gate/snapshot.ts:382-388#"export function resolveSettingsEntry"`). The same holds for the default `~/.claude/settings.json`. The backup and the snapshot therefore sit beside the file the link leads to; in a dotfiles repository they show up in its working tree, so ignore `harness.gate-disable.*` and `*.bak.*` there. When the directory of that file cannot be written (a read-only checkout), the verbs leave the settings file unchanged, exit non-zero and say that the link leads into a directory that refuses writes, naming it (`EACCES` or `EROFS`; `EPERM`, which a protected file raises as well as its directory, names the file or the directory without saying which) (`src/cli/gate/snapshot.ts:480-487#"export function readOnlyLinkTargetText"`). A disable names making the directory writable, then the disable again. It adds a copy of the file in place of the link (`cp <file> <link>.copy && mv <link>.copy <link>`, printed with quoted paths) only when the link sits in another directory than the file and no live snapshot sits beside the file: an enable through the copy looks only beside the copy, so it would report nothing to restore while the groups those snapshots removed are still missing. With such snapshots it names them instead and says to make the directory writable and run `harness gate enable --settings <link>` first, which restores them, before the link is replaced (`src/cli/gate/disable.ts:250-280#"function readOnlyTargetError"`). An enable says that making the directory writable and rerunning it is the way, or by hand putting the groups back from the snapshot and moving the snapshot aside once the directory can be written, because a copy in place of the link would not find the snapshot beside the file (`src/cli/gate/enable.ts:268-275#"once you can write its directory"`). When the refusal comes after this call wrote its own snapshot (a protected file, or a link into another directory whose file refuses the write), the message says that an enable, or this disable run again, through the settings file retires that snapshot; it names groups the file still holds, so the enable restores nothing and retires it as already restored (`src/cli/gate/disable.ts:459-459#"which an enable or this disable run again through"`). That snapshot is not one of the live snapshots beside the file the copy-over sentence above counts, but the copy is offered only after the enable through the link (or after the snapshot is moved aside): once the link is a copy, an enable through it looks only beside the copy and would leave the snapshot live beside the original file (`src/cli/gate/disable.ts:272-276#"written !== undefined"`). A read-only directory under a plain path (no link) fails with the plain error.

One live snapshot per settings file. Snapshots always sit beside their file and record its path, and only the basename counts, never how the directory was spelled (relative to another working directory, through a symlink). A snapshot belongs to the settings file when the file names the directory entry that basename names: the same spelling, or, on a filesystem that folds letter case or normalization (APFS by default), another spelling that `lstat` resolves to the same regular file with a link count of 1 (`Settings.json` for `settings.json`), so no second name of that inode could be the one that matched (`src/cli/gate/snapshot.ts:326-352#"function namesSameEntry"`). Every other name is another entry: a hard link to the settings file under another name, the file under its old name, or a snapshot found beside the file a symlink leads to but recorded under another name than that file's (the symlink's own name, say). Restoring through such a name would write a new file at that name (the atomic write renames a temp file into place, which detaches a hard link) and leave the recorded file as the disable left it, so a snapshot recorded for one is foreign to the other, with or without `--force`. A live snapshot for another entry in the same directory (say `settings.local.json`, or such an alias) is not read as this one's and not merged into; `gate enable` exits non-zero while one is live, writes nothing, and names each with the command that restores it, `harness gate enable --settings <dir>/<recorded name>`; when no file is at that name now it adds the rename-back step, the `.bak.<ISO>` file to restore it from if it is gone (the file before that disable; the named command then retires the snapshot) and the move-aside step (`src/cli/register-gate-gc-group.ts:339-360#"function foreignSnapshotsNote"`). It never prints "nothing to restore" then. A `--settings` that is itself a symlink is not another entry: the verbs follow it to the file it leads to (a chain, and a link whose file is gone, included) and look for snapshots beside the given path and beside that file, owning them by the file's name there (`src/cli/gate/snapshot.ts:412-453#"export function listLiveSnapshots"`). The chain is walked hop by hop, by the one walker the Codex gate uses as well, the way the kernel walks it: a relative link text is appended as written to the physical directory of the link that holds it, an absolute one is taken as written, and everything but the last name is resolved through the real directories, so a `..` (after a directory link, a `.` or an empty segment, in a relative or an absolute text) climbs out of the directory a name leads to, never out of the one a lexical reading of the text names; a text that passes through a directory that is gone ends the chain there, at the text as written, never at a guess (`src/cli/gate/link-chain.ts:57-57#"export function walkLinkChain"`). A loop is left as the path was given. A `--settings` spelled with `..` is taken through the directory the kernel reaches as well, so the backup and the snapshot land beside the file, not in a directory a lexical reading of the spelling names (`src/cli/gate/snapshot.ts:363-374#"export function settingsOwnEntry"`). A disable through the file's own path is therefore restored by an enable through a link to it in another directory, and the other way round, and the restore writes the file, not the link. When the file behind the link is gone, enable exits non-zero saying so and naming the `.bak.<ISO>` file to restore it from, never "nothing to restore" (`src/cli/gate/enable.ts:190-192#"stays live. Restore the file from"`).

A removed group counts as back only when the file holds an unchanged copy of it. The snapshot's groups are paired with the file's one to one: first every group with a deep-equal group of the same event (key order does not matter), then each group left over with a group that has its event and matcher but other content (`src/cli/gate/snapshot.ts:629-641#"canonicalJson(g) === wanted"`). Such a "same matcher, other content" group may be the gate's group re-rendered, or another hook that shares the matcher (a formatter guard on `Write|Edit`, say), so the gate never takes it for the removed one on its own: plain `gate enable` and `gate disable` refuse and name its event and matcher and the commands of both groups, and only `gate enable --force` accepts it as back.

A second disable while a snapshot is live looks at the live snapshots newest first (`src/cli/gate/disable.ts:526-577#"function chooseSnapshot"`):

- The file is exactly the state that snapshot left (its post-disable sha): the call writes its own backup, merges the groups it removed into the snapshot and rewrites settings.json. The merge keeps the original pre-disable sha, backup and filter, moves the post-disable sha to the new state, tags every group with the step that removed it (`step`, 0 for the first disable, 1 for the next) and appends a `merges` entry with that call's matcher and backup (`src/cli/gate/disable.ts:395-403#"merges: ["`). A group's recorded `index` is its position in the array just before its own step, so restore undoes the steps newest first, and inside a step by event and ascending index (`src/cli/gate/snapshot.ts:642-648#"if (stepA !== stepB) return stepB - stepA;"`). When the live snapshot was found beside a settings path that is a symlink to a file in another directory, the merged snapshot is written beside that file with the file's path recorded, and the old one is renamed to `*.superseded.json` once the settings write succeeded (kept for audit, never offered again; renamed as restored it would read as applied), so an enable through the file's own path finds it (`src/cli/gate/disable.ts:467-479#"supersedeSnapshot(target.path)"`). If the settings write fails after the merged snapshot was written, the snapshot is put back to its body from before the merge and the error is reported; when that rollback fails too, both errors are reported with the way out, `harness gate enable` (it leaves a group the file still holds unchanged alone) and then the disable again (`src/cli/gate/disable.ts:440-448#"could not be put back"`).
- The snapshot is spent, that is `gate enable` would only retire it: the file holds every group it names unchanged, which includes being back at the pre-disable state (put back by hand, restored from the `.bak.<ISO>` file, a snapshot left live by an older release's enable). Disable retires it the way enable does, prints a `retired a spent snapshot as ...` line, and looks at the next older one or starts a fresh snapshot (`src/cli/gate/disable.ts:537-540#"plan.restored.length === 0 && plan.changed.length === 0"`).
- Otherwise the file was edited since and some group the snapshot removed is still missing, or is there only with other content. Disable refuses, names the snapshot, the missing groups with their commands and the differing ones with both groups' commands, and says to run `harness gate enable --force`, then the disable again; when a group is there only with other content, it names the other way too, for the case that the file's group is another hook: make the file hold the snapshot's group (the `.bak.<ISO>` file it names has it), run `harness gate enable`, then the disable again. It writes no backup and changes no snapshot; the only thing it does first is retire the spent newer snapshots it walked past (an older release's leftovers), so that way out stays two commands (`src/cli/gate/disable.ts:541-575#"harness gate enable --force"`).

A live snapshot that cannot be read, or that records no target (its `settingsPath` is missing, empty, or ends in `.` or `..`, so no file name can be told: `src/cli/gate/snapshot.ts:188-192#"function hasRecordedTarget"`), makes disable and enable refuse before they write anything, because its target cannot be told; the message says which, names the file, and says to move it aside (rename it to `*.restored.json` once its groups are back; if it names groups that are still removed, put them back by hand first, the `settingsBackupPath` inside it is the file before the disable). Enable prints the command to run afterwards with the call's own `--settings` (`src/cli/gate/disable.ts:327-333#"cannot be read would be left out"`, `src/cli/gate/enable.ts:171-175#"Move ${found.path} aside"`). A retire the filesystem refuses (the rename to `*.restored.json`) fails the same way, naming the snapshot to move out of the directory by hand instead of a bare errno (`src/cli/gate/disable.ts:498-510#"function retireSpent"`, `src/cli/gate/enable.ts:300-304#"cannot retire the snapshot"`). Snapshots are version 2 now; a version 1 snapshot written by an earlier release is still read (`src/cli/gate/snapshot.ts:32-32#"LEGACY_SNAPSHOT_VERSION"`) and upgraded to version 2 when a disable merges into it.

Restore: `harness gate enable [--settings <path>] [--force]` applies the one live snapshot for this settings file and then retires it, renaming it to `harness.gate-disable.<ISO>.restored.json`, which stays on disk for audit and is never applied again (`retireSnapshot`, `src/cli/gate/snapshot.ts:266-271#"retireSnapshot"`). The live snapshots are the `harness.gate-disable.*.json` files beside the settings file that are not `*.restored.json` and belong to this settings file, newest `createdAt` first. What happens depends on the state of the file (`src/cli/gate/enable.ts:164-288#"export function gateEnable"`):

- It matches the snapshot's post-disable sha (nothing touched it since): every removed group goes back at its recorded position and the snapshot is retired. The result has the content the file had before the first disable. It is byte-identical only when that file was newline-terminated 2-space JSON with sorted events and no disable emptied an event or the whole `hooks` block; otherwise the indentation or key order can differ, and the snapshot's `.bak.<ISO>` file is the byte-exact original.
- It already matches the pre-disable sha (you restored it by hand): nothing is written, the snapshot is retired, exit 0 (`src/cli/gate/enable.ts:197-207#"already-restored"`).
- It holds a group with the event and matcher of a removed one but other content: enable refuses, names both groups' commands and any group still missing with its commands, and says to run `--force` if the file's group stands in for the snapshot's, or to make the file hold the snapshot's group (the `.bak.<ISO>` file has it) and run enable again (`src/cli/gate/enable.ts:215-230#"does not count as back"`).
- It holds every group the snapshot names unchanged although it was edited since: nothing is written and the snapshot is retired, exit 0 (`src/cli/gate/enable.ts:232-242#"plan.restored.length === 0"`).
- It matches neither state and some group is still missing: the missing groups are put back, and only when that gives exactly the pre-disable file (what a crash between the snapshot write and the settings write leaves behind) enable writes it. Anything else is an edit of yours, so enable refuses, names the missing groups with their commands, the snapshot and the `.bak.<ISO>` file to diff against, and says to run `--force` (`src/cli/gate/enable.ts:251-260#"harness gate enable --force"`).

`--force` is total: it puts back every group still missing, leaves a group the file holds unchanged alone, takes a group with the same event and matcher but other content as back (it is not put back) and prints the commands of both, keeps every other edit, and retires the snapshot, so a second `--force` finds nothing to apply and a group is never added twice (`src/cli/register-gate-gc-group.ts:200-205#"taken as back under --force"`). When nothing had to be written, the header says so without claiming the file holds every removed group: "nothing to put back ... there unchanged or taken as back under --force". Read the taken-as-back line before you rely on the gate again: when the file's group is not the gate's (a different command), the gate's group is still out of the file.

Exit 0 means no live snapshot remains beside the settings file, neither for it nor for another settings file in that directory, and every group those snapshots named is back unchanged, or was taken as back under `--force`. Releases before this change wrote one snapshot per disable and never retired them. When several are live, each enable handles the newest one, retires it and exits non-zero naming how many live snapshots remain (`src/cli/register-gate-gc-group.ts:237-244#"are still live next to"`); run the `harness gate enable` the message prints (it carries the call's `--settings`) again until it exits 0. Confirm with `harness gate disable` (list) that the group is back. `harness doctor`'s warning for a hook such a snapshot took out follows the same rule: it asks which snapshot a plain enable applies next and lets only that one (the newest, `nextEnableSnapshots`, `src/cli/gate/snapshot.ts:719-720#"return live.slice(0, 1);"`, which `gate enable` uses for its own pick) decide whether the warning names `--force`, so an older snapshot that would refuse against the current file never names the flag while the plain command restores from the newest, and when the newest refuses every gate-disabled hook names it, whichever snapshot removed it, because the plain command refuses for all of them.

## Codex: the harness-managed hook block

Flags: `harness gate disable --runtime codex [--matcher <pattern>] [--config <path>]` and `harness gate enable --runtime codex [--config <path>] [--force]` (task 1f6ec6c9). The default target is `~/.codex/config.toml` (`src/cli/apply/install-codex-config.ts:203-205#"config.toml"`); the verbs edit only the `# BEGIN harness-managed codex hooks` block that `harness apply --runtime codex --install` writes, and text outside the fences is never touched. A block the verbs cannot read without guessing refuses instead: a duplicate or moved BEGIN marker, or a foreign table inside the block (`src/cli/apply/install-codex-config.ts:45-47#"a duplicate/moved BEGIN marker, or a foreign table wedged"`). The config path is resolved the way the kernel reads it, by the one link walker the Claude gate uses (`src/cli/gate/link-chain.ts:57-57#"export function walkLinkChain"`): a `--config` that is a symlink is edited at the file its chain leads to, and a `..` in a link text after a directory link climbs out of the directory that link leads to, never out of the one a lexical reading names. A `--config` (and the installer's `--codex-config`, which `harness apply` hands over with its `..` unfolded, a leading `~` expanded by concatenation so it does not fold either) spelled with `..` after a directory link is taken through the directory the kernel reaches, so the backup and the snapshot sit beside the entry the spelling names, in the directory the kernel reaches (`src/cli/gate/link-chain.ts:130-130#"export function kernelEntry"`, `src/cli/gate/codex-snapshot.ts:163-163#"function absoluteEntry"`). A link the kernel resolves is never refused as unresolvable. A link whose chain ends at a file that is gone refuses naming that end, a link the kernel itself cannot read refuses with the kernel's cause, and a chain whose walk and the kernel's own lookup reach different files refuses too (a defence-in-depth check against the two disagreeing), so the installer never writes a file Codex does not read; each refusal writes nothing (`src/cli/apply/install-codex-config.ts:1766-1766#"export function resolveConfigSymlink"`). A config directory that does not exist yet, spelled with `..` after a directory link, is created where the kernel reaches it and the entry is resolved again once it exists, so the file is written there and not into a lexical fold of the spelling (`src/cli/apply/install-codex-config.ts:2419-2419#"configPath: kernelEntry(planned.configPath)"`). The default targets are the opposite case: `~/.codex/config.toml` and `~/.claude/settings.json` are joined onto the home directory lexically, so a home spelled with `..` after a directory link names the file Codex and Claude Code read for that spelling, never the one beside the link target (`src/cli/apply/install-codex-config.ts:203-205#"config.toml"`, `src/cli/gate/disable.ts:121-121#"path.join(home, DEFAULT_SETTINGS_REL)"`, `src/cli/gate/enable.ts:116-116#"path.join(home, DEFAULT_SETTINGS_REL)"`); `tests/cli/gate/default-paths-lexical.test.ts` pins it.

Disable does not delete a unit: the comment line, the `[[hooks.<Event>]]` header and the `matcher` line stay and the unit's `hooks = [...]` line becomes `hooks = []` (`CODEX_NEUTRALISED_HOOKS`, `src/cli/gate/codex-snapshot.ts:46#"CODEX_NEUTRALISED_HOOKS"`). Codex keys a user hook's trust and enabled state by the hook's position inside its event's array, and an empty group takes that position without registering a handler, so every other hook of every event keeps its position and its trust (`src/cli/gate/codex-snapshot.ts:6-7#"keys a user hook's trust and enabled state by its position in the"`). The matcher rule is the same literal substring as on Claude. The listing marks a unit an earlier disable already neutralised with `[disabled]`, and disable refuses to neutralise an already-disabled unit twice. A backup `<config>.bak.<ISO>` and a snapshot `harness.gate-disable-codex.<ISO>.json` land beside the config under its own file prefix (`src/cli/gate/codex-snapshot.ts:37#"CODEX_SNAPSHOT_BASENAME_PREFIX"`) with the config's own file mode, before the rewrite. The snapshot carries `version: 3` and `target: "codex"`, so a Claude settings snapshot is never restored into the Codex config and a Codex snapshot is never read as a settings.json one (`src/cli/gate/codex-snapshot.ts:14-17#"can never be restored"`).

At most one snapshot per config is live. A second `gate disable` while one exists backs the file up as usual and then merges the newly neutralised units into that snapshot, keeping the original pre-disable sha, recording the new post-disable sha and adding an audit entry (time, matcher, backup) to the snapshot's `merges` list (`src/cli/gate/codex-disable.ts:208-213#"merges: ["`). The backup and the merged snapshot are written before the config, so the config is never changed without both on disk; if the config write then fails, the snapshot is put back to its pre-merge body, so it never names units that are still enabled (`src/cli/gate/codex-disable.ts:240-250#"atomicWriteFile(configPath, next, { mode });"`). It can only join when the config is exactly what that snapshot left behind. A live snapshot that `gate enable` would only retire without writing is spent: an install re-rendered the block after it was taken, the config is back at the pre-disable state, or every unit it names is enabled again and still in the block. Disable retires a spent snapshot itself (the same `*.restored.json` / `*.superseded.json` rename) and starts a fresh one, with no enable in between (`src/cli/gate/codex-snapshot.ts:320-335#"export function spentCodexSnapshot"`, `src/cli/gate/codex-disable.ts:166-173#"spentCodexSnapshot("`); when that rename fails (the retired name is taken), both verbs refuse with what they have done so far, the file and the move-aside step (`src/cli/gate/codex-snapshot.ts:216-230#"cannot retire the snapshot"`). Any other live snapshot the config no longer matches refuses the disable and writes nothing. That refusal names `harness gate enable --runtime codex --force` when a forced restore would put the units back, and otherwise, when a unit the snapshot names is missing from the block or changed while still disabled, the ways out of that snapshot instead of `--force` (`src/cli/gate/codex-disable.ts:183-187#"cannot join it"`). Every command a Codex message prints repeats the config the call named, shell-quoted, and a call that used the default path prints the bare commands: the gate's own messages repeat `--config`, and `harness apply --runtime codex --install` gets `--codex-config` in them. That includes the refusal for a version 2 snapshot (`src/cli/gate/codex-snapshot.ts:521-521#"to rewrite the block, or restore the config"`) and the installer refusals the gate passes on, which carry the flag once, where the call's path is known (`toGateError`, `src/cli/gate/codex-snapshot.ts:149-149#"export function toGateError("`); `harness apply --install` does the same for its own refusals (`src/cli/apply/install-codex-config.ts:2143-2143#"nameInstallConfig(err.message"`), and so do the install warning for an unreadable snapshot, which names `harness gate enable --runtime codex` (`src/cli/apply/install-codex-config.ts:2450-2450#"will refuse on it"`), `harness doctor`'s install hint when a caller hands it a config other than the default, which only the doctor API can do today since the CLI compares the default config alone (`src/cli/doctor/hook-liveness.ts:410-410#"const fixHint"`) and the next-steps hint of `harness apply --runtime codex` without `--install` (`src/cli/apply/next-steps.ts:113-122#"codexInstallTarget"`). A live snapshot that cannot be read refuses the disable too, rather than starting a second one, and the message names the file and says to move it aside (`src/cli/gate/codex-snapshot.ts:424-428#"move ${snapPath} aside"`).

Enable reads the one live snapshot taken for that config. Ownership is decided the way the Claude gate decides it: snapshots sit beside their config and record its path, only the basename counts, and a snapshot is the config's own when the requested path names the directory entry that basename names, i.e. the same spelling or, on a filesystem that folds letter case or normalization (APFS by default), another spelling that `lstat` resolves to the same entry with a link count of 1 (`Config.toml` for `config.toml`; a symlinked config is one entry too, since the gate edits it at its target) (`src/cli/gate/codex-snapshot.ts:432#"namesSameEntry(dir, recordedName, targetName, { symlinks: true })"`). A snapshot recorded for any other name is another config's, a hard link or a second name of the config included, since a link count above 1 means no spelling can be proven to be the one that matched: it is skipped, never restored through the wrong name, and named with the command that restores it, `harness gate enable --runtime codex --config <dir>/<recorded name>` (the path is shell-quoted when it holds a space, a quote or another character a shell reads, so the printed command runs against the file it names), plus, when no file is at that name now, the rename-back step, the `<config>.bak.<ISO>` file to restore it from and the move-aside step (`src/cli/gate/codex-snapshot.ts:391#"export function foreignCodexExit"`). Enable follows the Claude exit rule: it exits non-zero while any live snapshot of another config sits beside the config, even when no unit of this config is disabled, and names each one with its `--config`, so a `--config` mistyped within the config's directory or a hard-link alias that parted from the config never ends in a quiet exit 0; exit 0 means no live snapshot remains beside the config. When units stay disabled too, the error carries those commands first and keeps the backup and the re-install as an otherwise, except when this call retired a snapshot of this config as superseded by a later install (dated by the installer's backup or by the generation marker): then the stale backup is not offered and the ways out are the enable through the other spelling of the config, the re-install and the `hooks` lines put back by hand (`src/cli/register-gate-gc-group.ts:256#"retired.installBackup !== undefined"`). Enable looks for snapshots only beside the path it is given, never beside another link to the same file: through a second link to the config in another directory it finds none and says no snapshot restores the units, then tells you to run enable with the same `--config` the disable used (`src/cli/register-gate-gc-group.ts:294#"run enable with that same"`). If the config matches its post-disable sha, each unit gets its original `hooks = [...]` line back, the result must hash to the recorded pre-disable sha (byte-identical restore), and the snapshot is renamed to `*.restored.json` (kept for audit, never offered again). A config that already matches the pre-disable sha writes nothing, retires the snapshot and exits 0. A snapshot taken before a later `harness apply --runtime codex --install`, or whose units are all enabled again and still in the block, is renamed to `*.superseded.json` instead and never applied. The installer retires the snapshot at the source: `harness apply --runtime codex --install` renames every live snapshot of the config it just rewrote to `*.superseded.json`, whatever backup files exist, looking beside the config and, for a symlinked config, beside every hop of the chain of links from the path it was given to the target and beside the target (`src/cli/gate/link-chain.ts:115-115#"export function linkChain"`), reading a directory once when it is reached under two spellings (a symlinked directory), and matching a snapshot by the file its recorded path names (same path, or the same device and inode, so a link or a hard link counts) (`src/cli/apply/install-codex-config.ts:2408-2408#"export function writeCodexConfigInstall("`). A rename that fails never fails the install, which is already on disk: `apply` prints a warning on stderr (and carries it as `snapshotWarnings` in `--json`) naming the snapshot and the step to move it out of the directory by hand, and leaves it live; a live snapshot the install cannot read is left alone and named the same way. The snapshots that install cannot find are the ones beside a link above the path it was run through (an install run on the target's own path, or on an intermediate link, is not told which links lead to it) and the ones beside a second link to the config that is on no chain the install walks. The block's generation marker dates them: the installer writes one comment line, `# harness block generation: <sha256>`, directly under the BEGIN fence, holding the hash of the content it renders (`src/cli/apply/install-codex-config.ts:35#"CODEX_BLOCK_GENERATION_PREFIX"`, `src/cli/apply/install-codex-config.ts:1492#"codexBlockGeneration(rendered)"`), and `gate disable` records the block's marker in its snapshot as `blockGeneration` (`src/cli/gate/codex-disable.ts:227#"blockGeneration: block.generation"`). The line is a TOML comment, so it adds, removes and moves no hook entry and positional trust is untouched, and the same content renders the same line, so an install of an unchanged manifest still writes nothing (the first install after upgrading rewrites the block once to add it). A snapshot whose recorded marker differs from the one the block carries now was taken from a block a later install re-rendered: enable and disable retire it as `*.superseded.json` and never apply it, with or without `--force`, whatever link it sits beside and whether any backup file still exists, and the retirement line names both markers; a disable then starts a fresh snapshot instead of joining it (`src/cli/gate/codex-snapshot.ts:349#"recorded !== blockGeneration"`, `src/cli/register-gate-gc-group.ts:327#"its generation marker is now"`). Only the exact line right under BEGIN counts (`src/cli/apply/install-codex-config.ts:2554#"BLOCK_GENERATION_LINE_RE.exec(lineAt(pos))"`), and a marker dates a snapshot only when both the snapshot and the block carry one. Enable keeps a second line of defence, which runs first for every snapshot and is the only one for a snapshot without a marker (written before the marker existed) or a block without one (written by an older installer, or with the line removed or edited by hand): it dates the install by the installer's `<config>.harness-backup-*` files, which sit beside the path the install ran through, and looks for them beside the path it is given, beside every hop of that path's link chain and beside the target (`src/cli/gate/codex-snapshot.ts:313#"export function latestInstall"`). A backup spelled in another letter case counts when both spellings are one entry (`src/cli/apply/install-codex-config.ts:2289-2289#".harness-backup-"`). A snapshot older than the newest install it finds is retired as superseded and never applied. A marker line removed or edited into another shape never locks a legitimate enable out: the config no longer hashes to the snapshot's post-disable state, so it counts as edited, enable names `--force`, and `--force` restores the units as for any other edit. A marker edited into another well-formed hash reads as a re-install: the snapshot is retired, the unit stays off and enable names it, and the ways out it names are the enable through the other spelling of the config, a re-install and the `hooks` line copied back from the retired snapshot file, which keeps it, exactly as for the retirement recipe below (the backup the gate wrote is no longer offered there either, though here no install has run and it holds the current lines). A `blockGeneration` that is not a marker (64 lowercase hex) makes the snapshot unreadable, with the move-aside refusal below (`src/cli/gate/codex-snapshot.ts:569#"GENERATION_RE.test(generation)"`). Residual: a snapshot without a marker is still dated by the backup files alone, so beside a second link on neither chain (whose install backups enable cannot see), or once those files are deleted or moved, only the checks on the config's content stand between it and an outdated hooks line; the same holds after an install by an older installer, which writes no marker. The outdated line can come back only when a unit the snapshot names is neutralised again after the install (by a disable run through another spelling, or by hand) and either the file then equals the snapshot's post-disable state or `--force` is given. Run disable and enable through the same `--config` spelling to keep that residual shut. A config that matches neither state (edited since, or left half-merged by a crash) gets a planned restore that skips every unit that is back already, present once and not neutralised whatever its event or matcher now, so its line is never overwritten, and puts back the rest, found by id (`src/cli/gate/codex-snapshot.ts:253-261#"export function planCodexRestore("`). Before any refusal that names `--force`, enable checks what `--force` could not get past: a unit the snapshot names that is missing from the block, listed twice, or still neutralised under another event or matcher refuses with and without `--force` and names the ways out (`src/cli/gate/codex-enable.ts:144-145#"if (!plan.ok) throw"`), and the installer's post-edit guard runs on the planned result (`src/cli/gate/codex-enable.ts:148-151#"assertCodexHookEditInvariant(original"`). The planned restore is then applied without `--force` only when it rebuilds the pre-disable bytes exactly, for example a unit put back by hand with its original line; otherwise enable refuses and names `--force` (`src/cli/gate/codex-enable.ts:165-175#"edited since the snapshot was taken"`). Enable exits non-zero and names the units while any unit stays disabled, a unit the snapshot names is missing from the block (the snapshot then stays live), more than one live snapshot of the config remains, or a live snapshot of another config sits beside it (`src/cli/register-gate-gc-group.ts:270-275#"are missing from the harness-managed block"`).

`--force` is total: it restores every unit the snapshot names that is still neutralised (found by id), skips and reports every unit that is present and not neutralised, whatever its event or matcher now, so no unit is ever added twice and a live line is never overwritten (`src/cli/gate/codex-snapshot.ts:280-282#"if (unit !== undefined && !unit.disabled) {"`), keeps every other edit, and then retires the snapshot, so a second forced run has nothing to splice. It does not get past what no forced write could fix: a unit that is missing or changed while still disabled, and the post-edit guard. A snapshot whose recorded lines do not rebuild the config it was taken from is refused, with or without `--force`, when the config is exactly at the snapshot's post-disable state (`src/cli/gate/codex-enable.ts:157-159#"does not rebuild the config"`); on an edited config and in `gate disable` that check does not run. The missing or changed unit and the rebuild refusal name their way out, never `--force`; a post-edit guard refusal names the construct it could not edit, and the way out is to fix it or restore the backup the snapshot names. Every refusal that comes from the gate's own state (the block, a snapshot, an edit since the disable) names a way out of at most two commands: the fix the message names, then the refused verb again (for an edited config, `--force` is the whole fix). Snapshots from an earlier build, which kept one snapshot per disable, are the exception: enable applies the newest by its recorded `createdAt`, never by file mtime, retires it, and exits non-zero naming how many remain, so they take one enable each (`src/cli/gate/codex-snapshot.ts:403-405#"never by file mtime"`); a disable among several joins the newest. A later `harness apply --runtime codex --install` re-renders the whole block and brings disabled units back (`src/cli/gate/codex-disable.ts:8-9#"re-renders the whole block"`).

## Hooks without a matcher

The matcher is a literal substring of the hook group's `matcher`, so a group WITHOUT a matcher cannot be targeted by `gate disable` on either runtime (`src/cli/gate/disable.ts:211-213#"if (m === null) return false;"`, `src/cli/gate/codex-disable.ts:114#"unit.matcher !== null"`). A manifest hook with no `match` projects exactly such a matcher-less group (`src/cli/apply/generate-settings.ts:13-13#"is omitted when the manifest hook has no"`), and the documented runtime-reality hook entry is declared without `match` (`docs/runtime-reality-hook.md:22-28#"harness pack hook runtime-reality"`). Switch such a hook off with its own switch (`RUNTIME_REALITY_DISABLE=1` for runtime-reality, `docs/runtime-reality-hook.md:77#"short-circuit the hook entirely"`), give the entry a `match` and re-run `harness apply`, or remove it from the manifest and re-run `harness apply`.

## Branch-protection

branch-protection is the shipped gate the kill switch was written for: it asks git for the branch on every call and keeps no ledger tag, session state or override marker, and it never yielded to the removed pause. Its hook matches only `Write|Edit` on Claude Code and `apply_patch` on Codex (`src/policy-packs/builtin/branch-protection.ts:70-71#"PRE_TOOL_USE_MATCH_CODEX"`), so reach for the gate when the edit itself is refused.

- Claude Code: `harness gate disable` (list), `harness gate disable --matcher 'Write|Edit'` (quoted: an unquoted `|` is a shell pipe), do the edit, `harness gate enable`.
- Codex: `harness gate disable --runtime codex --matcher apply_patch`, do the edit, `harness gate enable --runtime codex`; see the pack doc (`docs/policy-packs/branch-protection.md:231#"Disable the gate (operator only)"`). On Codex, `enabled: false` on the pack plus `harness apply --runtime codex --install` does the same durably (`docs/policy-packs/branch-protection.md:248-248#"enabled: false"`).

## Recovery recipes

- Edit refused on a protected branch: the branch-protection recipe above, per runtime.
- A custom hook group blocks and you need it off for one call: list, disable by matcher substring, fix the underlying state, enable.
- `gate enable` refuses because the file was edited since the disable: read the diff against the `.bak.<ISO>` file the refusal names, then pass `--force`. Claude puts back every group still missing, leaves a group the file holds unchanged alone, keeps your other edits and retires the snapshot, so a second `--force` has nothing to apply; Codex restores every unit the snapshot names that is still neutralised, skips the ones that are back, keeps the other edits and retires the snapshot.
- Claude `gate enable` or `gate disable` refuses because the file holds a group with the event and matcher of a removed one but other content: the message prints both groups' commands, and the commands of every group still missing. If the file's group is the gate's (re-rendered by an apply), run the `harness gate enable --force --settings <path>` the message prints, which takes it as back. If it is another hook that shares the matcher, make the file hold the snapshot's group from the `.bak.<ISO>` file the message names (or remove the other group) and run `harness gate enable`; `--force` would leave the gate's group out. After a disable refusal, run the disable again once enable has exited 0.
- Claude `gate disable` refuses because a live snapshot names a group that is still missing and the file was edited since: run the `harness gate enable --force --settings <path>` the message prints, then run the disable again. The refused call wrote nothing; it only retired spent snapshots of an older release it walked past, and says so.
- Claude `gate enable` exits non-zero saying other snapshots are still live: they come from a release that wrote one snapshot per disable; run `harness gate enable` again until it exits 0.
- Claude `gate disable` or `gate enable` fails on a snapshot it cannot read, or cannot rename to `*.restored.json`: the message names the file; fix it or move it aside (rename it to `*.restored.json` once its groups are back), then run the verb again.
- Claude `gate disable` or `gate enable` says a snapshot "has no recorded target": its `settingsPath` was edited away or never written, so it cannot be matched to a settings file and is not guessed at. If the groups it names are still out of the settings file, put them back by hand (the snapshot's `settingsBackupPath` is the file before the disable, or restore the newest `.bak.<ISO>` beside the settings file), then move the snapshot aside (rename it to `*.restored.json`) and run the `harness gate enable --settings <path>` the message prints; it exits 0 once nothing is live.
- Claude `gate enable` through a symlinked `settings.json` says "settings file not found" for the file behind the link while a snapshot is live: the link's file was moved or deleted after the disable. Restore the file from the `.bak.<ISO>` file the message names, then run the printed command again.
- Claude `gate disable` or `gate enable` says the `settings.json` is a symlink to a file that cannot be written where it sits: the settings file was not changed. For a disable, make the directory writable (for `EPERM`, the file too) and run the printed disable again. When the message prints a `cp ... && mv ...`, putting that copy of the file in place of the link is the other way (the gate then edits a file it can write). When it names live snapshots beside the file instead, do not replace the link: an enable through the copy would not find them and would report nothing to restore while their groups are missing. Make the directory writable and run the printed `harness gate enable --settings <link>` first, which restores them; only then replace the link, if a copy is still wanted. A message that names the snapshot this very call wrote (the file was not changed) asks for the same order: run the printed enable, which only retires that snapshot, or move the snapshot aside, and then replace the link. For an enable, make the directory writable and run the printed enable again; a copy in place of the link would not find the snapshot beside the file, so if the directory must stay read-only, put the snapshot's groups back by hand (the snapshot lists them, `settingsBackupPath` is the file before the disable) and move the snapshot aside (rename it to `*.restored.json`) once the directory can be written.
- Claude `gate enable` exits non-zero naming a snapshot taken for another settings file: that snapshot names a different directory entry in the same directory (`settings.local.json`, say; a hard link to the settings file under another name; the file under its old name). Run the `harness gate enable --settings <dir>/<name>` the message prints, which restores the file the snapshot was taken for; running enable through a hard link to it is refused, with or without `--force`, because the write would land at the link's name and leave the recorded file as it is (a symlink to it is not such an alias: it is followed to the file, which is restored with the link left in place). If the message adds that no file is at that name, you renamed the settings file after the disable: rename it back, then run that command. If the file is gone for good, restore it from the `.bak.<ISO>` file the message names (the file before that disable) and run that command, which retires the snapshot; or move the snapshot out of the directory by hand once its groups are back. A disable through another spelling of the same name on a case-insensitive filesystem (`Settings.json`) needs nothing: it is the same entry.
- Codex `gate disable` refuses a second disable with "cannot join it" and names `--force`: the config was edited since the live snapshot and the snapshot still names units that are off. Run `harness gate enable --runtime codex --force`, then disable again. (A snapshot with nothing left to restore never causes this refusal: disable retires it and starts a fresh one. When `--force` could not restore the snapshot either, the refusal names the ways out of the next recipe instead.)
- A Codex verb says a unit of the snapshot "is not in the block" of the config "as it was" (the unit was deleted by hand, is listed twice, or was moved to another event or matcher while still disabled): no gate command can restore it, so `gate disable`, `gate enable` and `gate enable --force` all refuse, write nothing and name the ways out, never `--force`. Pick one. Run `harness apply --runtime codex --install` (with `--codex-config <path>` for a config you named, as the message prints it), which re-renders the block from the manifest and supersedes the snapshot, then run the refused verb again, which retires it (two commands). Or copy the backup the message names (the config before the snapshot's first disable) over the config, then run the refused verb again (two commands; every edit since that disable is lost). Or move the snapshot out of the directory and put back by hand the `hooks` line of any unit it names that is still off (the lines are in the moved file).
- Codex `gate enable` prints `skipped <snapshot>: taken for another config` with a `harness gate enable --runtime codex --config <dir>/<name>` command and exits non-zero, with or without units still disabled: the snapshot was recorded for another name in the directory (`other.toml`, say; a hard link or a second name of the config; the config under its old name; the name you meant when `--config` was mistyped). Exit 0 means no live snapshot remains beside the config. A config beside it that you keep disabled on purpose keeps this exit non-zero by design; `harness gate disable --runtime codex --config <this config>` lists this config's own units to confirm it is clean. Otherwise run the printed command (its path is shell-quoted), which restores the config the snapshot was taken for; enable through an alias of it never restores it, with or without `--force`. If the message adds that no file is at that name, you renamed the config after the disable: rename it back, then run that command. If the file is gone for good, restore it from the `<config>.bak.<ISO>` file the message names and run that command, which retires the snapshot; or move the snapshot out of the directory by hand once its units are back. A disable through another spelling of the same name on a case-insensitive filesystem (`Config.toml`) needs nothing: it is the same entry.
- Codex `gate enable` says a unit stays disabled and no snapshot restores it: a unit was neutralised by hand beyond the snapshot; put its `hooks` line back by hand, restore the config from the `<config>.bak.<timestamp>` beside it, or re-render the block with `harness apply --runtime codex --install`. When the same message adds that the live snapshot this call retired was superseded by a later install, that backup is not one of the message's ways out and must not be used (it predates the install): the next recipe's ways out apply.
- Codex `gate enable` or `gate disable` says it retired a snapshot because a later install re-rendered its units (the retirement line names the installer backup that dates the install) or re-rendered the harness-managed block (its generation marker changed), and enable exits non-zero naming a unit that stays disabled: the snapshot holds the hooks lines of a block that no longer exists, so it is never applied, with or without `--force`, and the still-disabled message no longer offers the stale backup; it names the ways out below. If the unit was neutralised again by a disable run through another spelling of the config (a second link to it), run `harness gate enable --runtime codex --config <that spelling>`: the snapshot beside it holds the current line. Otherwise re-run `harness apply --runtime codex --install`, which re-renders every unit, or put the `hooks` line back by hand. Do not restore the `<config>.bak.<timestamp>` that `gate disable` wrote beside the retired snapshot's spelling: that backup predates the install and holds the outdated line this rule keeps out; only a backup written after the install is safe.
- Codex says more live snapshots remain: an earlier build left one per disable; run `harness gate enable --runtime codex` again until none is left.
- Codex says a snapshot's unit is missing from the block while none of its units is off: that snapshot stays live and restores nothing; re-run `harness apply --runtime codex --install` (the install renames the snapshot to `*.superseded.json`), restore the config from the backup beside it, or move the snapshot file aside by hand if the unit is gone for good.
- A Codex verb says a live snapshot cannot be read (broken JSON, a version 2 file, a file that is not a Codex snapshot, a recorded config path with no file name such as an empty path, `.`, `..` or `/`, a `blockGeneration` that is not a block generation marker): it blocks both verbs on purpose, because guessing could leave a unit off. Move the named file out of the config's directory, then run the verb again; if units are still off afterwards, restore the config from the `<config>.bak.<timestamp>` beside it or re-render the block with `harness apply --runtime codex --install`.
- A Codex verb says it cannot retire the snapshot (the retired name is taken, for example by a directory): when enable says it restored the units the config is already restored, and a disable has written nothing. Move the named snapshot out of the directory by hand so it is never applied again, then run the verb again.
- Codex says the snapshot does not rebuild the config it was taken from: its recorded lines were altered, and nothing was written, with or without `--force`. Restore the config from the backup the message names, or re-render the block with `harness apply --runtime codex --install`, then run `harness gate enable --runtime codex`, which retires the snapshot.
- Codex enable says the config is not found while a snapshot is live: restore the config from the backup the message names, or write it again with `harness apply --runtime codex --install`, then run enable again.
- Codex disable says the config could not be written and the merged snapshot could not be put back either: fix what stopped the write (the message carries both errors), then run `harness gate enable --runtime codex`, which restores what is off.
- A settings file corrupted by hand: restore the newest `.bak.<ISO>` file next to it; on Claude the gate verbs refuse to operate on a file that is not a JSON object rather than overwrite it.
