# Kill switch: `harness gate disable` / `harness gate enable`

harness ships ONE operator kill switch: `harness gate disable` takes the hook groups or hook units whose matcher matches a substring out of the live runtime config with a reversible snapshot, and `harness gate enable` puts them back. `harness pause` and `harness resume` were removed in 1.0.0 (task 973163a4), and the gate verbs are their replacement: both are `REMOVED_COMMANDS` entries now, so a hook or `ux.run` line that still calls one is reported by validate, doctor and apply (`src/schema/removed-keys.ts:474-475#"the operator pause is removed"`).

## When to use this

- Lockout recovery: a hard-blocking hook refuses the calls you would use to recover.
- "Is this harness or my code?" debugging: switch one hook off, reproduce, enable it again.
- A deliberate edit on a protected branch (a hotfix on `master`): branch-protection is the shipped gate this is for.
- One specific hook group must be off for a while and you want the file state back afterwards.

To turn a shipped gate off permanently use NEITHER verb: set `policy_packs[].enabled: false` on the pack (`src/schema/policy-packs.ts:24#"enabled: z.boolean().default(true),"`) or remove the hook entry from the manifest, then re-run `harness apply`. Persistent, diff-able, source-controlled.

## Guardrail note

The gate is the "operator escape hatch for hard-blocking hooks" (`src/cli/register-gate-gc-group.ts:39#"operator escape hatch for hard-blocking hooks"`), but nothing enforces that in the CLI: `GateDisableOptions` is only `settingsPath | homeDir | matcher | now` (`src/cli/gate/disable.ts:33-50#"now?: Date"`), with no agent-session env-var or TTY refusal. An agent with Bash access can run the verb; the snapshot plus `.bak` file are the recovery record either way.

## Claude Code: settings.json surgery

Flags: `harness gate disable [--matcher <pattern>] [--settings <path>] [--runtime claude|codex]`, default runtime `claude`; `--config` belongs to `--runtime codex` and is refused here (`src/cli/register-gate-gc-group.ts:25-26#"only applies to --runtime codex; use --settings"`). The verb reads `~/.claude/settings.json` (`DEFAULT_SETTINGS_REL`, `src/cli/gate/disable.ts:31#"DEFAULT_SETTINGS_REL"`) and removes the hook groups whose `matcher` contains the pattern, a literal substring and not a regex (`m.includes(pattern)`, `src/cli/gate/disable.ts:184-192#"m.includes(pattern)"`). With no `--matcher` it is a pure listing of the candidate groups and writes nothing (`src/cli/gate/disable.ts:10-10#"pure listing"`); a `--matcher` that matches nothing errors and points at that listing (`src/cli/gate/disable.ts:222-223#"no hook groups matched"`). A settings file that is not a JSON object refuses the operation rather than being "fixed" (`src/cli/gate/disable.ts:110-115#"restore from a backup"`).

What it writes, in order: a backup of the original to `<settings.json>.bak.<ISO>`, a snapshot of the removed groups to `<settings-dir>/harness.gate-disable.<ISO>.json` (ISO stamps use `-` for `:`, `src/cli/gate/snapshot.ts:65-76#"bak."`), then the atomic rewrite of settings.json; the backup lands before any mutation and the snapshot before the live rewrite, so a crash between the writes never leaves settings.json mutated without its way back (`src/cli/gate/disable.ts:230-265#"atomicWriteFile(settingsPath, newSettings);"`).

Restore: `harness gate enable [--settings <path>] [--force]` picks the NEWEST `harness.gate-disable.*.json` snapshot next to settings.json by mtime (`candidates.sort`, `src/cli/gate/snapshot.ts:87-110#"candidates.sort"`) and splices the groups back at their recorded indices. Two safety behaviors: a file that already matches the pre-disable sha exits 0 without writing (idempotent, `src/cli/gate/enable.ts:160-163#"already-restored"`), and a file whose sha matches neither state (you edited it since the disable) refuses, so the restore cannot overwrite your edits: inspect the diff against the recorded `settingsBackupPath`, then pass `--force` (`src/cli/gate/enable.ts:166-171#"pass --force to restore anyway"`). Unlike Codex, the Claude gate never retires a snapshot: enable always picks the newest snapshot by mtime and leaves it in place after the restore (`src/cli/gate/enable.ts:186#"snapshotPath: latest"`). So undo several disables in reverse order (after each enable the next older snapshot is not picked automatically: move the restored snapshot aside, or restore settings.json from the oldest `.bak.<ISO>`), run `--force` at most once per snapshot (a second forced run splices the same groups in again), and confirm with `harness gate disable` (list) that the group is back.

## Codex: the harness-managed hook block

Flags: `harness gate disable --runtime codex [--matcher <pattern>] [--config <path>]` and `harness gate enable --runtime codex [--config <path>] [--force]` (task 1f6ec6c9). The default target is `~/.codex/config.toml` (`src/cli/apply/install-codex-config.ts:157-158#"config.toml"`); the verbs edit only the `# BEGIN harness-managed codex hooks` block that `harness apply --runtime codex --install` writes, and text outside the fences is never touched.

Disable does not delete a unit: the comment line, the `[[hooks.<Event>]]` header and the `matcher` line stay and the unit's `hooks = [...]` line becomes `hooks = []` (`CODEX_NEUTRALISED_HOOKS`, `src/cli/gate/codex-snapshot.ts:41#"CODEX_NEUTRALISED_HOOKS"`). Codex keys a user hook's trust and enabled state by the hook's position inside its event's array, and an empty group takes that position without registering a handler, so every other hook of every event keeps its position and its trust (`src/cli/gate/codex-disable.ts:10-10#"keys a user hook's trust and enabled state by its position in the event's"`). The matcher rule is the same literal substring as on Claude. The listing marks a unit an earlier disable already neutralised with `[disabled]`, and disable refuses to neutralise an already-disabled unit twice. A backup `<config>.bak.<ISO>` and a snapshot `harness.gate-disable-codex.<ISO>.json` land beside the config under its own file prefix (`src/cli/gate/codex-snapshot.ts:32#"CODEX_SNAPSHOT_BASENAME_PREFIX"`) with the config's own file mode, before the rewrite. The snapshot carries `version: 3` and `target: "codex"`, so a Claude settings snapshot is never restored into the Codex config and a Codex snapshot is never read as a settings.json one (`src/cli/gate/codex-snapshot.ts:13-15#"can never be restored"`).

At most one snapshot per config is live. A second `gate disable` while one exists backs the file up as usual and then merges the newly neutralised units into that snapshot, keeping the original pre-disable sha, recording the new post-disable sha and adding an audit entry (time, matcher, backup) to the snapshot's `merges` list (`src/cli/gate/codex-disable.ts:15-19#"merges its units into that snapshot"`). The backup and the merged snapshot are written before the config, so the config is never changed without both on disk; if the config write then fails, the snapshot is put back to its pre-merge body, so it never names units that are still enabled (`src/cli/gate/codex-disable.ts:236-256#"atomicWriteFile(configPath, next, { mode });"`). It can only join when the config is exactly what that snapshot left behind. A live snapshot that `gate enable` would only retire without writing is spent: an install re-rendered the block after it was taken, the config is back at the pre-disable state, or every unit it names is enabled again and still in the block. Disable retires a spent snapshot itself (the same `*.restored.json` / `*.superseded.json` rename) and starts a fresh one, with no enable in between (`src/cli/gate/codex-snapshot.ts:188-206#"export function spentCodexSnapshot"`, `src/cli/gate/codex-disable.ts:178-200#"spentCodexSnapshot("`). Any other live snapshot the config no longer matches refuses the disable, writes nothing and names `harness gate enable --runtime codex --force` (`src/cli/gate/codex-disable.ts:200-206#"cannot join it"`). A live snapshot that cannot be read refuses the disable too, rather than starting a second one, and the message names the file and says to move it aside (`src/cli/gate/codex-snapshot.ts:228-236#"move ${snapPath} aside"`).

Enable reads the one live snapshot taken for that config (another config's is skipped and named, `src/cli/gate/codex-enable.ts:4-11#"Another config's snapshot is skipped and named"`). If the config matches its post-disable sha, each unit gets its original `hooks = [...]` line back, the result must hash to the recorded pre-disable sha (byte-identical restore), and the snapshot is renamed to `*.restored.json` (kept for audit, never offered again). A config that already matches the pre-disable sha writes nothing, retires the snapshot and exits 0. A snapshot taken before a later `harness apply --runtime codex --install`, or whose units are all enabled again and still in the block, is renamed to `*.superseded.json` instead and never applied. The install is dated by the installer's `<config>.harness-backup-*` files beside the config (`src/cli/apply/install-codex-config.ts:2222-2223#".harness-backup-"`), which is the protection against an outdated snapshot putting an outdated hooks line back: delete or move those files and that protection is gone (`src/cli/gate/codex-enable.ts:16-17#"dates that write"`). A config that matches neither state (edited since, or left half-merged by a crash) is restored without `--force` only when skipping the units that are back already (present and not neutralised, never overwritten) rebuilds the pre-disable bytes exactly, for example a unit put back by hand with its original line; otherwise it refuses (`src/cli/gate/codex-enable.ts:25-34#"the restore skips every"`). Enable exits non-zero and names the units while any unit stays disabled, a unit the snapshot names is missing from the block (the snapshot then stays live), or more than one live snapshot remains (`src/cli/register-gate-gc-group.ts:172-195#"are missing from the harness-managed block"`).

`--force` is total: it restores every unit the snapshot names that is still neutralised (found by id), skips and reports every unit that is back already so no unit is ever added twice and a live line is never overwritten, keeps every other edit, refuses only a unit that is missing or changed (another event or matcher), and then retires the snapshot, so a second forced run has nothing to splice (`src/cli/gate/codex-enable.ts:25-34#"the restore skips every"`). A refusal therefore always has an exit in at most two commands. Snapshots from an earlier build, which kept one snapshot per disable, are still handled: enable applies the newest by its recorded `createdAt`, never by file mtime, retires it, and exits non-zero naming how many remain until you run it again (`src/cli/gate/codex-snapshot.ts:321#"never by file mtime"`); a disable among several joins the newest. A later `harness apply --runtime codex --install` re-renders the whole block and brings disabled units back (`src/cli/gate/codex-disable.ts:30-31#"re-renders the whole block"`).

## Hooks without a matcher

The matcher is a literal substring of the hook group's `matcher`, so a group WITHOUT a matcher cannot be targeted by `gate disable` on either runtime (`src/cli/gate/disable.ts:184-186#"if (m === null) return false;"`, `src/cli/gate/codex-disable.ts:132#"unit.matcher !== null"`). A manifest hook with no `match` projects exactly such a matcher-less group (`src/cli/apply/generate-settings.ts:13-13#"is omitted when the manifest hook has no"`), and the documented runtime-reality hook entry is declared without `match` (`docs/runtime-reality-hook.md:22-28#"harness pack hook runtime-reality"`). Switch such a hook off with its own switch (`RUNTIME_REALITY_DISABLE=1` for runtime-reality, `docs/runtime-reality-hook.md:77#"short-circuit the hook entirely"`), give the entry a `match` and re-run `harness apply`, or remove it from the manifest and re-run `harness apply`.

## Branch-protection

branch-protection is the shipped gate the kill switch was written for: it asks git for the branch on every call and keeps no ledger tag, session state or override marker, and it never yielded to the removed pause. Its hook matches only `Write|Edit` on Claude Code and `apply_patch` on Codex (`src/policy-packs/builtin/branch-protection.ts:70-71#"PRE_TOOL_USE_MATCH_CODEX"`), so reach for the gate when the edit itself is refused.

- Claude Code: `harness gate disable` (list), `harness gate disable --matcher 'Write|Edit'` (quoted: an unquoted `|` is a shell pipe), do the edit, `harness gate enable`.
- Codex: `harness gate disable --runtime codex --matcher apply_patch`, do the edit, `harness gate enable --runtime codex`; see the pack doc (`docs/policy-packs/branch-protection.md:231#"Disable the gate (operator only)"`). On Codex, `enabled: false` on the pack plus `harness apply --runtime codex --install` does the same durably (`docs/policy-packs/branch-protection.md:248-248#"enabled: false"`).

## Recovery recipes

- Edit refused on a protected branch: the branch-protection recipe above, per runtime.
- A custom hook group blocks and you need it off for one call: list, disable by matcher substring, fix the underlying state, enable.
- `gate enable` refuses because the file was edited since the disable: read the diff against the `.bak.<ISO>` file the refusal names, then pass `--force` (Claude splices the snapshot's groups back into the file as it is now and keeps other edits, but does not retire the snapshot, so run it once; Codex restores every unit the snapshot names that is still neutralised, skips the ones that are back, keeps the other edits and retires the snapshot).
- Codex `gate disable` refuses a second disable with "cannot join it": the config was edited since the live snapshot and the snapshot still names units that are off. Run `harness gate enable --runtime codex --force`, then disable again. (A snapshot with nothing left to restore never causes this refusal: disable retires it and starts a fresh one.)
- Codex `gate enable` says a unit stays disabled and no snapshot restores it: a unit was neutralised by hand beyond the snapshot; put its `hooks` line back by hand, restore the config from the `<config>.bak.<timestamp>` beside it, or re-render the block with `harness apply --runtime codex --install`.
- Codex says more live snapshots remain: an earlier build left one per disable; run `harness gate enable --runtime codex` again until none is left.
- Codex says a snapshot's unit is missing from the block: that snapshot stays live and restores nothing; re-run `harness apply --runtime codex --install` (the install supersedes the snapshot), restore the config from the backup beside it, or move the snapshot file aside by hand if the unit is gone for good.
- A Codex verb says a live snapshot cannot be read (broken JSON, a version 2 file, a file that is not a Codex snapshot): it blocks both verbs on purpose, because guessing could leave a unit off. Move the named file out of the config's directory, then run the verb again; if units are still off afterwards, restore the config from the `<config>.bak.<timestamp>` beside it or re-render the block with `harness apply --runtime codex --install`.
- Codex says it restored the units but cannot retire the snapshot (the retired name is taken): the config is already restored; move the named snapshot out of the directory by hand so it is never applied again.
- Codex says the snapshot does not rebuild the config it was taken from: its recorded lines were altered; nothing was written. Move the snapshot aside and restore from the `<config>.bak.<timestamp>`.
- A settings file corrupted by hand: restore the newest `.bak.<ISO>` file next to it; on Claude the gate verbs refuse to operate on a file that is not a JSON object rather than overwrite it.
