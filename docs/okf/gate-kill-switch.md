# Kill switch: `harness gate disable` / `harness gate enable`

harness ships ONE operator kill switch: `harness gate disable` takes the hook groups or hook units whose matcher matches a substring out of the live runtime config with a reversible snapshot, and `harness gate enable` puts them back. `harness pause` and `harness resume` were removed in 1.0.0 (task 973163a4), and the gate verbs are their replacement: both are `REMOVED_COMMANDS` entries now, so a hook or `ux.run` line that still calls one is reported by validate, doctor and apply (`src/schema/removed-keys.ts:474-475#"the operator pause is removed"`).

## When to use this

- Lockout recovery: a hard-blocking hook refuses the calls you would use to recover.
- "Is this harness or my code?" debugging: switch one hook off, reproduce, enable it again.
- A deliberate edit on a protected branch (a hotfix on `master`): branch-protection is the shipped gate this is for.
- One specific hook group must be off for a while and you want the file state back afterwards.

To turn a shipped gate off permanently use NEITHER verb: set `policy_packs[].enabled: false` on the pack (`src/schema/policy-packs.ts:24#"enabled: z.boolean().default(true),"`) or remove the hook entry from the manifest, then re-run `harness apply`. Persistent, diff-able, source-controlled.

## Guardrail note

The gate is the "operator escape hatch for hard-blocking hooks" (`src/cli/register-gate-gc-group.ts:40#"operator escape hatch for hard-blocking hooks"`), but nothing enforces that in the CLI: `GateDisableOptions` is only `settingsPath | homeDir | matcher | now` (`src/cli/gate/disable.ts:50-67#"now?: Date"`), with no agent-session env-var or TTY refusal. An agent with Bash access can run the verb; the snapshot plus `.bak` file are the recovery record either way.

## Claude Code: settings.json surgery

Flags: `harness gate disable [--matcher <pattern>] [--settings <path>] [--runtime claude|codex]`, default runtime `claude`; `--config` belongs to `--runtime codex` and is refused here (`src/cli/register-gate-gc-group.ts:27-27#"only applies to --runtime codex; use --settings"`). The verb reads `~/.claude/settings.json` (`DEFAULT_SETTINGS_REL`, `src/cli/gate/disable.ts:48#"DEFAULT_SETTINGS_REL"`) and removes the hook groups whose `matcher` contains the pattern, a literal substring and not a regex (`m.includes(pattern)`, `src/cli/gate/disable.ts:197-206#"m.includes(pattern)"`). With no `--matcher` it is a pure listing of the candidate groups and writes nothing (`src/cli/gate/disable.ts:20-20#"pure listing"`); a `--matcher` that matches nothing errors and points at that listing (`src/cli/gate/disable.ts:235-236#"no hook groups matched"`). A settings file that is not a JSON object refuses the operation rather than being "fixed" (`src/cli/gate/disable.ts:135-136#"restore from a backup"`).

What it writes, in order: a backup of the original to `<settings.json>.bak.<ISO>`, a snapshot of the removed groups to `<settings-dir>/harness.gate-disable.<ISO>.json` (ISO stamps use `-` for `:`, `src/cli/gate/snapshot.ts:112-115#"bak."`), then the atomic rewrite of settings.json; the backup lands before any mutation and the snapshot before the live rewrite, so a crash between the writes never leaves settings.json mutated without its way back (`src/cli/gate/disable.ts:262-315#"atomicWriteFile(settingsPath, newSettings);"`). The snapshot records the settings file and the backup as absolute paths; a relative `--settings` is resolved against the working directory at disable time.

One live snapshot per settings file. Snapshots always sit beside their file and record its path, and only the basename counts, never how the directory was spelled (relative to another working directory, through a symlink). A snapshot belongs to the settings file when the file names the directory entry that basename names: the same spelling, or, on a filesystem that folds letter case or normalization (APFS by default), another spelling that `lstat` resolves to the same regular file with a link count of 1 (`Settings.json` for `settings.json`), so no second name of that inode could be the one that matched (`src/cli/gate/snapshot.ts:275-306#"function namesSameEntry"`). Every other name is another entry: a hard link or a symlink to the settings file under another name, or the file under its old name. Restoring through such a name would write a new file at that name (the atomic write renames a temp file into place, which detaches a hard link and replaces a symlink) and leave the recorded file as the disable left it, so a snapshot recorded for one is foreign to the other, with or without `--force`. A live snapshot for another entry in the same directory (say `settings.local.json`, or such an alias) is not read as this one's and not merged into; `gate enable` exits non-zero while one is live, writes nothing, and names each with the command that restores it, `harness gate enable --settings <dir>/<recorded name>`; when no file is at that name now it adds the rename-back step, the `.bak.<ISO>` file to restore it from if it is gone (the file before that disable; the named command then retires the snapshot) and the move-aside step (`src/cli/register-gate-gc-group.ts:267-293#"function foreignSnapshotsNote"`). It never prints "nothing to restore" then. Enable looks for snapshots only beside the path it is given, so a symlink to the settings file in another directory finds none there and reports "nothing to restore" while the snapshot beside the real file stays live: run enable with the same `--settings` the disable used.

A removed group counts as back only when the file holds an unchanged copy of it. The snapshot's groups are paired with the file's one to one: first every group with a deep-equal group of the same event (key order does not matter), then each group left over with a group that has its event and matcher but other content (`src/cli/gate/snapshot.ts:473-484#"canonicalJson(g) === wanted"`). Such a "same matcher, other content" group may be the gate's group re-rendered, or another hook that shares the matcher (a formatter guard on `Write|Edit`, say), so the gate never takes it for the removed one on its own: plain `gate enable` and `gate disable` refuse and name its event and matcher and the commands of both groups, and only `gate enable --force` accepts it as back.

A second disable while a snapshot is live looks at the live snapshots newest first (`src/cli/gate/disable.ts:381-432#"function chooseSnapshot"`):

- The file is exactly the state that snapshot left (its post-disable sha): the call writes its own backup, merges the groups it removed into the snapshot and rewrites settings.json. The merge keeps the original pre-disable sha, backup and filter, moves the post-disable sha to the new state, tags every group with the step that removed it (`step`, 0 for the first disable, 1 for the next) and appends a `merges` entry with that call's matcher and backup (`src/cli/gate/disable.ts:293-306#"merges: ["`). A group's recorded `index` is its position in the array just before its own step, so restore undoes the steps newest first, and inside a step by event and ascending index (`src/cli/gate/snapshot.ts:486-492#"if (stepA !== stepB) return stepB - stepA;"`). If the settings write fails after the merged snapshot was written, the snapshot is put back to its body from before the merge and the error is reported; when that rollback fails too, both errors are reported with the way out, `harness gate enable` (it leaves a group the file still holds unchanged alone) and then the disable again (`src/cli/gate/disable.ts:324-333#"could not be put back"`).
- The snapshot is spent, that is `gate enable` would only retire it: the file holds every group it names unchanged, which includes being back at the pre-disable state (put back by hand, restored from the `.bak.<ISO>` file, a snapshot left live by an older release's enable). Disable retires it the way enable does, prints a `retired a spent snapshot as ...` line, and looks at the next older one or starts a fresh snapshot (`src/cli/gate/disable.ts:392-395#"plan.restored.length === 0 && plan.changed.length === 0"`).
- Otherwise the file was edited since and some group the snapshot removed is still missing, or is there only with other content. Disable refuses, names the snapshot, the missing groups with their commands and the differing ones with both groups' commands, and says to run `harness gate enable --force`, then the disable again; when a group is there only with other content, it names the other way too, for the case that the file's group is another hook: make the file hold the snapshot's group (the `.bak.<ISO>` file it names has it), run `harness gate enable`, then the disable again. It writes no backup and changes no snapshot; the only thing it does first is retire the spent newer snapshots it walked past (an older release's leftovers), so that way out stays two commands (`src/cli/gate/disable.ts:396-431#"harness gate enable --force"`).

A live snapshot that cannot be read makes disable and enable refuse before they write anything, because its target cannot be told; the message names the file: move it aside (rename it to `*.restored.json` once its groups are back) and run the verb again (`src/cli/gate/disable.ts:245-250#"cannot be read would be left out"`, `src/cli/gate/enable.ts:160-166#"Move ${found.path} aside"`). A retire the filesystem refuses (the rename to `*.restored.json`) fails the same way, naming the snapshot to move out of the directory by hand instead of a bare errno (`src/cli/gate/disable.ts:353-365#"function retireSpent"`, `src/cli/gate/enable.ts:274-284#"cannot retire the snapshot"`). Snapshots are version 2 now; a version 1 snapshot written by an earlier release is still read (`src/cli/gate/snapshot.ts:30-30#"LEGACY_SNAPSHOT_VERSION"`) and upgraded to version 2 when a disable merges into it.

Restore: `harness gate enable [--settings <path>] [--force]` applies the one live snapshot for this settings file and then retires it, renaming it to `harness.gate-disable.<ISO>.restored.json`, which stays on disk for audit and is never applied again (`retireSnapshot`, `src/cli/gate/snapshot.ts:232-236#"retireSnapshot"`). The live snapshots are the `harness.gate-disable.*.json` files beside the settings file that are not `*.restored.json` and belong to this settings file, newest `createdAt` first. What happens depends on the state of the file (`src/cli/gate/enable.ts:157-266#"export function gateEnable"`):

- It matches the snapshot's post-disable sha (nothing touched it since): every removed group goes back at its recorded position and the snapshot is retired. The result has the content the file had before the first disable. It is byte-identical only when that file was newline-terminated 2-space JSON with sorted events and no disable emptied an event or the whole `hooks` block; otherwise the indentation or key order can differ, and the snapshot's `.bak.<ISO>` file is the byte-exact original.
- It already matches the pre-disable sha (you restored it by hand): nothing is written, the snapshot is retired, exit 0 (`src/cli/gate/enable.ts:179-191#"already-restored"`).
- It holds a group with the event and matcher of a removed one but other content: enable refuses, names both groups' commands and any group still missing with its commands, and says to run `--force` if the file's group stands in for the snapshot's, or to make the file hold the snapshot's group (the `.bak.<ISO>` file has it) and run enable again (`src/cli/gate/enable.ts:196-212#"does not count as back"`).
- It holds every group the snapshot names unchanged although it was edited since: nothing is written and the snapshot is retired, exit 0 (`src/cli/gate/enable.ts:213-225#"plan.restored.length === 0"`).
- It matches neither state and some group is still missing: the missing groups are put back, and only when that gives exactly the pre-disable file (what a crash between the snapshot write and the settings write leaves behind) enable writes it. Anything else is an edit of yours, so enable refuses, names the missing groups with their commands, the snapshot and the `.bak.<ISO>` file to diff against, and says to run `--force` (`src/cli/gate/enable.ts:238-252#"harness gate enable --force"`).

`--force` is total: it puts back every group still missing, leaves a group the file holds unchanged alone, takes a group with the same event and matcher but other content as back (it is not put back) and prints the commands of both, keeps every other edit, and retires the snapshot, so a second `--force` finds nothing to apply and a group is never added twice (`src/cli/register-gate-gc-group.ts:201-205#"taken as back under --force"`). When nothing had to be written, the header says so without claiming the file holds every removed group: "nothing to put back ... there unchanged or taken as back under --force". Read the taken-as-back line before you rely on the gate again: when the file's group is not the gate's (a different command), the gate's group is still out of the file.

Exit 0 means no live snapshot remains beside the settings file, neither for it nor for another settings file in that directory, and every group those snapshots named is back unchanged, or was taken as back under `--force`. Releases before this change wrote one snapshot per disable and never retired them. When several are live, each enable handles the newest one, retires it and exits non-zero naming how many live snapshots remain (`src/cli/register-gate-gc-group.ts:225-231#"are still live next to"`); run `harness gate enable` again until it exits 0. Confirm with `harness gate disable` (list) that the group is back.

## Codex: the harness-managed hook block

Flags: `harness gate disable --runtime codex [--matcher <pattern>] [--config <path>]` and `harness gate enable --runtime codex [--config <path>] [--force]` (task 1f6ec6c9). The default target is `~/.codex/config.toml` (`src/cli/apply/install-codex-config.ts:165-166#"config.toml"`); the verbs edit only the `# BEGIN harness-managed codex hooks` block that `harness apply --runtime codex --install` writes, and text outside the fences is never touched.

Disable does not delete a unit: the comment line, the `[[hooks.<Event>]]` header and the `matcher` line stay and the unit's `hooks = [...]` line becomes `hooks = []` (`CODEX_NEUTRALISED_HOOKS`, `src/cli/gate/codex-snapshot.ts:42#"CODEX_NEUTRALISED_HOOKS"`). Codex keys a user hook's trust and enabled state by the hook's position inside its event's array, and an empty group takes that position without registering a handler, so every other hook of every event keeps its position and its trust (`src/cli/gate/codex-disable.ts:10-10#"keys a user hook's trust and enabled state by its position in the event's"`). The matcher rule is the same literal substring as on Claude. The listing marks a unit an earlier disable already neutralised with `[disabled]`, and disable refuses to neutralise an already-disabled unit twice. A backup `<config>.bak.<ISO>` and a snapshot `harness.gate-disable-codex.<ISO>.json` land beside the config under its own file prefix (`src/cli/gate/codex-snapshot.ts:33#"CODEX_SNAPSHOT_BASENAME_PREFIX"`) with the config's own file mode, before the rewrite. The snapshot carries `version: 3` and `target: "codex"`, so a Claude settings snapshot is never restored into the Codex config and a Codex snapshot is never read as a settings.json one (`src/cli/gate/codex-snapshot.ts:13-15#"can never be restored"`).

At most one snapshot per config is live. A second `gate disable` while one exists backs the file up as usual and then merges the newly neutralised units into that snapshot, keeping the original pre-disable sha, recording the new post-disable sha and adding an audit entry (time, matcher, backup) to the snapshot's `merges` list (`src/cli/gate/codex-disable.ts:15-19#"merges its units into that snapshot"`). The backup and the merged snapshot are written before the config, so the config is never changed without both on disk; if the config write then fails, the snapshot is put back to its pre-merge body, so it never names units that are still enabled (`src/cli/gate/codex-disable.ts:245-255#"atomicWriteFile(configPath, next, { mode });"`). It can only join when the config is exactly what that snapshot left behind. A live snapshot that `gate enable` would only retire without writing is spent: an install re-rendered the block after it was taken, the config is back at the pre-disable state, or every unit it names is enabled again and still in the block. Disable retires a spent snapshot itself (the same `*.restored.json` / `*.superseded.json` rename) and starts a fresh one, with no enable in between (`src/cli/gate/codex-snapshot.ts:264-271#"export function spentCodexSnapshot"`, `src/cli/gate/codex-disable.ts:180-186#"spentCodexSnapshot("`); when that rename fails (the retired name is taken), both verbs refuse with what they have done so far, the file and the move-aside step (`src/cli/gate/codex-snapshot.ts:166-180#"cannot retire the snapshot"`). Any other live snapshot the config no longer matches refuses the disable and writes nothing. That refusal names `harness gate enable --runtime codex --force` when a forced restore would put the units back, and otherwise, when a unit the snapshot names is missing from the block or changed while still disabled, the ways out of that snapshot instead of `--force` (`src/cli/gate/codex-disable.ts:198-202#"cannot join it"`). A live snapshot that cannot be read refuses the disable too, rather than starting a second one, and the message names the file and says to move it aside (`src/cli/gate/codex-snapshot.ts:313-317#"move ${snapPath} aside"`).

Enable reads the one live snapshot taken for that config (another config's is skipped and named, `src/cli/gate/codex-enable.ts:4-11#"Another config's snapshot is skipped and named"`). If the config matches its post-disable sha, each unit gets its original `hooks = [...]` line back, the result must hash to the recorded pre-disable sha (byte-identical restore), and the snapshot is renamed to `*.restored.json` (kept for audit, never offered again). A config that already matches the pre-disable sha writes nothing, retires the snapshot and exits 0. A snapshot taken before a later `harness apply --runtime codex --install`, or whose units are all enabled again and still in the block, is renamed to `*.superseded.json` instead and never applied. The installer retires the snapshot at the source: `harness apply --runtime codex --install` renames every live snapshot of the config it just rewrote to `*.superseded.json`, whatever backup files exist, looking beside the config and, for a symlinked config, beside the link and beside the target, and matching a snapshot by the file its recorded path names (same path, or the same device and inode, so a link or a hard link counts) (`src/cli/apply/install-codex-config.ts:2324#"export function writeCodexConfigInstall("`). A rename that fails never fails the install, which is already on disk: it warns on stderr, naming the snapshot and the step to move it out of the directory by hand, and leaves it live; a live snapshot the install cannot read is left alone and named the same way. The snapshot that install cannot find is the one taken through a symlink when the install is run on the target's own path (it sits beside the link, a directory the installer is not given). For that case, and for a snapshot written while an older installer ran, enable keeps a second line of defence: it dates the install by the installer's `<config>.harness-backup-*` files beside the config (`src/cli/apply/install-codex-config.ts:2230-2231#".harness-backup-"`), so a snapshot older than the newest install is retired as superseded and never applied. That second line depends on the backup files: delete or move them and a snapshot the install did not retire can still put an outdated hooks line back (`src/cli/gate/codex-enable.ts:16-17#"dates that write"`). A config that matches neither state (edited since, or left half-merged by a crash) gets a planned restore that skips every unit that is back already, present once and not neutralised whatever its event or matcher now, so its line is never overwritten, and puts back the rest, found by id (`src/cli/gate/codex-snapshot.ts:202-210#"export function planCodexRestore("`). Before any refusal that names `--force`, enable checks what `--force` could not get past: a unit the snapshot names that is missing from the block, listed twice, or still neutralised under another event or matcher refuses with and without `--force` and names the ways out (`src/cli/gate/codex-enable.ts:162-163#"if (!plan.ok) throw"`), and the installer's post-edit guard runs on the planned result (`src/cli/gate/codex-enable.ts:164-167#"assertCodexHookEditInvariant(original"`). The planned restore is then applied without `--force` only when it rebuilds the pre-disable bytes exactly, for example a unit put back by hand with its original line; otherwise enable refuses and names `--force` (`src/cli/gate/codex-enable.ts:174-184#"edited since the snapshot was taken"`). Enable exits non-zero and names the units while any unit stays disabled, a unit the snapshot names is missing from the block (the snapshot then stays live), or more than one live snapshot remains (`src/cli/register-gate-gc-group.ts:187-191#"are missing from the harness-managed block"`).

`--force` is total: it restores every unit the snapshot names that is still neutralised (found by id), skips and reports every unit that is present and not neutralised, whatever its event or matcher now, so no unit is ever added twice and a live line is never overwritten (`src/cli/gate/codex-snapshot.ts:228-230#"if (unit !== undefined && !unit.disabled) {"`), keeps every other edit, and then retires the snapshot, so a second forced run has nothing to splice. It does not get past what no forced write could fix: a unit that is missing or changed while still disabled, and the post-edit guard. A snapshot whose recorded lines do not rebuild the config it was taken from is refused, with or without `--force`, when the config is exactly at the snapshot's post-disable state (`src/cli/gate/codex-enable.ts:176-178#"does not rebuild the config"`); on an edited config and in `gate disable` that check does not run. The missing or changed unit and the rebuild refusal name their way out, never `--force`; a post-edit guard refusal names the construct it could not edit, and the way out is to fix it or restore the backup the snapshot names. Every refusal that comes from the gate's own state (the block, a snapshot, an edit since the disable) names a way out of at most two commands: the fix the message names, then the refused verb again (for an edited config, `--force` is the whole fix). Snapshots from an earlier build, which kept one snapshot per disable, are the exception: enable applies the newest by its recorded `createdAt`, never by file mtime, retires it, and exits non-zero naming how many remain, so they take one enable each (`src/cli/gate/codex-snapshot.ts:301-303#"never by file mtime"`); a disable among several joins the newest. A later `harness apply --runtime codex --install` re-renders the whole block and brings disabled units back (`src/cli/gate/codex-disable.ts:32-33#"re-renders the whole block"`).

## Hooks without a matcher

The matcher is a literal substring of the hook group's `matcher`, so a group WITHOUT a matcher cannot be targeted by `gate disable` on either runtime (`src/cli/gate/disable.ts:197-199#"if (m === null) return false;"`, `src/cli/gate/codex-disable.ts:135#"unit.matcher !== null"`). A manifest hook with no `match` projects exactly such a matcher-less group (`src/cli/apply/generate-settings.ts:13-13#"is omitted when the manifest hook has no"`), and the documented runtime-reality hook entry is declared without `match` (`docs/runtime-reality-hook.md:22-28#"harness pack hook runtime-reality"`). Switch such a hook off with its own switch (`RUNTIME_REALITY_DISABLE=1` for runtime-reality, `docs/runtime-reality-hook.md:77#"short-circuit the hook entirely"`), give the entry a `match` and re-run `harness apply`, or remove it from the manifest and re-run `harness apply`.

## Branch-protection

branch-protection is the shipped gate the kill switch was written for: it asks git for the branch on every call and keeps no ledger tag, session state or override marker, and it never yielded to the removed pause. Its hook matches only `Write|Edit` on Claude Code and `apply_patch` on Codex (`src/policy-packs/builtin/branch-protection.ts:70-71#"PRE_TOOL_USE_MATCH_CODEX"`), so reach for the gate when the edit itself is refused.

- Claude Code: `harness gate disable` (list), `harness gate disable --matcher 'Write|Edit'` (quoted: an unquoted `|` is a shell pipe), do the edit, `harness gate enable`.
- Codex: `harness gate disable --runtime codex --matcher apply_patch`, do the edit, `harness gate enable --runtime codex`; see the pack doc (`docs/policy-packs/branch-protection.md:231#"Disable the gate (operator only)"`). On Codex, `enabled: false` on the pack plus `harness apply --runtime codex --install` does the same durably (`docs/policy-packs/branch-protection.md:248-248#"enabled: false"`).

## Recovery recipes

- Edit refused on a protected branch: the branch-protection recipe above, per runtime.
- A custom hook group blocks and you need it off for one call: list, disable by matcher substring, fix the underlying state, enable.
- `gate enable` refuses because the file was edited since the disable: read the diff against the `.bak.<ISO>` file the refusal names, then pass `--force`. Claude puts back every group still missing, leaves a group the file holds unchanged alone, keeps your other edits and retires the snapshot, so a second `--force` has nothing to apply; Codex restores every unit the snapshot names that is still neutralised, skips the ones that are back, keeps the other edits and retires the snapshot.
- Claude `gate enable` or `gate disable` refuses because the file holds a group with the event and matcher of a removed one but other content: the message prints both groups' commands, and the commands of every group still missing. If the file's group is the gate's (re-rendered by an apply), run `harness gate enable --force` (same `--settings`), which takes it as back. If it is another hook that shares the matcher, make the file hold the snapshot's group from the `.bak.<ISO>` file the message names (or remove the other group) and run `harness gate enable`; `--force` would leave the gate's group out. After a disable refusal, run the disable again once enable has exited 0.
- Claude `gate disable` refuses because a live snapshot names a group that is still missing and the file was edited since: run `harness gate enable --force` (same `--settings`), then run the disable again. The refused call wrote nothing; it only retired spent snapshots of an older release it walked past, and says so.
- Claude `gate enable` exits non-zero saying other snapshots are still live: they come from a release that wrote one snapshot per disable; run `harness gate enable` again until it exits 0.
- Claude `gate disable` or `gate enable` fails on a snapshot it cannot read, or cannot rename to `*.restored.json`: the message names the file; fix it or move it aside (rename it to `*.restored.json` once its groups are back), then run the verb again.
- Claude `gate enable` exits non-zero naming a snapshot taken for another settings file: that snapshot names a different directory entry in the same directory (`settings.local.json`, say; a hard link or a symlink to the settings file under another name; the file under its old name). Run the `harness gate enable --settings <dir>/<name>` the message prints, which restores the file the snapshot was taken for; running enable through an alias of it is refused, with or without `--force`, because the write would land at the alias and leave the recorded file as it is. If the message adds that no file is at that name, you renamed the settings file after the disable: rename it back, then run that command. If the file is gone for good, restore it from the `.bak.<ISO>` file the message names (the file before that disable) and run that command, which retires the snapshot; or move the snapshot out of the directory by hand once its groups are back. A disable through another spelling of the same name on a case-insensitive filesystem (`Settings.json`) needs nothing: it is the same entry.
- Codex `gate disable` refuses a second disable with "cannot join it" and names `--force`: the config was edited since the live snapshot and the snapshot still names units that are off. Run `harness gate enable --runtime codex --force`, then disable again. (A snapshot with nothing left to restore never causes this refusal: disable retires it and starts a fresh one. When `--force` could not restore the snapshot either, the refusal names the ways out of the next recipe instead.)
- A Codex verb says a unit of the snapshot "is not in the block" of the config "as it was" (the unit was deleted by hand, is listed twice, or was moved to another event or matcher while still disabled): no gate command can restore it, so `gate disable`, `gate enable` and `gate enable --force` all refuse, write nothing and name the ways out, never `--force`. Pick one. Run `harness apply --runtime codex --install`, which re-renders the block from the manifest and supersedes the snapshot, then run the refused verb again, which retires it (two commands). Or copy the backup the message names (the config before the snapshot's first disable) over the config, then run the refused verb again (two commands; every edit since that disable is lost). Or move the snapshot out of the directory and put back by hand the `hooks` line of any unit it names that is still off (the lines are in the moved file).
- Codex `gate enable` says a unit stays disabled and no snapshot restores it: a unit was neutralised by hand beyond the snapshot; put its `hooks` line back by hand, restore the config from the `<config>.bak.<timestamp>` beside it, or re-render the block with `harness apply --runtime codex --install`.
- Codex says more live snapshots remain: an earlier build left one per disable; run `harness gate enable --runtime codex` again until none is left.
- Codex says a snapshot's unit is missing from the block while none of its units is off: that snapshot stays live and restores nothing; re-run `harness apply --runtime codex --install` (the install renames the snapshot to `*.superseded.json`), restore the config from the backup beside it, or move the snapshot file aside by hand if the unit is gone for good.
- A Codex verb says a live snapshot cannot be read (broken JSON, a version 2 file, a file that is not a Codex snapshot): it blocks both verbs on purpose, because guessing could leave a unit off. Move the named file out of the config's directory, then run the verb again; if units are still off afterwards, restore the config from the `<config>.bak.<timestamp>` beside it or re-render the block with `harness apply --runtime codex --install`.
- A Codex verb says it cannot retire the snapshot (the retired name is taken, for example by a directory): when enable says it restored the units the config is already restored, and a disable has written nothing. Move the named snapshot out of the directory by hand so it is never applied again, then run the verb again.
- Codex says the snapshot does not rebuild the config it was taken from: its recorded lines were altered, and nothing was written, with or without `--force`. Restore the config from the backup the message names, or re-render the block with `harness apply --runtime codex --install`, then run `harness gate enable --runtime codex`, which retires the snapshot.
- Codex enable says the config is not found while a snapshot is live: restore the config from the backup the message names, or write it again with `harness apply --runtime codex --install`, then run enable again.
- Codex disable says the config could not be written and the merged snapshot could not be put back either: fix what stopped the write (the message carries both errors), then run `harness gate enable --runtime codex`, which restores what is off.
- A settings file corrupted by hand: restore the newest `.bak.<ISO>` file next to it; on Claude the gate verbs refuse to operate on a file that is not a JSON object rather than overwrite it.
